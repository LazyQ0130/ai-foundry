# 扫码付款与人工核实开通

## 配置与上线

1. 备份数据库，部署时先执行 `npm run db:generate` 与 `npm run db:migrate`，再启动新版本服务。本次迁移只增加购买申请和私有凭据表、枚举及索引，不修改已有账号或权限。
2. 收款二维码使用仓库 `public/payment-alipay.png`、`public/payment-wechat.png`，从运营者提供的原图直接裁切，未重绘。两种付款方式默认展示的收款名均为“FY工作室”。上线前用对应支付 App 实际扫码，核对收款方、备注填写及金额输入；代码检查不能代替支付 App 的收款方核验。不要为测试实际转账。
3. 可用 `ALIPAY_PAYMENT_QR_URL`、`WECHAT_PAYMENT_QR_URL` 覆盖收款码，`ALIPAY_PAYMENT_NAME`、`WECHAT_PAYMENT_NAME` 设置收款名。URL 使用同源路径或 HTTPS；同源图片支持直接下载，外部图片的保存行为取决于浏览器与远端响应。设置空 URL 可关闭某种付款方式。
4. 管理员联系二维码继续使用 `WECHAT_QR_URL`，微信号继续使用 `WECHAT_CONTACT`；它们与付款码独立。配置变更后重启服务。

## 用户与管理员流程

- 用户登录选方案后准备付款申请。服务端保存方案名称、当前价格和“完整注册手机号｜课程方案”备注。后续打开同方案会复用未完成申请及价格快照，避免同一笔付款因改价丢失原金额。
- 用户选择支付宝或微信，填写完整备注并付款，无需点击“我已付款”或在站内上传截图。
- 管理员核对实际收款记录中的金额和备注，确认同一笔付款未重复使用，再进入“后台 → 用户管理”，搜索备注中的完整注册手机号，为该账号开通对应单阶段、全阶段课程版或项目版。
- 付款不会自动解锁课程，个人中心展示实际生效的课程权限。页面不承诺具体处理时长；有问题再联系管理员，提供注册手机号、课程方案及付款记录协助核实。
- 权益和审计日志同事务提交，已有生效权益的开通日期保持不变。已有部分权益购买套餐仍按套餐原价。
- 此前已提交的付款申请继续在后台“付款申请”页面处理；个人中心仅在存在这类记录时显示“历史付款申请”。历史需补充信息的申请仍可补充资料，避免旧记录失去处理入口。
- 历史凭据通过需要登录且不缓存的接口提供给本人或管理员。备份数据库时包含凭据；账号注销、凭据清理或退款仍按现有人工流程核实处理。
- 本期不接入支付网关、自动到账、差价计算或自动退款。退款沿用用户协议，首次开通后 72 小时内可申请；申请记录的“已开通”表示历史审核结果，实际学习权限以当前权益为准。

## 接口与校验

- 付款信息使用 `POST /api/purchases/prepare` 保存方案、金额与备注。正常扫码付款流程不调用凭据上传或申请提交接口。
- 为历史申请保留：`GET /api/purchases`，`GET /api/purchases/:id`，`PUT /api/purchases/:id/proof`（原始图片请求体），`POST /api/purchases/:id/submit`。
- 凭据：`GET /api/purchases/:id/proof?v=版本`，仅本人或管理员可访问。
- 管理员：`GET /api/admin/purchases`（手机号、方案及状态筛选），`GET /api/admin/purchases/:id`，`POST /api/admin/purchases/:id/review`。
- 提交和审核携带申请版本，阻止旧页面覆盖新提交。状态为 `DRAFT → PENDING → APPROVED` 或 `PENDING → NEEDS_INFO → PENDING`。用户不能设置价格、归属、审核结果或课程权限。
- 每账号每分钟最多 30 次购买写操作；管理员接口沿用后台权限及同源请求保护。

## 回归验证

运行 `npm run typecheck`、`npm run build`、`npm test`。测试脚本只迁移和写入独立 `aifoundry_test` schema；既有购买测试继续覆盖历史申请及凭据的安全性。上线前检查手机与桌面的付款码、保存、备注复制，以及管理员按手机号手动开通后个人中心权限生效；正常购买页面不应出现付款凭据提交按钮或表单。
