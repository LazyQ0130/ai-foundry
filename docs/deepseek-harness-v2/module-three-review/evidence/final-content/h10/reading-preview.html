Agent Loop：Turn、Step 与任务执行状态机

150～200 分钟（分三段；作者估算，实际时长待试读，环境准备另计）

同一个助手为什么又问了一次模型？

工作台已经能创建和关闭Agent。现在给其中的A发送任务：“请读取README，概括项目功能，并检查相关测试文件。”第一次模型输出没有摘要，而是一个读取请求；工具返回README后，模型又要求读取测试；第二个工具结果回来，模型才生成答复。界面一直显示同一个助手在工作，后台却有三次模型请求。

如果第一次请求失败后重试，总数会变成四次。这是否意味着四个Step？用户中途补充“先看空输入的测试”，该开新Agent，还是接着当前任务做？输入被策略拒绝、根本没有问模型时，还能留下一轮工作的记录吗？这些判断关系到界面如何显示进度，也关系到失败后能用哪些事实解释刚才发生的事。

这节的产出是一张你亲手标注的轨迹：当前在哪个Turn、哪个Step；请求试了几次；下一次推进由工具反馈、待办输入还是重试决定。 H03画过整体请求流，本节打开Driver里的判断条件；H09解决实例的生存与释放，本节只研究一个已经创建的实例怎样工作。

history.push(userInput)

这段代码抓住“模型判断→工具反馈→再次判断”，却没有回答输入何时接纳、运行时新消息放哪里、请求失败怎样重试、取消以后还欠哪些记录。官方Loop在这条主线上加入了工作边界、待办箱和停止决策。不要只把while写得更长；先确定每个可观察状态意味着什么。

回忆六项前置知识：H03里Session保存交互事实；H09里Registry委托Factory创建实例，Handle负责释放，Turn结束不销毁实例；H06的Waterfall把参数交给监听器和next()，返回决策会改变后续路径；H07的Fiber/Effect管理插件资源；await暂停当前异步函数，其他任务仍能发送消息；AbortSignal传递停止请求，不能强制杀死任意Promise。本节的Loop Phase属于某个Agent的驱动活动，不是Cordis Fiber的状态。

Agent实例是带id、Session、Inbox、Scope与当前状态的活对象；Agent Loop是推进其工作的一套驱动逻辑。默认实现中，AgentLoop服务提供工厂，创建ReactLoopAgent实例，其私有turn/step方法落实循环。同一个实例可以先后跑很多Turn，共享服务也不把多个实例的队列合并成一个。

用一个下载按钮理解状态机

状态就是程序此刻允许做哪些事；事件是外部或内部发生的输入；转换是收到事件后改变状态。例如这个可运行的JavaScript小程序，只演示状态机，不模拟Harness：

JAVASCRIPT静态预览：可选择代码复制
let state = 'ready'
function receive(event) {
  if (state === 'ready' && event === 'click') state = 'loading'
  else if (state === 'loading' && event === 'done') state = 'ready'
  return state
}
console.log(receive('click')) // loading
console.log(receive('click')) // loading：不会再启动一次
console.log(receive('done'))  // ready

边界的用处是让“按钮按了两次”有唯一解释。Loop也要防止一条新输入在已有Driver运行时又开一个Driver。不同的是，它还需要记录工作编号、待办和取消信号，单个字符串不足以描述全部状态。

四个单位：先会数，再看循环

**Turn（轮次）**是Driver管理的一轮工作边界，以turn/start和turn/end记录。**Step（步骤）**是Turn内一次模型判断及其相关工具执行的工作边界，以step/start和step/end记录。通常可把一个Step理解为“请求模型，结算它的输出，再处理这份输出中的工具”；但正式Step已经打开以后，也可能在请求准备阶段被取消，实际模型调用为零。

**Attempt（请求尝试）**是同一Step内的一次请求尝试。失败满足恢复条件、监听器明确要求重试时，可以留在当前Step再次请求。**Tool Call（工具调用）**是模型输出中的某项工具请求；同一份输出可以含多个调用，因此一个Step可以有零个、一个或多个Tool Call。

输入怎样找到下一次接纳位置

Inbox（待办箱）保存尚未进入模型历史的输入。它不是作者随手写的数组，而是根据Session中的agent/inbox/spliced事实维护的两份视图；投影实现留H17。本节只读inbox.ts:73–112的工作接口。

入口通常入队位置主动唤醒已在正常运行时，输入通常在哪接纳
followupnext-turn是下一Turn开始的候选Step
steernext-step是当前Turn后续候选Step
injectnext-step否现有Driver下次领取；若真正idle则停放等待

“通常”有明确例外：若已有活动的信号已aborted，此时调用会唤醒的followup/steer，send()把输入转投next-turn并申请收束后的唤醒。inject仍不主动唤醒。源码在170–197行。本课运行测试覆盖正常运行中的三入口；“abort后转投”的细分竞态仅核对源码，不冒称已实测。

领取次序更值得亲手算。claim('next-turn', turn)先取走全部next-step，再取走一个next-turn；claim('next-step', turn)只取全部next-step。两次队列变更先记录，再通知实时agent/inbox/claimed。假设维护期间依次注入I、排普通任务F1/F2、steer S，第一轮领取是I,S,F1，第二轮才是F2。这不是按所有入口的调用时间混排。

领取会把输入从待办移除，但还没有产生普通user/message。如果随后pre-step拒绝，刚领取的输入不会自动退回；其他未领取输入可能仍停放。inbox.clear()则会记录明确的canceled移除，顺序是next-step在前、next-turn在后。领取移除与主动取消不能混用一个词。

Turn先开始，Step却还只是候选

沿turn()，327–433行读一次完整工作。进入时先检查活动信号，再计算新Turn编号，追加turn/start。此时尚未请求模型，Step计数还是零。每轮正常切到下一Turn时Step计数重置，所以下一个Turn又从Step 1开始；编号必须写成(turn, step)二元组。

循环接下来准备候选Step：先按target领取输入，再捕获model.current()的选择快照，解析该选择下可见的工具集合，等待System Prompt组装，然后调用agent/pre-step的Waterfall。见preStep()，283–317行。工具与组装都可能异步等待，取消检查也在正式Step之前发生。模型选择、工具集和Prompt在这里取得一致的候选视图；System Prompt构造算法留H11。

agent/pre-step不是“Step已开始后的通知”。它能接纳、改写输入或拒绝。本课默认路径会整理运行上下文候选，随后返回enter；监听器也可以返回reject。只有接纳且需要实际执行，才追加step/start。 首次拒绝时Turn记blocked并停止，因此存在一轮零Step。首次接纳结果为空时也可能直接completed且零Step。已经有停止候选、又准备到空消息时，也可以直接退出，不再开一个空Step。

在纸上标出五个时刻：①Turn开始；②输入领取；③候选被接纳并打开Step；④实际向适配器发请求；⑤Turn最终结束。①与③之间有拒绝/取消；③与④之间还有请求准备、绑定和历史提交。任何两点合并，都会让某个失败分支解释不通。

Step结束后，为什么还继续？

普通工具批次结束且未声明concluded时，step()返回null，意思是“尚无结束候选，继续让模型消化结果”。无工具的正常答复返回completed；max-tokens返回对应结束候选；工具批次的concluded也可能给出completed。它们都还要交给Turn层判断。

如果已有结束候选，而且next-step为空，Driver才串行通知agent/turn-stopping。通知期间可以有新输入进来，之后再次检查next-step；有输入就继续当前Turn。尚无结束候选的普通工具反馈路径不会在每个Step后都发这个通知。见368–404行。

结束后turn/end记录reason。正常落到函数尾部时，若仍有待办，重置下一轮活动信号与Step计数，返回true给kick()再开Turn；否则返回false回idle。首次拒绝、空输入的早退，以及异常收束，并不承诺自动把所有尾部待办耗尽。实践D08验证拒绝后F2仍在队列，不能用whenIdle()当作“所有输入都已完成”的回执。

还有一个读日志时的小心点：max-tokens结束候选具有保留性。本课停止监听器再steer一次，后续Step正常回答，最终Turn仍记max-tokens。最终reason描述整轮的结束状态，不能只从最后一条Assistant文本倒推。

打开Step之后：先准备，再把输入写成事实

这是本节最重要的一条顺序。先读step()的435–486行，再读prepareRequest()，613–652行：

  1. 候选阶段已经捕获模型选择、解析工具、组装Prompt并通过pre-step；Turn层记录step/start。
  2. Step渲染Prompt；请求尝试循环准备配置，经agent/request和llm.prepareCall绑定有效路线，沿途检查取消。
  3. 准备成功后刷新运行上下文，投影并提交系统提示；第一次尝试才把本Step接纳的输入提交为消息。
  4. buildRequest()按需记录请求头、工具表面变化和请求上下文，再从session.deriveMessages()派生历史并冻结本次请求。
  5. 实际发送，消费流式输出，结算Assistant；需要时执行工具批次；退出时由Turn层记录step/end。

这条顺序解释一个看似矛盾的实验结果：日志已经有step/start，模型请求数却是零，而且没有本次system/message、user/message。实验在agent/request处暂停并取消，准备阶段尚未越过消息接纳边界。不能说“只要Step开始，用户消息一定已经写入”；也不能说“先写入全部消息，再选适配器”。本课用真实适配器绑定路线；源码还保留NO_ADAPTER时由中间件提供路线的兼容分支，不把所有部署简化成同一失败点。

下一Step为什么能读到工具结果

请求历史不直接拼接Inbox或UI消息。buildRequest()从已记录事实派生消息，并冻结这一次的边界视图，见656–744行。在README任务中，请求1没有工具结果；Step 1的Assistant、tool/call、tool/result已提交后，请求2才派生到README结果；Step 2又提交测试结果，请求3才同时看到两份内容。旧请求不会随Session增长而偷偷变长。

我们的分析：把“当前打算做什么”和“已证明发生什么”分开，让重试、界面和后续请求有共同依据。这里只解释Loop调用这些接口的位置；H17再研究事件与投影。Session追加成功是会话日志接纳边界，不自动证明磁盘已经flush。本课Session完全在内存中。

模型响应结束，工具工作才接上

流开始时建立本次Attempt，逐块推送实时agent/assistant-stream；正常完成会把完整Assistant内容与嵌入流结算到Session，再发送带提交seq的end帧。见assistant-stream.ts:49–104。收到一个text-delta只能证明看见临时内容，不能证明已有assistant/message。

随后，Step检查finish reason与tool calls：max-tokens先返回，不执行其中的工具请求；没有工具则给completed候选；有工具才调用tools.execute()，等待批次，并把附加上下文放进next-step，见577–609行。Step边界覆盖了这批相关工具，而不是每个工具单独开一个Step。并发、守卫、审批及执行器内部留H14。

失败不是一条统一的重试箭头

同一Step内的重试

本课让官方MockAdapter第一次抛出LlmError。LLM Runtime把它规范成请求失败的流结束；Loop结算assistant/attempt后，询问agent/request-error的Waterfall。监听器返回{ kind: 'retry' }，取消检查通过，才在Step内continue。没有这个决策，就抛出错误并结束本轮。见535–571行。

这次continue重新准备请求，但不会重新走pre-step、解析本Step工具集或组装候选Prompt，也不会把用户输入再接纳一遍。实验D09实测计数：pre-step=1、assemble=1、agent/request=2、模型请求=2。Prompt按准备好的结果投影，运行上下文可在尝试间刷新，不意味着所有请求相关事件都只发生一次。

并非任何throw都进入这条恢复支路。agent/request中间件直接抛错发生在流开始之前，本课D10看到零模型请求、零request-error调用和Turn error。流迭代异常、结算失败等也有各自catch路径；不能把“模型服务限流的规范化错误结束”推广成“任何失败都会自动重试”。真正的退避预算与恢复策略留H20。

工具主体失败，与工具结果未知

实践让read_fixture主体抛出FIXTURE_READ_FAILED。真实工具流水线把它规范成错误tool/result，Loop仍进入Step 2，模型据此回答“不能声称读到内容”，Turn是completed。completed表明控制流收束，不担保用户业务目标成功。 前端如果把它显示成“文件已读取”，就是用控制状态替代任务结果。

若工具批次调度或日志提交等基础设施失败，Step层还会尝试为缺失结果补全记录，再让Turn走error/aborted。已提交的tool/result、只被模型请求却没有tool/call的调用，以及已有tool/call却缺少结果的调用，证据不同。固定源码的ToolCallRecovery，105–193行区分TOOL_NOT_STARTED与TOOL_OUTCOME_UNKNOWN。后者不能推成“工具没有副作用，可以放心重跑”。本课只静态审读这一修复分支，未运行进程崩溃、未知外部副作用或真实工具恢复。

取消要问：取消发生在哪个边界？

cancel()默认清空两份Inbox并撤销待放行唤醒；keepInbox=true则保留尚未领取的输入，再中止当前非idle活动。它不销毁Agent，也不会把已经领取的输入重新排队。信号让协作方退出；如果作者自制的监听器正在等一个不理会信号的Promise，仍要释放那道门，不能期望cancel强制打断JavaScript。

agent/request尚未放行1 / 0尚未提交step/end，再turn/end aborted
流已给出partial正文1 / 1已提交非空部分内容结算为interrupted assistant/message，再结束边界

表中每行都先等Turn确实开始。若信号在turn/start之前已经aborted，源码会先检查并退出，不能承诺每次cancel都新增一条turn/end。流已开始但无可结算内容时也可能留下assistant/attempt；本课流取消实测的是已有非空文本的分支。事件结算失败、取消胜过重试等更深组合，保留给H20而不虚构通过。

export async function routing() {

export async function cancellation(kind: CancelCase) {

    const hook = async (_event: any, next: any) => { entered.resolve(); await release.promise; return next(); };
    if (kind === 'pre-step') h.ctx.on('agent/pre-step', hook);
    else if (kind !== 'stream') h.ctx.on('agent/request', hook);
    else h.ctx.on('agent/assistant-stream', ({ frame }) => { if (frame.type === 'chunk' && frame.chunk.type === 'text-delta') entered.resolve(); });
    h.agent.followup(message('正在处理')); await entered.promise;
    if (kind === 'keep-inbox' || kind === 'drop-inbox') {
      h.agent.followup(message('后续普通输入')); h.agent.inject(message('待处理上下文'));
    }
    h.agent.cancel({ kind: 'user' }, { keepInbox: kind === 'keep-inbox' });
    const afterCancel = { nextTurn: h.agent.inbox.nextTurn.length, nextStep: h.agent.inbox.nextStep.length };
    release.resolve(); await h.agent.whenIdle();
    return { afterCancel, ...snapshot(h, adapter) };
  } finally { release.resolve(); await h.close(); }
}

思考 1：三次API请求，能确定三个Step吗？

想深入再看：思考 1 参考答案

不能。直接三次模型判断可能是三个Step；第一次判断失败并重试，第二次判断直接结束，则可能是两个Step、三次请求。若同Step连续失败两次再成功，也可能只有一个Step。还要看turn/step边界与尝试归属。请求次数描述对模型的派发，Step描述Loop的工作边界；准备期取消甚至会留下一个Step而零请求，所以两种计数在两个方向都不能互相替代。

思考 2：轨迹有turn/start→claimed→turn/end(blocked)，没有user/message，输入去哪里了？

想深入再看：思考 2 参考答案

这是候选Step接纳前拒绝的轨迹。claim已经从Inbox移除输入并通知claimed，随后pre-step返回reject，所以没有step/start，也没有把输入提交成普通user/message；Turn仍有开始与blocked结束。已领取输入不会自动退回，其他未领取的next-turn输入可以保留。要检查此前的spliced事实和当前Inbox，不能把“没有user/message”理解为“输入从未入队”，也不能把blocked理解为“整张待办表都清空”。

思考 3：一个Assistant消息有两个Tool Call，随后回答，共有几个Step？

想深入再看：思考 3 参考答案

在普通工具反馈且没有结束工具、额外输入或失败的前提下，是两个Step。第一个Step请求模型并处理这一份输出中的两个工具调用，第二个Step读取两份工具结果后回答。两个工具可以有各自call/result事实，但它们共享第一个Step的(turn,step)位置。若模型分两次才决定两项调用，就会变成三个Step。工具并发顺序会影响执行时序，不直接把一个Step切成多个Step。

思考 4：为什么重试不能再把这条用户消息追加一遍？

想深入再看：思考 4 参考答案

用户输入在当前Step第一次成功准备请求之后已经接纳；重试是再次请求同一工作，不是用户又发了一条消息。若每次重试都追加一次，后续历史会出现重复要求，计数与因果关系也失真。源码用firstAttempt限制接纳，重试仍可准备有效请求路线、投影Prompt和刷新上下文。D09的1次pre-step/组装与2次请求说明重试循环位于Step内部，但并不等于请求相关所有状态完全冻结不变。

思考 5：轨迹是step/start→取消→step/end→turn/end(aborted)，请求数0，缺了哪些必需事件？

想深入再看：思考 5 参考答案

仅凭这些信息不能断言缺事件。如果取消发生在agent/request等待门或其他提交前的异步准备点，正式Step已经打开，实际模型派发与本次消息接纳尚未发生，完全可以没有user/message、assistant/message和实时流start。需要核对取消位置、已接纳历史及信号检查。此题和实践D的request路径一致；Step结束事件说明边界收束，不证明Step中每项计划动作都已经执行，更不能伪造一条Assistant答复补齐画面。

思考 6：前端已经显示半句答复，为什么还不能确认Session已有Assistant消息？

想深入再看：思考 6 参考答案

实时chunk先被发布，前端可以立刻绘制临时文本，完整Assistant事实却要等结算追加。正常settle先append，再发带seq的committed end；追加失败可能abandon临时行。取消时非空部分内容可能形成interrupted消息，也不能把它当完整回答。要确认已提交，关联Session事件与end的outcome，而不是只看屏幕文字。即便Session追加成功，本课内存实验也没有证明磁盘flush；这属于另一层持久化保证。

思考 7：运行中先followup，再steer，下一次请求必然处理followup吗？

想深入再看：思考 7 参考答案

不必然。正常运行未取消时，followup在next-turn等待，steer在next-step等待；当前Turn的下一个候选Step先领取next-step，所以通常先处理steer。当前Step若已发出不可变请求，steer不会回头改写那份请求，而是影响后续接纳。等当前Turn收束、正常推进下一Turn，才领取一个next-turn，且仍先合并全部next-step。若发送时活动已aborted，还要应用唤醒输入转投next-turn的例外，不能把正常路线当作所有竞态的保证。

思考 8：已经有completed候选，Driver为什么还能继续当前Turn？

想深入再看：思考 8 参考答案

completed是Step交给Turn的停止候选，Turn还会检查next-step；若有输入就继续。候选存在且队列空时，Driver发出串行turn-stopping通知，等监听器完成后再检查一次。监听器steer的新输入或期间到来的输入都可能使同一Turn继续。普通工具反馈返回null则还没有停止候选，直接继续下一次判断。下一Turn的followup与本Turn的next-step不同；不能只看“还有消息”就判定必然同Turn，也不能只看某个Step返回completed就宣布Driver已经idle。
