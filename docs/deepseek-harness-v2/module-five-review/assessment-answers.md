# 18题标准答案、逐步推导与评分

每题完整上下文见[题册](assessment.md)，交互预览包含相同上下文与折叠答案。允许等价的有依据推导，按分项给分，不按关键词匹配。

## Q01｜事件位置与Header（4分）

**标准答案**

长度6，末Seq5，结尾Offset6；读取1/2/3共3条；Header不占Seq；不能承诺磁盘恢复。

**逐步推导**

1. 先区分元数据与事件。
2. Seq指事件位置，Offset可指结尾；半开区间排除4。
3. 内存追加没有参与存储或屏障的证据。

**评分 Rubric**

- 长度/末Seq/Offset全对1分
- 区间结果1分
- Header不占1分
- 解释缺后端/屏障1分

**常见错误及分析**

- 把Header当seq0，会整体偏一。
- 构造SessionSeq(6)可通过数字校验，仍不证明本日志存在事件6。

## Q02｜按位置替换Surface（4分）

**标准答案**

第一次拒绝，节点和日志不变；来源至少覆盖[6,4]后该user替换合法，节点[0,7,5]，2条消息；原日志增长到8条，旧1/2/4/6都保留。

**逐步推导**

1. 端点在当前位置6先于4，不能按数值排序。
2. 缺4导致源覆盖不全，失败发生commit前。
3. 修正后7占被遮蔽span起点；5为空developer不产Message。

**评分 Rubric**

- 位置判断1分
- 拒绝与最小来源1分
- 节点/消息数1分
- 日志保留且增长1分

**常见错误及分析**

- 以6>4拒绝合法位置跨度。
- 把summary替换解释为删掉旧磁盘记录。

## Q03｜Projection不是另一份真源（4分）

**标准答案**

idle/0/0→running/1/0→同一running对象→同一对象→completed/1/1；状态变化通知2次，asOfSeq3。无关事件新对象可触发多余通知；反过来原地改旧对象可能掩盖变化。

**逐步推导**

1. 按事件顺序折叠，不由最终聊天文本猜任务。
2. 通知受state和view引用门控。
3. snapshot说明覆盖切面；解释规则/版本才使重建可重复。

**评分 Rubric**

- 状态轨迹1分
- 2次通知与引用1分
- asOfSeq3 1分
- 解释新对象或原地修改问题1分

**常见错误及分析**

- 把snapshot当不依赖事件/单元版本的独立权威数据。
- 误称live每步必过完整stateSchema。

## Q04｜读写所有权（4分）

**标准答案**

B可读，C写冲突，D可读；A成功close后新writer可取得。seam至少实施同后端实例单写者；JSONL使用内核机制提供指定平台的跨实例/PID排他。

**逐步推导**

1. read不占写权。
2. 跨实例排他不是一个进程Map独自实现。
3. 关闭释放当前句柄所有权，历史保留。

**评分 Rubric**

- B/D可读1分
- C拒绝与关闭后接管1分
- seam/JSONL分层1分
- 平台范围和close非删除1分

**常见错误及分析**

- 将Windows已验推广到NFS/POSIX/跨登录全部已验。
- 把旧writer重新使用当作新所有者。

## Q05｜Append与Flush（4分）

**标准答案**

直接writer.flush不负责drainLive；应对活Session用ctx.sessions.flush或服务flush并确认对应writer与成功结果。无writer的true只说明监听者存在，e2可能仅在内存。失败要观察、保留待写事实并按支持路径重试，不能报告耐久成功。

**逐步推导**

1. 先定位Promise覆盖的对象。
2. 区分Session提交、句柄接受与路由排空。
3. 后端成功屏障才按其契约解释持久性。

**评分 Rubric**

- 直接flush范围1分
- 无writer true反例1分
- 正确入口及writer前提1分
- 失败不宣称已存1分

**常见错误及分析**

- 把所有同名flush当同一个排空操作。
- 把JSONL每批sync推成所有后端append都同步。

## Q06｜JSONL重新打开的证据（4分）

**标准答案**

none为1 Header+5事件，Seq仍0..4；魔数对应默认Zstd，不能按UTF-8 JSON行直接读；V3源在内存迁移后可返回V4逻辑值，源未必发布后继。新PID正常读取不证明完整Agent崩溃后恢复或断电耐久。

**逐步推导**

1. 把物理编码、逻辑格式和事件位置分开。
2. 比对Header/每条事件/消息，而非只看文件存在。
3. 核是否真实退出进程、哪个组件重新运行。

**评分 Rubric**

- 6行/Seq1分
- Zstd解释1分
- V3/V4/源不变1分
- 新PID与真实崩溃/E边界1分

**常见错误及分析**

- 把只读迁移当写迁移已通过。
- 把新后端对象当全新操作系统进程。

## Q07｜Resume、Fork与运行父级（4分）

**标准答案**

正常Resume多普通marker16，共17；Fork继承0..9共10，子10 tagged marker、11 UNKNOWN引用9、12 step/end、13 turn/end forked，共14。普通sessions.fork仅活内存Session，不自动writer或parentAgent，不重放旧工具。

**逐步推导**

1. 切点包含，先数原前缀。
2. marker与closer属子自有事实。
3. 普通Fork持久化必须另接工厂writer；谱系与runtime所有权分开。

**评分 Rubric**

- 17/14/继承10 1分
- 子新增顺序及原因1分
- 无工具重放1分
- writer/parentAgent边界1分

**常见错误及分析**

- 用父后来result10补回切点9的子历史。
- 把Fork等同Subagent激活。

## Q08｜物理尾与语义尾（4分）

**标准答案**

甲返回合法前缀，read和write-open本身不改文件，新append前处理撕裂尾并保持已提交字节。乙不是因开放Turn就物理损坏；Agent恢复层用同writer补UNKNOWN、step/end、turn/end interrupted，再构造生命周期marker。

**逐步推导**

1. 先检物理记录合法性。
2. 完整开放生命周期由语义repair处理。
3. 任何坏Seq/未知必需格式不能用删尾一概处理。

**评分 Rubric**

- 甲读取不修改1分
- 甲新append时修尾1分
- 乙语义所有者与顺序1分
- 完整坏数据拒绝/原前缀保留1分

**常见错误及分析**

- 删掉完整tool/call以得到看似闭合日志。
- 认为所有撕裂Zstd帧必须整帧全丢。

## Q09｜缺失ToolResult的三种输入（4分）

**标准答案**

按提议序只补a NOT_STARTED（无call来源）、b UNKNOWN（source=[7]）；c保持原result。再补开放step/end、turn/end interrupted。call是登记接手，早于dispatch，不能单凭它证明主体生效。

**逐步推导**

1. Recovery按callId及Turn/Step追待答。
2. 已有append结果移除待答；关闭Step清集合。
3. 错误结果陈述证据缺口，不撤销效果。

**评分 Rubric**

- 两码及顺序1分
- 来源与c保留1分
- Step/Turn顺序1分
- call/副作用边界1分

**常见错误及分析**

- 给a伪造一个开始来源。
- 把b补成成功或自动执行写工具。

## Q10｜Token预算与计量（4分）

**标准答案**

T7000，R1440；6999不触发，7000合格；Usage1170，reasoning不重复；1120仅提示词侧input+cache，不含output，不能拿它替代当前完整measure或金额。

**逐步推导**

1. T取窗口比例和W−O−B中较小者。
2. R分母W−O=9000。
3. 合格后仍先prune/重测，非保证一定摘要。

**评分 Rubric**

- T7000及边界1分
- R1440和分母1分
- Usage1170 1分
- UI/measure/费用分层1分

**常见错误及分析**

- 把所有数都当精确分词或同一账单分项。
- 把摘要maxTokens当会话O。

## Q11｜Compaction选区与工具配对（4分）

**标准答案**

第一例必须整体保留A/T，可压缩U；第二例整体工具单元保留后无较早可用范围，可能null。无实际replaceGeneration进展，Basic不能凭这一路授权重试；可按合法开放Turn先prune再测，但不保证最终能装下。

**逐步推导**

1. 切点前仍有待答调用则向前移。
2. 保护首system，不能拆消息或配对凑预算。
3. 执行函数/新增日志不等于模型输入实际变小。

**评分 Rubric**

- 整体保留A/T 1分
- U与第二例null 1分
- 进展条件1分
- prune条件与不保证1分

**常见错误及分析**

- 按最近N个日志事件截断，忽略仅日志与消息节点。
- 认为retain0可以随意切断最后一个工具单元。

## Q12｜Overflow与普通Retry（4分）

**标准答案**

Retry先：计划1、摘要0；Basic先：计划0、摘要1；两例普通请求均2。不能推广全局2次；normal耗尽可委派独立Basic，其他输入恢复也可能接手，always又无normal次数上限。

**逐步推导**

1. normal合格就自己恢复，不自动先next。
2. Basic取得输入进展后直接返回retry。
3. 预算键/重置和下游所有权必须分别解释。

**评分 Rubric**

- Retry先结果1分
- Basic先结果1分
- 说明Waterfall接手原因1分
- 否定全局上限并给独立预算路径1分

**常见错误及分析**

- 把两个插件都想成每个错误各加一次重试。
- 认为always保证成功或默认等同normal。

## Q13｜指数退避与取消（4分）

**标准答案**

450ms和1100ms；normal对20000委派不写本插件计划，always回退本地算法。等待中取消清timer，可有retry无started、无下一请求；started即使存在也只说明等待结束，不证明成功。

**逐步推导**

1. 先指数封顶，再乘.9+.2U，最后再次封顶。
2. Provider延迟在有效范围原样用，超范围不等同截成M。
3. signal/lifetime负责取消等待，Step/Turn仍需结束。

**评分 Rubric**

- 450/1100及计算1分
- normal/always区别1分
- 计划无started合法1分
- 等待/请求/成功区别1分

**常见错误及分析**

- 第二次仍算550。
- 将已提交计划当每个后端fsync完成，或重开自动继续旧timer。

**评分 Rubric**

## Q15｜综合B：真实JSONL保存、恢复与Fork（10分）

**标准答案**

取得工厂writer→真实任务→sessions.flush→Handle.read核前缀→dispose/close→新Context+JSONL同root→agents.resume；原16条相等，marker后17，模型消息/头相等且旧调用0。sessions.fork用于内存对照，官方buildForkSeed含9+inherited10交agents.create取新writer，子14。父子新任务后26/23，双方旧前缀相等且专有输入不串；单写者冲突拒绝。全部仅同进程新实例，不自动是独立进程崩溃。

**逐步推导**

1. 每个root来自mkdtemp，所有权与try/finally配对，不读个人Home。
2. 检查点核真实参与者，不用文件存在或flush布尔单独证明。
3. 切点包含及子marker/closer与源继承分开。
4. 保存/重开/继续/分支未来均比对实际对象，最后观察close结果。

**评分 Rubric**

- 隔离root/API/所有权与收尾2分
- 保存+新实例Resume的前缀/消息/旧调用0 3分
- 持久分支接线+10/14计数3分
- 独立未来26/23及平台证据范围2分

**常见错误及分析**

- 直接sessions.fork后声称已持久化。
- 把新后端实例当独立进程，或为清理执行递归删除。

## Q17｜综合D：Retry与取消的两条未来（8分）

**标准答案**

## Q18｜综合E：非幂等未知结果的完整诊断（10分）

**标准答案**

拒绝盲重与补造成功；先取得Session写权、读有效前缀并保守补UNKNOWN/开放边界，不执行工具。通过获授权的只读查询核业务键/资源身份/状态，证实已创建则使用既有资源并记录新的有依据核查事实；查不到也不能仅凭缺日志断定未生效，无法确定则请用户决定或停止。真正幂等重发必须由外部系统强制键协议支持。normal/always仅控制明确模型Attempt恢复，不能重接用户或重做所有工具；压缩只改变当前Surface不删事实；取消阻止新工作并排空已启动，不回滚效果。真实外部结果、实际Provider费用与E仍待证据，盲重未知写或虚假耐久/成功为P0阻断。

**逐步推导**

1. 先分已提交/已持久/外部状态/控制signal四层。
2. UNKNOWN是认识边界，自动错误不是撤销通知。
3. 核业务键与准确资源，不把相同prompt/callId当幂等。
4. 决定后生成新的有来源事实，保留原错误和原始失败证据。
5. 评估哪些测试只是Map模拟，哪些是真实JSONL，不能升级E或声称真实学员理解。

**评分 Rubric**

- 故障层与保守修复且不重放3分
- 外部只读核查/业务键/无法确定停止3分
- Retry/Compaction/Cancel边界2分
- 证据等级/未验证与P0门禁2分

**常见错误及分析**

- 重发成功就认为原操作没有发生，可能创建两份。
- 删除原错误或把合成UNKNOWN当业务回滚。
- 只背“幂等”一词却不说明谁实施、如何核查，不能得外部协议分。
