## “我读过了”这句话，应该由什么证明？

你向项目助手发出一个很普通的任务：**“请帮我读取项目 README，概括它的主要功能。”**

如果你已经把 README 全文贴在消息里，模型可以根据这些文字直接概括。可如果你只给了文件名，模型接到的并没有文件内容。它即使回答得像模像样，也不能证明读过你电脑上的文件。正确的系统需要先取得允许读取的内容，再把内容交给模型。

这就出现了一连串具体问题：消息先由谁接收？模型什么时候被调用？谁真正读文件？读取失败后，模型怎样知道？界面上出现“正在读取”，是不是已经有一条可恢复的记录？

H01 解释了这些职责为什么需要 Harness，H02 帮我们找到对应的包。这节把地图变成时间顺序。课末你要画出一条完整运行线，并解释**多走一步、被拒绝、被取消、运行失败**分别发生在哪里。

:::concept{title="本课的范围与版本"}
研究的是固定 Commit `f3803c96974ad4a94195fb97e5c637e9c2a3afe3` 的默认 Agent Loop，以及已挂载模型适配器、使用原生工具执行器时的主线。具体入口如何把网页或 CLI 消息送到 Agent，在不同产品中可以不同；我们从它们共同使用的 Agent 输入接口开始。

**官方实现**标出真实文件和行号；**教学简化**保留关键顺序，但不代表完整实现；**我们的分析**用于解释取舍。这里不安装整个 Harness，也不展开 H10–H12、H14、H17 的全部算法。
:::

## 用六分钟找回 Stage 4 的闭环

Stage 4 的 [4.1](/lesson/stage-4/s4-l1) 已经做过两种固定模型响应：Direct 直接回答；Tool 先提议一个工具调用，收到结果后再回答。其正文强调“模型提议、应用验证、服务端执行”，并要求检查工具名、严格参数、调用上限与取消。

先把那条线写出来。下面是**教学伪代码**，不是本版本的 API：

```text
重复，但不能无限进行：
    响应 = 模型(当前历史, 可用工具说明)
    如果是回答：记录并尝试结束
    如果是工具提议：检查 → 执行允许的工具 → 把结果交回模型
    遇到取消、错误或明确的运行边界：按对应原因停止
```

注意“把结果交回模型”。如果工具读到了 README，却没有把内容送入后续请求，模型仍没有看过它。工具调用（Tool Calling）是一种结构化提议与反馈机制，不能把模型输出的一句“读取 README”当成文件读取。

4.5 把搜索、整理、提议保存与人工确认串成 Workflow（工作流），同时提醒：页面时间线不代表已经写入数据库。4.6 才加入 Run、Step、Action 的持久化与安全恢复点。H03 继续追问相同的问题，但开始使用 Harness 自己的运行单位和事件词汇。

:::deepdive{title="基础回顾：没上过 Stage 4，也能继续"}
Runtime 在这里指控制运行的程序职责：什么时候请求模型、怎样检查和分派工具、怎样推进状态与停止。它不是某个必须存在的 `Runtime` 类。模型做建议，工具实现做具体操作，Runtime 把两者接成受控反馈。

状态管理就是把“现在进行到哪里、哪些事实已经发生”保存成明确的数据。Stage 4 中，Run 是一次研究任务、Step 是其中的步骤、Action 是待确认写提议；**不要把这套字段直接搬到 Harness，认为名字相同就定义相同**。Harness 的 Turn 与 Step 要按下面的源码重新确认。

## 先把四种“东西”分开

### Session 记经历，Agent 推进正在发生的工作

先想一张持续使用的工作记录：昨天读过什么、今天收到什么、哪次读取报错，都能写进去。**Session（会话）**解决“这段交互有哪些已经接纳的运行事实”这个问题。在 Harness 中，它持有有序的事件日志，并能从其中派生模型所需的消息历史。

**Agent** 则是当前推进工作的运行实例。可以把 Session 看作工作记录，Agent 看作此刻使用记录的执行者。严格地说，两者不是“文件与人”的关系：Session 也有内存对象与投影；Agent 也不一定是独立进程。源码的创建契约使用同一个 `sessionId` 作为 Agent 与会话身份，[`CreateAgentOptions` 的 59–68 行](PIN/packages/core/agent/src/index.ts#L59-L68)说明了这一点。

**Agent Lifecycle（实例生命周期）**问的是“这个实例何时被创建、可以使用、运行、停止和释放”。它比一次任务长。创建时要先准备会话与作用域，完成 setup，再对外登记 Agent；参见 [`initializeAgent()`，621–640 行](PIN/packages/core/agent-loop/src/index.ts#L621-L640)。一轮工作结束后，实例通常回到 idle，还能接下一条消息，并不是自动销毁。拥有它的 handle 被释放时才会停止、等待退出并清理注册与作用域，见 [`AgentHandle` 注释，150–162 行](PIN/packages/core/agent/src/index.ts#L150-L162)。释放运行对象也不能被理解成删除了已经持久保存的历史。

常见误解是“会话还在，就一定有 Agent 在后台工作”。会话记录与一个正在运行的实例不是同一件事。先检查自己：关闭执行实例后，为什么仍可能有记录可读？因为记录描述过去的事实，不以运行器此刻仍活着为前提。

### Inbox：先收进待办篮，不代表已经交给模型

**Inbox（输入队列）**解决“执行器忙着时，新输入先放在哪里，以及在哪个边界领取”。像把一张任务单放进待办篮：收到、领取、接纳进本次工作，是不同动作。

本例使用 `agent.followup(message)`。官方 [`followup()`，179–181 行](PIN/packages/core/agent-loop/src/agent.ts#L170-L189)将消息送到 `next-turn`，并请求唤醒驱动。Inbox 还支持 `next-step`，后续可用于转向或补充上下文；本课不展开所有并发输入规则。

真实 Inbox 的变更先写入 `agent/inbox/spliced` 会话事实，再发相应通知；领取通过 `claim()` 从队列移出消息。证据在 [`inbox.ts` 的 108–112 行](PIN/packages/core/agent-loop/src/inbox.ts#L108-L112)与 [215–230 行](PIN/packages/core/agent-loop/src/inbox.ts#L215-L230)。所以，**“队列里收到过”不等于“模型历史里已经有”**。如果接纳环节拒绝，模型可见的 `user/message` 根本不会产生；队列事实仍记录了输入的流转。

待办篮类比也有边界：实际有两条有序队列、消息身份和事件重建，不是任意塞进一个数组。现在只需回答：为什么消息显示“已发送”，还不足以证明模型读到了它？因为它可能仍在排队，也可能领取后被拒绝。

### Turn 与 Step：一轮工作可以包含几次判断

**Turn（轮次）**解决“这一次驱动处理工作的边界在哪里”。就像接过一张任务单，持续处理到一个结束点；处理中可能多次查资料和作判断。它不是一次模型 API 请求。

**Step（步骤）**解决“这轮工作中，下一次模型判断与由此产生的工具动作算哪一段”。在官方定义中，一个 Step 包含一次模型请求及其相关工具调用；一个 Turn 包含零个或多个 Step，见[架构文档 81–87 行](PIN/docs/architecture.zh.md#L81-L87)。多个工具调用可能属于同一 Step；只回答、没有工具，也仍然是一个 Step。

把 README 场景放进去：第一步模型提出读取；程序执行读取并得到结果。第二步模型看见结果，给出摘要。这是一个 Turn、两个 Step、一次工具调用。如果先读 README，又读它引用的 USAGE，再总结，可以有三个 Step。

更容易读错的是零 Step。官方 `turn()` **先追加 `turn/start`，再领取和检查输入**；`agent/pre-step` 返回 reject 时，以 `blocked` 关闭这一 Turn，不创建 `step/start`。请核对 [`turn()`，327–361 行](PIN/packages/core/agent-loop/src/agent.ts#L327-L361)，以及[拒绝测试 253–274 行](PIN/packages/core/agent-loop/tests/interception.spec.ts#L253-L274)：模型请求为零，没有 `user/message`，但有轮次起止。

![三个轮次分别展示：接纳前拒绝产生零 Step；直接回答产生一个 Step；读取工具并回读结果产生两个 Step。Step 内同时包含模型请求和相关工具执行](/course-media/harness-v2/h03/h03-02.png "图 1｜Turn 是工作边界，Step 是模型判断及相关动作的边界。图中无重试；一次 Step 内的重试可能产生多个模型请求尝试，不能据 Step 数硬推网络请求数。")

这张图的边框是包含关系，不是进程和线程。Turn/Step 编号把事实关联起来，不代表自动提供事务回滚。普通两步案例中两次模型请求对应两个 Step；特殊情况下，失败请求可在**同一个 Step 内重试**，源码在 [`step()` 的 541–563 行](PIN/packages/core/agent-loop/src/agent.ts#L541-L563)，具体策略留 H20。

先口述一次：只有工具调用才有 Step 吗？不是。输入被拒绝为什么还有 Turn？因为轮次边界在接纳决定之前已经打开。

## 一次请求：从待办篮到新的观察

下面以“输入被接纳、模型先要工具、然后回答”为主线。图中在对应阶段标出写入 Session 的会话事实，因为记录贯穿运行过程，不能只在最后画一个“保存”。

![输入通过 followup 入队并唤醒驱动，turn/start 后领取输入、选择模型与组装材料，经 pre-step 接纳才打开 Step。准备适配器后提交消息与请求快照，模型流结算为助手消息，工具分派记录调用与结果；右侧虚线返回候选 Step 的准备，底部另列实时通知，停止检查后写 turn/end](/course-media/harness-v2/h03/h03-01.png "图 2｜默认循环的完整主线。蓝色为处理，青绿为会话事实，琥珀为决定或边界；右侧虚线表示继续下一 Step，底部单列实时观察。图中省略历史压缩、并发工具和多入口传输，条件分支见正文。")

### 1. 收到输入，打开轮次，再决定是否接纳

应用入口先把用户内容转换成输入消息，调用已有 Agent 的 `followup()`。`send()` 让 Inbox 插入消息，并请求驱动工作；它不是直接调用模型。驱动的 `kick()` 可以接连处理轮次，完成后把运行状态切回 idle，见 [`send()`、`wakeDriver()` 与 `kick()`](PIN/packages/core/agent-loop/src/agent.ts#L170-L280)。

`turn()` 写入 `turn/start` 后调用 `preStep()`。后者领取输入，取得当前模型选择，解析本步工具集合，组装提示词材料，再经过 `agent/pre-step` 接纳决定。输入是待领取消息与当前运行位置，输出是 reject，或带消息、模型选择和工具集合的准备结果。证据在 [`preStep()`，283–317 行](PIN/packages/core/agent-loop/src/agent.ts#L283-L317)。

这个扩展点本身不是一次模型调用，也不是每次都要问人。输入拒绝与工具审批是不同边界：前者可能让本轮一个 Step 都不进入；后者发生在模型已经提议工具之后。解析模型或提示词出错，也可能在 Step 开始前终止轮次。

### 2. 准备请求：不只有用户的一句话

消息被接纳后，程序追加 `step/start`。随后要准备三类东西：

| 请求材料 | README 任务中的具体作用 |
| --- | --- |
| 模型路由与控制参数 | 选择 provider、model，以及适用的输出等配置 |
| 指令与消息历史 | 系统指令、已接纳输入、以前的回答和工具结果 |
| 本步可用能力与运行边界 | 工具说明、会话身份、取消 signal 等 |

**Prompt Assembly（提示词组装）**先用人话说，就是“把这一步该交代的要求收齐”。像向同事交接：任务是什么、哪些资料可用、哪些工具能用，需要一起说明。严格到本实现，`systemPrompt.assemble()` 返回结构化组装材料，`renderPrompt()` 再将材料渲染为提示内容；它不是把日志全文拼成一个字符串。对应 [`preStep()` 的组装](PIN/packages/core/agent-loop/src/agent.ts#L287-L307)与 [`step()` 的 435–460 行](PIN/packages/core/agent-loop/src/agent.ts#L435-L460)。类比中的同事会自行理解环境，模型请求则必须拿到明确的数据，不能靠文件名猜内容。

**Model History（模型历史）**是“这次实际给模型看的既有对话”。它像从工作记录中整理出的交接材料，不是把所有流水账全寄过去。严格地说，`Session.deriveMessages()` 根据当前消息表面派生消息；Turn 边界、排队记录和失败 attempt 不会因此都变成聊天消息。源码见 [`deriveMessages()`，999–1029 行](PIN/packages/core/session/src/index.ts#L999-L1029)。这里的“消息表面”暂且理解为目前有效的消息视图，其投影与压缩留 H17–H19。

还有一处值得停下来读：在默认已注册适配器路径中，循环先执行 `prepareRequest()`，用 `ctx.llm.prepareCall()` 绑定准备好的模型调用与有效配置，**之后**才提交本次接纳的系统、用户消息。不是先把输入记成模型历史，再随便找一个 Provider。阅读 [`prepareRequest()`，613–652 行](PIN/packages/core/agent-loop/src/agent.ts#L613-L652)和 [`step()`，443–479 行](PIN/packages/core/agent-loop/src/agent.ts#L443-L479)。若准备阶段失败，Step 已打开，但待进入的用户消息不一定已经提交。

`buildRequest()` 按需要写入 `request/header` 与 `request/context`，再从 Session 派生并冻结本次请求消息，见 [656–744 行](PIN/packages/core/agent-loop/src/agent.ts#L656-L744)。前者记有效调用配置和工具描述等请求头信息；后者记录模型上下文容量等信息。它们不是每个 Step 都强制新增一份；配置未变时可以复用。首次接纳的用户消息也不是下一 Step 又复制一次。后续模型看见工具结果，来自增长后的历史。

检查理解：第二次模型请求里，README 内容来自用户新发了一遍消息吗？在本例中不是，它来自第一步留下的工具结果。

### 3. 模型流：边生成边显示，不等于每一块已经落盘

LLM 服务将准备好的调用分派到同一适配器；[`LlmRuntime.prepareCall()`，960–1017 行](PIN/packages/llm/llm/src/index.ts#L960-L1017)会保留注册信息与有效配置，返回的 `stream` 负责该次分派。适配器把不同 Provider 的响应转为共同的流结构，本课只确认这个边界，协议转换留 H12。

**Stream（流）**解决“能不能逐步消费生成结果，而不必等全部结束”。像逐页接收传真，你可能先看见半句话。技术上，这里是可以异步迭代的响应块，块可携带文本、工具调用、用量或结束等信息，不能把每块简单等同一个字或一个 token。

循环使用 `AssistantStreamAttempt` 汇集这些块，并通过 `agent/assistant-stream` 发出 start、chunk、end 实时帧。成功结算时，先把完整 `assistant/message` 及紧凑流数据追加到 Session，才发送带会话序号的 committed 结束帧。证据是 [`AssistantStreamAttempt`，49–108 行](PIN/packages/core/agent-loop/src/assistant-stream.ts#L49-L108)，以及[实际顺序测试 79–123 行](PIN/packages/core/agent-loop/tests/loop.spec.ts#L79-L123)。

常见误解是“屏幕已经出现文字，刷新就肯定能找回”。还不一定。中途失败可能留下 `assistant/attempt`，取消且已有安全前缀时则可能留下 `interrupted: true` 的助手消息；没有开始的分派甚至不会有 live start。部分文字不是完整答案，也不能把实时块画成一连串已持久化的 `assistant/chunk` 事件。

:::deepdive{title="Session 事实与磁盘持久化，还隔着一层"}
这里说“提交到 Session”，首先指通过校验并加入它的内存日志，向 `session/event` 观察者发布；[`Session.commit()`，892–911 行](PIN/packages/core/session/src/index.ts#L892-L911)实际执行的是 `log.push(event)`。是否持久保存、何时 flush，还要由生命周期接入的日志写入方处理。SessionStore 注释明确说明本身不实现持久化，见 [1057–1063 行](PIN/packages/core/session/src/index.ts#L1057-L1063)。

因此，带 seq 的 committed end 表示这次 Session 结算完成，不等于磁盘已经刷新。日志提供上下文重建与恢复的依据，也不等于能把进程恢复到原来那一行，更不会自动撤销已经发生的外部操作。H17、H18 会专门验证这些区别。
:::

### 4. 模型提议工具，程序执行后才产生新的观察

**Tool Call（工具调用提议）**说的是“想调用哪个工具、带什么参数”；**Tool Result（工具结果）**说的是“执行系统实际返回了什么”。像一张领料单与仓库回执：领料单不证明货已经拿到，回执中的失败也不能改成成功。

在实现中，模型的 `tool-call` 块先作为助手响应的一部分结算。循环再取出这些块，通过 `ctx.tools.execute(...)` 送往工具系统，见 [`step()` 的 566–597 行](PIN/packages/core/agent-loop/src/agent.ts#L566-L597)。工具服务按当前选择的执行器分派；本课选原生执行器，沿用 H02 找到的[服务入口](PIN/packages/core/tools/src/index.ts#L369-L377)与[原生委托](PIN/packages/core/tool-executor-native/src/index.ts#L15-L35)。

原生批次执行先记录某调用开始的 `tool/call`，再进入准备与执行；准备包含登记/参数相关检查、执行前策略、可能的审批、守卫与取消检查。证据在 [`batch.ts` 的 154–170 行](PIN/packages/core/tools/src/batch.ts#L154-L170)与 [`pipeline.prepare()`，190–231 行](PIN/packages/core/tools/src/pipeline.ts#L190-L231)。所以 **`tool/call` 记录本身仍不能证明工具主体成功执行**。拒绝也需要产生相应结果。

实际结果以 `tool/result` 写入会话，并通过调用身份与来源序号关联，见 [`BatchSettlement`，243–265 行](PIN/packages/core/tools/src/batch.ts#L243-L265)。下一 Step 派生消息时便能得到 `role: tool` 的结果。这是“读到文件”和“模型知道文件内容”之间不可缺的桥。

若本步有普通工具结果，循环通常还欠一次后续模型判断；结果带 `isError` 也不自动消除这次判断。工具可以明确请求结束 Turn，另有输入也可能使循环继续，见 [`step()` 的返回分支](PIN/packages/core/agent-loop/src/agent.ts#L584-L609)与[结束前检查 395–400 行](PIN/packages/core/agent-loop/src/agent.ts#L395-L400)。不是每次工具之后都无条件再请求，也不是任何工具错误都立刻让整个 Turn 报错。

### 案例 A：用户已经附上 README 全文

用户消息是“概括下面的 README：……完整正文……”。Agent 入队并唤醒；Turn 打开，领取与接纳后打开 Step 1。循环准备适配器，记录被接纳的消息与必要请求信息，从会话派生历史，再请求模型。

模型直接返回摘要，流结算为 `assistant/message`，Step 1 关闭。没有工具调用且没有新的 next-step 输入时，循环经过 `agent/turn-stopping` 检查，再确认队列，最后写 `turn/end`。在这个稳定场景中结束原因为 `completed`。

相关测试是 [`loop.spec.ts` 的 455–489 行](PIN/packages/core/agent-loop/tests/loop.spec.ts#L455-L489)：它核对输入队列事实先于轮次内消息，边界顺序为 turn/start → step/start → step/end → turn/end，并核对派生的 system、user、assistant 消息。测试证明这个用例的行为，不代表模型摘要一定正确。

### 案例 B：用户只给出 README 文件名

Step 1 的请求只有任务与可用工具说明，没有本机文件的秘密访问通道。模型提议读取，助手消息先结算；循环分派调用，工具系统检查并执行允许的读取，将成功内容或错误作为 `tool/result` 记录。

Step 1 随后关闭。普通工具结果让循环继续到 Step 2；第二次模型请求包含工具结果，模型此时才有依据作摘要。它直接回答后，Step 2 关闭，经过停止检查再关闭 Turn。

官方[工具回读测试 491–525 行](PIN/packages/core/agent-loop/tests/loop.spec.ts#L491-L525)用 `echo` 代替真实文件读取，断言有两次模型请求，且第二次历史中有对应调用身份的工具结果。它验证的是反馈机制。本课的 README 场景与下方 `read_fixture` 都是**教学示例名称与资料**，不把它们冒充官方文件工具的名称、路径规则或安全保证。

第一段的输入是本次候选步骤的位置、领取目标和 signal；处理是等待准备结果并检查 reject；正常路径才会追加 Step 起点。输出不是“模型回答”，而是外层驱动该怎样推进；异常还可能进入轮次错误路径。

```typescript
const toolCalls = message.content.filter(block => block.type === 'tool-call')
if (toolCalls.length === 0) return { kind: 'completed' }
```

## 结束，不只有一种含义

**Event Log（事件日志）**用一句话说，就是“按顺序留下已经接受的事实，而不是只留最后一张状态照片”。像工作记录能区分“申请读取”“读取失败”“已告知用户”，最终都显示 idle 的界面则无法说明这些差别。

技术上，本版本的 Session 接受有类型、有连续序号的会话事件；消息历史与运行边界可以从相关事实派生。并不是所有实时事件都进入它，也不是每个日志条目都给模型看。事件日志提供重建依据，但它不是外部世界的全量录像，不自动证明业务成功。

最容易误判的几条路径在这里对照。每一行都要读结束原因和实际结果，不能只看最后回到 idle。

| 路径 | 本课应读出的区别 | 固定依据 |
| --- | --- | --- |
| 输入被拒绝 | 本例 Turn 是 blocked；零 Step、零模型请求、无接纳后的 user/message | [拒绝测试](PIN/packages/core/agent-loop/tests/interception.spec.ts#L253-L274) |
| 工具执行失败，产生错误结果 | `tool/result` 带 isError，可进入下一 Step，让模型如实说明失败；最后 completed 也不表示读到了文件 | [错误结果测试](PIN/packages/core/agent-loop/tests/coverage-edges.spec.ts#L227-L253)、[循环工具分支](PIN/packages/core/agent-loop/src/agent.ts#L586-L609) |
| 用户取消模型请求 | signal 被取消，Turn 原因 aborted；安全前缀可能以 interrupted 消息留下，没有可保留内容时可记 attempt | [流错误/取消处理](PIN/packages/core/agent-loop/src/agent.ts#L499-L539)、[取消测试](PIN/packages/core/agent-loop/tests/loop.spec.ts#L1403-L1427) |
| 模型错误或超时 | 可通过错误结束或失败流结算；是否重试取决于错误形态、策略和扩展点，不能说所有错误自动重试 | [attempt 与重试分支](PIN/packages/core/agent-loop/src/agent.ts#L541-L563)、[模型错误测试](PIN/packages/core/agent-loop/tests/loop.spec.ts#L1851-L1875) |
| 输出达到 max-tokens | 有独立结束原因；截断步骤不会继续分派其中工具调用，不能把截断答案算完整成功 | [max-tokens 分支](PIN/packages/core/agent-loop/src/agent.ts#L584-L587)、[截断测试](PIN/packages/core/agent-loop/tests/loop.spec.ts#L1520-L1549) |

工具失败还可能升级为批次调度异常，导致整个 Step、Turn 出错；上表第二行仅讨论已经正常产出错误结果的情况。轮次通过 catch/finally 记录错误与结束，见 [`turn()` 的 402–425 行](PIN/packages/core/agent-loop/src/agent.ts#L402-L425)。如果进程硬崩溃，或日志追加本身失败，不能保证所有结束事件都已写好。

取消也不是时间倒流。它表达“停止继续工作”的信号，能否及时结束依赖适配器与工具配合；已经发生的外部操作不会因此自动撤销。更完整的故障恢复留到 H20。

本版本仍是[未经安全审计的实验性开发者预览](PIN/SAFETY.zh.md#L5-L15)。本课解释真实机制，不把插件、审批或沙箱当成已经验证的生产级安全结论。
