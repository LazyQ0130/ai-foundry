## AI 已经会回答，为什么还要等？

3.1 的问答会先显示「正在等待…」，模型写完后，整段答案才突然出现。回答正确，等待时的体验却仍然迟钝。这一课让同一个知识工作台多一个**流式模式**：输入「用几句话解释 Git 为什么能帮助我安全试错。」，点击「开始生成」，先看到「正在连接模型…」，然后看着答案一段段长出来。你还可以在中途点「停止生成」。3.1 的普通模式与 3.2 的结构化资料建议继续保留。

```text
Git
Git 可以
Git 可以记录每次修改……
```

这不是打字机动画。每段文字要在服务端收到模型新内容后才进入页面。今天关注用户能观察到的变化与边界；无需先钻进 SSE 或 HTTP Chunk 的细节。

## 先用 Mock 把体验做出来

从你完成的 3.2 项目继续。让 AI 先检查已有问答、建议区、Provider、认证、同源保护与共享限流，以及你自己的页面调整。保持同一个问答输入框，增加「普通模式 / 流式模式」切换，不需要再堆一个几乎一样的输入区。先使用 `AI_PROVIDER_MODE=mock`；固定的四段短文字、每段约 800 毫秒，就足够让你看到状态变化，也不会消耗真实额度。

:::prompt{title="给现有问答加流式模式"}

```text
请先只读检查我已经完成的 3.2 知识工作台，保留普通 /api/ai/answer、结构化 /api/ai/suggest、严格 Zod 校验、Resource CRUD、认证和我自己的页面调整。只增量开发 3.3 流式问答：在原问答区加入普通/流式切换，新增 POST /api/ai/stream，沿用同源、Session、JSON、trim 后 1～2000 字符输入与共享的每用户限流。浏览器只提交 input，忽略其 model、apiKey、baseUrl、max_tokens、timeout、userId 和 provider。扩展现有 server-only lib/ai-provider.ts 的 stream()，复用它的 Key、base URL、模型、max_tokens=256、enable_thinking=false、20 秒超时和受控错误；不要复制第二套 Provider。真实请求使用 stream:true 与 stream_options.include_usage:true，正确解析任意切分的 Provider SSE、[DONE]、delta、usage、坏数据和中途关闭。Route 不透传原始 SSE，只向浏览器逐行发送 meta/delta/usage/done/error NDJSON；开始发送后发生错误，就用 error 事件。Mock 固定分成 3～5 段并稍作延迟。页面明确区分 idle、pending、streaming、completed、cancelled、failed；第一段前显示“正在连接模型”，第一段后才显示“正在生成”。停止按钮使用 AbortController，Route 将取消传到 Provider fetch，保留已收到的部分文字；generation id 阻止取消的旧请求晚到后写入新回答。先用 Mock 与本地 Stub 测试，再报告证据；不要改 3.2 建议，不做 Embedding、RAG 或数据库迁移，不操作 Git。
```

:::

启动项目并登录，切换流式模式，提问一次。页面应先显示「正在连接模型…」，第一段真正到达后才显示「正在生成…」，结束时显示「生成完成」。Mock 卡片要明写「Mock 模式 · 未调用真实模型」。普通模式仍一次返回完整回答；两种体验放在一起比较更容易看出差别。

:::check{title="先观察两种等待"}
- 普通模式等待后一次出现整段答案。
- 流式模式第一段到达前是 pending；之后文字逐段增长。
- 流式 Mock 不请求真实模型，重复运行有相同的四段内容。
:::

## 亲手停止一次

再次用 Mock 开始生成，在第二段出现时按「停止生成」。页面立即显示「已停止生成」，保留已经收到的部分文字，后续文字不再追加，也不能显示「生成完成」。取消是一种用户选择，不应变成红色失败提示。

接着迅速开始请求 B。请求 A 的某一段可能已经在网络路上，单靠 `busy=true` 守不住这种情况。给每次生成一个递增编号；每次写入页面前检查编号是否仍属于当前请求。A 被取消后，即使最后一段晚到，也必须忽略，B 只显示 B 的回答。

```text
A 开始 → A 收到一段 → 停止 A → B 开始
                             A 迟到：忽略    B 新段：显示
```

![请求 A 流式输出后被取消，请求 B 用新编号开始，A 的迟到片段被忽略](/course-media/stage-3/s3-3-01.webp "取消后旧请求不能污染新的流式回答")

:::concept{title="流式问答的六个界面状态"}

`idle` 是尚未开始；`pending` 是已请求但尚未收到正文；`streaming` 是正文正在增长；`completed` 是收到正常结束；`cancelled` 是用户停止；`failed` 是连接、Provider 或数据出了问题。取消与失败都可能发生在首段之前或之后。

:::

## 主动制造中途失败

:::deepdive{title="为什么 generation id 能阻止旧请求污染新请求？"}
每次开始生成都递增编号。收到文字时，先比较这段文字所属编号和当前编号；取消 A 后启动 B，即使 A 的网络响应迟到，编号已不同，页面会忽略它。AbortController 负责尽量停止网络工作，编号负责保护最后一次状态写入。
:::

用本地 Provider Stub 先送一段，再送一条坏事件或直接断开，不必反复花真实 token 制造故障。页面应显示「生成中断，以下是已经收到的部分内容」，并保留那一段；状态是 `failed`，绝不能伪装成 `completed`。如果在第一段之前收到 Provider 401 或 5xx，页面显示受控错误，不回显 Provider 原文或 Key。

登录、Origin、JSON、输入长度与限流都在开始流之前检查，所以仍用正常 HTTP 401、403、400、429 等状态。回答开始发送后，HTTP 状态不能再改；应用自己的流用 `error` 事件告诉页面后续失败。

## 再接真实模型

确认 Mock 和 Stub 通过后，在被 Git 忽略的本机 `.env` 配置你自己的北京地域百炼 Workspace；Key 只留在服务端，绝不贴到聊天、课程、代码或浏览器。用 `qwen3.7-flash` 提一个短问题，观察第一段延迟、收到的文本段数、总耗时和是否有 token usage。不要把完整回答写进验收日志。再发一条短请求，收到首段时停止，检查之后的页面新增段数为 0，并用本地 Stub 确认取消使 Provider 连接关闭。

当你只看页面时，整个数据流可以记成：

```text
百炼逐段返回
   ↓
服务端 Provider 解析
   ↓
你自己的 meta / delta / usage / done / error 事件
   ↓
浏览器逐行读取并更新当前这次回答
```

百炼怎样发流，与产品怎样告诉页面「有新文字、结束、出错」是两层事。未来换模型时，页面只需继续理解自己的事件。`usage` 若在流尾出现，就显示 total tokens；没有 usage 也允许正常完成。3.2 的 `summary / tags / confidence` 仍走普通 `generate()` 与严格 Schema；这节不处理流式 JSON。

:::stuck{title="一直停在正在连接，或者文字突然消失"}

先查 `/api/ai/stream` 的 HTTP 状态：401 看登录，403 看同源，400 看输入，429 等共享限流窗口。若是 200 但没有逐段显示，用本地 Stub 检查 Route 是否把每段立即写出、浏览器是否按行读取；不要假设一次 `reader.read()` 就是一条完整事件。中途断开时保留 partial text，并确认错误走 `error` 事件。取消后仍有文字，检查 AbortSignal 与 generation id 两条防线。

:::

## 验证并保存版本

跑 Provider parser、Route 和页面请求编号测试，再回归普通问答、结构化建议、资料 CRUD 和不同账号的数据隔离。自己按一次 Prompt Copy，核对粘贴内容完整；桌面和 390px 宽度各看一次，确保切换、状态与停止按钮仍可用。最后看 Git diff：只应有本课的课程与参考实现，不应出现 `.env`、Key、完整模型输出或构建缓存。确认数据库 schema、Starter 和其他 Stage 没变，再提交自己的版本。

完成本课后，你的 AI 问答不再只会等待整段答案；它能让用户看见生成进度、主动停止，并在失败或旧请求晚到时保持当前视图可信。下一课才会进入新的能力，本课停在流式体验。
