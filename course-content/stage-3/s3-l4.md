## AI 会回答了，但还没读过我的资料

3.1～3.3 的知识工作台已经能问答、输出结构化建议，还能逐段显示回答。可是你粘贴在自己资料区的内容，并不会自动成为模型能寻找的知识。今天只做一件事：把一篇你自己的非敏感文本变成能保存在数据库中的向量分块。

```text
一篇完整资料 → KnowledgeDocument → 多个 Chunk
                                      ↓
                               每块生成 Embedding
                                      ↓
                           PostgreSQL vector(1024)
```

完成时，你应该能在页面看到「已入库、3 个分块、text-embedding-v4、1024 维」，也能从数据库读到每块的 `vector_dims=1024`。先不做提问或检索。建议分两次完成：第一次准备数据库，第二次建立索引。

## 第一部分：从现有项目加上能存向量的数据库

从你完成的 3.3 项目继续。保留已有的 User、Session、Resource、A/B 页面差异、普通问答、结构化建议和流式问答。`Resource` 是原来的资料卡片，不要改名或改造成知识文档；新增 `KnowledgeDocument` 和 `KnowledgeChunk`。文档属于一个已登录用户，分块属于一篇文档，`position` 从 0 依序递增，同一篇文档内不能重复。

:::prompt{title="在现有项目中增量建立知识文档模型"}

```text
请先只读检查我完成的 Stage 3.3 项目、Prisma 6.19.3 schema、三次历史 migration 和当前 A/B 个性化页面。只增量做 3.4 的数据库准备：新增 KnowledgeDocument(id, ownerId 非空, title, content, status, createdAt, updatedAt) 与 KnowledgeChunk(id, documentId, position, content, embedding, embeddingModel, embeddingDimension, createdAt)，关系为 User → KnowledgeDocument → KnowledgeChunk；同一文档的 position 唯一。Prisma schema 中 embedding 使用 Unsupported("vector")?，正式 SQL migration 先 CREATE EXTENSION IF NOT EXISTS vector，再建真正的 vector(1024) 列。status 只允许 indexing/ready/failed。保留 Resource 和所有旧 migration，不用 db push 或 migrate reset，不加 HNSW/IVFFlat/ANN。请先在专用的全新本地测试库执行原三次 migration，放入一条非敏感旧 User/Resource 测试数据，确认 3.3 应用可启动；再增量 deploy 新 migration，检查旧数据仍在、extension 与 vector(1024) 存在。不要连接平台或生产数据库，不操作 Git；如果增量迁移失败，先停止并报告原因。
```

:::

先检查 `DATABASE_URL` 指向专用本地测试库，确认不是平台库、Stage 2 公开演示库或生产库。运行 `npx prisma migrate deploy` 和 `npx prisma migrate status`；新 migration 必须排在三次旧 migration 之后。验证旧 User、Session、Resource 表仍可用，旧测试数据没有消失。PostgreSQL 的 `vector` 扩展与 `vector(1024)` 是数据库事实，单看 Prisma schema 不能替代检查。

:::check{title="数据库准备停点"}
- 原有三次 migration 之后成功增量应用第 4 次 migration。
- `KnowledgeDocument.ownerId` 非空，`KnowledgeChunk.embedding` 的真实列类型为 `vector(1024)`。
- 旧 User / Resource 测试数据仍在，原工作台能启动。
:::

**到这里可以先休息。** 你已经准备了能保存向量的数据库，但还没有产生任何真实向量。第二次继续时，先确认你仍连接同一个隔离测试库。

## 第二部分：用 Mock 把一篇资料真正入库

页面加一个「我的向量资料」区域，只接收标题和粘贴的纯文本或 Markdown。标题 1～100 字符，正文 1～6000 字符，最多 8 个 Chunk。先用 `AI_PROVIDER_MODE=mock`。粘贴一篇带三个段落的非敏感笔记，例如分别谈 Git、PostgreSQL、浏览器状态；让它分成 2～3 块并保存。页面显示 `Mock 向量`，不要让人误以为已调用真实 Embedding。

切块规则保持简单：先按空行分段，尽量把短段合并到约 800 字符；单段过长再每 800 字符硬切；不加 overlap。相同输入每次得到相同分块。若超过 8 块，服务端直接拒绝，不能继续付费调用。Chunk 的 `position` 是稳定的 0、1、2……，以后才方便从结果回到原文。

:::prompt{title="让知识文档完成 Mock 向量入库"}

```text
请在现有 3.3 项目上增量完成 3.4 的 Mock 入库。保留普通问答 generate()、结构化建议、stream()、认证、Resource CRUD 与 A/B 差异。扩展同一个 server-only ai-provider.ts，新增 embed()，Mock 对相同文本返回相同的 1024 个有限 number；不要新建第二套 Provider。新增 GET/POST /api/knowledge/documents：POST 验证 Session、同源、JSON、标题 1～100、正文 1～6000、最多 8 块，只接收 title/content；ownerId 从 Session 得到，不接收客户端 ownerId、userId 或 embedding。先建 indexing 文档，事务外逐块 embed 并验证 Array、长度 1024、元素 finite；通过后用 Prisma tagged-template $executeRaw 与参数化 vectorLiteral 写入所有 Chunk，再用短事务把文档标成 ready。任何 Embedding 或写入失败要标 failed，不返回 Key、原始 Provider 响应或完整向量。GET 只列当前用户的安全元数据与短分块预览。页面区分 indexing、ready、failed 和 Mock 模式，不展示完整向量；不做检索、Top-K、RAG 或文件上传。先用测试证明切块确定性、维度拒绝、双账号隔离与失败状态，不操作 Git。
```

:::

这里的 Embedding 不是摘要。它把一段文本映射成一组可比较的数字；1024 是这组数字的维度。意思相近的文字通常在向量空间中方向更接近。现在只需要知道 PostgreSQL 的 pgvector 能保存这组数字，数学细节留到以后再用。

不要在数据库事务里等待外部 AI 服务：最多 8 次调用可能耗时数秒。先在事务外得到并检查所有向量，再用一个短事务写 Chunk、改 `ready`。如果调用或写入失败，保留文档的 `failed` 状态。文档行存在不等于索引完成。

:::check{title="Mock 索引停点"}
- 同一篇资料重复切块得到同样的内容与 position，超出 8 块时明确报错。
- 页面显示 Mock、分块数量与 1024 维；数据库里的文档状态为 ready。
- 换另一个账号登录，看不到这篇文档。
:::

## 从数据库确认，而不是只看页面

在**隔离测试库**执行只读查询，确认页面分块数与数据库一致；不要 `SELECT embedding`，那会打印 1024 个数字。

```sql
SELECT d."id", d."title", d."status", COUNT(c."id") AS chunk_count
FROM "KnowledgeDocument" d
LEFT JOIN "KnowledgeChunk" c ON c."documentId" = d."id"
GROUP BY d."id", d."title", d."status"
ORDER BY d."id" DESC;

SELECT "documentId", "position", "embeddingModel", "embeddingDimension",
       vector_dims("embedding") AS actual_dimension
FROM "KnowledgeChunk"
ORDER BY "documentId", "position";
```

每个 ready 文档应有对应数量的 Chunk；每个实际维度应是 1024。再用本地 Provider Stub 分别制造配置缺失、401、5xx、超时、3 维向量与数据库写入错误，确认文档都不是 ready，页面只出现脱敏错误。真实云服务不适合反复用来制造坏结果。

:::stuck{title="页面有文档，却没有分块或显示 failed"}

先看文档 status，再看服务端受控错误类别。检查 `AI_PROVIDER_MODE`、独立的 `AI_EMBEDDING_*` 配置、Chunk 上限和数据库 migration；不要把 Provider 原始响应或 Key 贴给 AI。若状态是 `failed`，数据库中不应出现部分成功却显示 ready 的记录。不要通过补 0、截断或改列维度来掩盖错误向量。

:::

## 最后用一次真实 Embedding 验收

确认 Mock 流程、数据库检查和 Stub 失败路径都通过，再在**本机被 Git 忽略的服务端 `.env`** 中使用自己的北京地域百炼 Workspace 配置 `AI_EMBEDDING_BASE_URL`、`AI_EMBEDDING_API_KEY`、`AI_EMBEDDING_MODEL=text-embedding-v4`、`AI_EMBEDDING_DIMENSION=1024`，把 `AI_PROVIDER_MODE` 设为 `real`。Chat 的 `AI_CHAT_*` 保持独立。Key 不要粘贴进聊天、课程、网页或 Git；不要用 `NEXT_PUBLIC_` 前缀。

先提交一条短文本，确认 HTTP 成功、`kind: real`、向量长 1024 且全是有限 number，记录耗时和 usage（若有）。再提交一篇约 2～3 块的非敏感短文，确认页面 `ready`、模型 `text-embedding-v4`、分块数和数据库中每行 `vector_dims=1024`。只记这些摘要，不保存原文、完整向量或 Provider 原始响应。若当前账号或地域无法使用该模型，记下真实错误并停在 Mock 成果，不要悄悄改用别的模型。

最后重跑普通问答、结构化建议、流式取消和 Resource CRUD；用 Alice 建文档、Bob 登录读列表验证隔离。亲自点击一次课程 Prompt 的 Copy，检查粘贴内容完整；在桌面与 390px 宽度查看表单、状态和分块预览。检查 `git diff`、migration 历史、被忽略的 `.env`，确认没有 Key、完整向量、测试资料或构建缓存，再保存一个可恢复的 Git 版本。
