## AI 回一句话还不够

3.1 中，你的知识工作台已经能安全地请真实模型回答问题。普通文字适合读，但如果产品想把回答拆成「摘要」「标签」「置信度」，就需要知道每一部分是什么。今天仍在同一个项目里增加「AI 资料分析」：输入一段资料，点击「生成结构化建议」，页面直接展示这三项。先看结果，再动手；暂时不用面对原始 JSON。

本课最重要的一句话是：**模型输出属于不可信外部输入。** 即使文字看起来很像正确答案，也不能跳过服务端检查，更不能直接写进资料库。

## 先看我们想得到什么

用这段非敏感资料作为练习：`Git 是一个分布式版本控制系统，可以记录代码历史，并帮助开发者恢复到之前的版本。` 期待页面出现一段简短摘要、1～5 个标签、0～1 之间的置信度。页面必须清楚写着：「AI 建议仅供预览，不会自动修改你的资料。」原有问答区、登录、Resource CRUD、搜索与各自做过的页面调整仍然可用。

<!-- 配图建议：同一知识工作台中的结构化建议卡片，摘要、标签、置信度分区展示，并标出“仅供预览”。 -->

:::concept{title="两道检查"}

`JSON.parse` 只回答“这段文字能不能读成 JSON”；严格 Schema 再回答“对象是不是恰好有 summary、tags、confidence，且每个值都合规”。两道都通过，服务端才向页面返回 suggestion。

:::

## 在 3.1 项目里加建议区

让 AI 先读当前项目，而不是复制一套新 Provider。建议独立使用 `POST /api/ai/suggest`，保留已有 `POST /api/ai/answer`；两个 Route 共用原来的登录、同源保护、用户级限流、Provider 配置、超时和错误映射。给现有 `generate()` 增加最小 structured 选项；服务端保存分析任务 Prompt，页面只提交 `content`。

:::prompt{title="在原工作台新增结构化建议"}

```text
先只读检查我完成的 3.1 知识工作台、lib/ai-provider.ts、登录与同源写保护、共享限流，以及现有 A/B 或我自己的页面变化。然后增量加入 AI 资料分析：输入资料内容，点击“生成结构化建议”，显示摘要、1～5 个标签、0～1 置信度，并明确写“AI 建议仅供预览，不会自动修改你的资料”。新增 POST /api/ai/suggest，只接受 content 字符串，trim 后非空且最多 3000 字符；登录、同源、约 5 次/分钟限流仍在服务端执行，并与 /api/ai/answer 共用同一个用户限流 Map。不要接受浏览器传来的 model、schema、system prompt、Key、baseUrl、max_tokens、userId 或 ownerId。只扩展现有 Provider generate()，复用同一 fetch、配置、20 秒默认超时、max_tokens=256、错误处理；structured 模式请求 response_format: {type:"json_object"}，服务端 Prompt 明确要求只输出 JSON object。加入 Zod 4.6.5：严格校验 summary 为 trim 后 1～500 字符，tags 为 1～5 个 trim 后 1～32 字符字符串，confidence 为 0～1 的 number，拒绝额外字段。真实和确定性 Mock 都经过 JSON.parse 与 Zod，只有通过后才向页面返回 suggestion；失败只返回受控错误。保留原有问答、资料 CRUD 和个性化页面。绝不根据 AI 建议新增或 PATCH Resource，不实现 Streaming、Embedding 或 RAG。先测试 Mock、坏输出和原有功能，报告实际证据；不要操作 Git。
```

:::

Schema 是服务端接受数据前的一张结构检查表。本课只需用到 `z.strictObject`、字符串/数组/数字约束和 `safeParse`。3.1 的 Provider 仍是唯一的 Provider；不要再建一份取 Key、发请求或处理超时的代码。

## JSON 为什么还不能直接相信

真实模型返回的是文字。服务端先对它执行 `JSON.parse`，再用严格 Schema 验证：`summary` 去掉首尾空格后仍有内容且最多 500 字符；`tags` 是 1～5 项数组，每项是去空格后 1～32 字符的文字；`confidence` 是 0～1 的数字；对象没有第四个字段。`"0.9"` 是字符串，不是数字，不能偷偷转换。只有通过后的值才组成成功响应。

```text
Model → JSON text → JSON.parse → strict Zod Schema → 合法 suggestion → 页面 Preview
                         失败 ↘          失败 ↘       受控错误
```

`response_format: {"type":"json_object"}` 可以帮助模型输出 JSON，但它不替你检查字段。百炼的 [OpenAI-compatible 文档](https://help.aliyun.com/zh/model-studio/qwen-api-via-openai-chat-completions)也要求在使用该格式时，Prompt 明确说要输出 JSON。这里由服务端写 Prompt，不要求你把模型规则或自己的 Key 复制到浏览器。

## 主动制造几个坏结果

在本地测试或受控 Provider Stub 中，依次给 validator 这些结果：`{ summary:`、缺少 `confidence`、`tags` 是字符串、`confidence` 是 `"0.9"` 或 `2`、以及多了 `extra` 字段。它们都应失败；合法的 `{"summary":"测试","tags":["Git"],"confidence":0.9}` 应通过。返回 Markdown 代码围栏也应失败。不要为了演示错误反复请求真实模型。

:::stuck{title="看见 JSON，却没有建议卡片"}

先看 `/api/ai/suggest` 的 HTTP 状态，再区分 JSON 语法与 Schema：语法错误查是否有围栏或额外说明；Schema 错误按 summary、tags、confidence 的类型、范围、缺失与多余字段逐项核对。页面只显示受控错误，不回显完整模型原文。若是 401 查登录，403 查 Origin，429 等限流窗口过去；不要删掉验证来让卡片出现。

:::

## 只做一次真实结构化调用

用 3.1 已安全配置的**自己**北京地域 Workspace，把 `AI_PROVIDER_MODE` 切到 `real` 并重启服务。课程 baseline 继续是 `qwen3.7-flash`、`AI_TIMEOUT_MS=20000`、`AI_CHAT_DISABLE_THINKING=1`，真实 Key 仍只在被 Git 忽略的服务端环境文件。输入前面的 Git 短文本，只调用一次。Network 里目标应是自己的 `/api/ai/suggest`、HTTP 200、`kind: real`；页面显示三个字段，usage 若返回则显示用量。HTTP 200 之前，模型文本必须已通过 JSON.parse 和严格 Zod 校验；不要用页面出现“看起来像 JSON”的字来代替证据。

## 检查数据库没有被建议改写

在建议前后分别读取当前账号的 Resource 列表，比对条数与原有记录内容；Network 中不应因点击「生成结构化建议」出现 `POST /api/resources` 或 `PATCH /api/resources/[id]`。本课的 suggest Route 不调用 Prisma 写入。**“AI 说得像真的”和“产品允许写进数据库”是两件事。** 即使建议很好，也只能先预览；本课不做自动保存按钮。

## 解释改动并保存版本

请 AI 只读指出原 Provider 的 structured 选项、Zod Schema、suggest Route、页面建议卡片在哪里；说明为什么页面只收到通过验证的 suggestion，以及为什么没有 Resource 写入。自己复查 `git diff` 与 `git status`，确认 `.env`、Key、原始模型文本、日志和构建缓存不会提交，再运行构建与测试并保存可恢复版本。3.1 的问答链路和你的页面个性化结果仍应存在。
