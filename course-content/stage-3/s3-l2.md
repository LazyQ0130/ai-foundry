## AI 回一句话还不够

3.1 中，你的知识工作台已经能安全地请真实模型回答问题。普通文字适合读，但如果产品想把回答拆成「摘要」「标签」「置信度」，就需要知道每一部分是什么。今天仍在同一个项目里增加「AI 资料分析」：输入一段资料，点击「生成结构化建议」，页面直接展示这三项。先看结果，再动手；暂时不用面对原始 JSON。

本课最重要的一句话是：**模型输出属于不可信外部输入。** 即使文字看起来很像正确答案，也不能跳过服务端检查，更不能直接写进资料库。

## 先看我们想得到什么

用这段非敏感资料作为练习：`Git 是一个分布式版本控制系统，可以记录代码历史，并帮助开发者恢复到之前的版本。` 期待页面出现一段简短摘要、1～5 个标签、0～1 之间的置信度。页面必须清楚写着：「AI 建议仅供预览，不会自动修改你的资料。」原有问答区、登录、Resource CRUD、搜索与各自做过的页面调整仍然可用。

**结构化建议**就是让回答分别放进指定格子：summary 放摘要，tags 放标签列表，confidence 放置信度数字。这样页面知道哪里放哪项，不必从一大段话里猜。这里的 confidence 是模型自己填的数字，**0.9 不等于已经测得“90% 正确”**；通过范围检查也不能证明内容可靠。

:::concept{title="两道检查"}

先检查文字格式能不能读懂，这一步叫 `JSON.parse`；再按一张明确的规则表检查字段，这张表叫 **Schema**，本课由 **Zod 这个现成的校验库**执行。“库”就是安装到项目里、供程序调用的一包现成功能，不是另一个需要打开的软件。AI 会安装和接入，你先看懂它检查什么：例如模型返回的 tags 是一句话，但规定它必须是列表，就要拒绝；confidence 是数字 2，也超出 0～1 的范围。

**strict（严格）**还要求没有约定以外的字段，不能把模型偷偷增加的内容一并接受。两道检查通过，才向页面返回 suggestion。这里的 Schema 是回答格式的检查规则；2.3 的 schema.prisma 描述数据库表结构。请按上下文理解同一个名称。

想一想：回答是合法 JSON，字段也都合格，却说“Git 是数据库”，应当怎样判断？格式检查可能通过，内容仍是错的，不能据此自动保存。后面读原文和评估时继续检查内容。

:::

## JSON 为什么还不能直接相信

真实模型返回的是文字。服务端先对它执行 `JSON.parse`，再用严格 Schema 验证：`summary` 去掉首尾空格后仍有内容且最多 200 字符；`tags` 是 1～5 项数组，每项是去空格后 1～32 字符的文字；`confidence` 是 0～1 的数字；对象没有第四个字段。`"0.9"` 是字符串，不是数字，不能偷偷转换。只有通过后的值才组成成功响应。

```text
Model → JSON text → JSON.parse → strict Zod Schema → 合法 suggestion → 页面 Preview
                         失败 ↘          失败 ↘       受控错误
```

`response_format: {"type":"json_object"}` 可以帮助模型输出 JSON，但它不替你检查字段。百炼的 [OpenAI-compatible 文档](https://help.aliyun.com/zh/model-studio/qwen-api-via-openai-chat-completions)也要求在使用该格式时，Prompt 明确说要输出 JSON。这里由服务端写 Prompt，不要求你把模型规则或自己的 Key 复制到浏览器。
