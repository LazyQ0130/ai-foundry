## 模型说「来源是它」，你为什么敢信？

先打开完成 3.5 的工作台，用自己的测试账号做一次旧操作：

1. 确认自己的 Git 学习资料已入库，模式与资料向量一致。在提问区输入「什么工具可以帮助我保存代码版本？」。
2. 点击已有的「先看检索命中」，找到「本次检索命中」里的文档标题和片段。这个按钮只查资料，不调用 Chat；实际命中以你这次请求为准。
3. 记下一条候选资料的标题，想一想：看到它出现在候选区，能证明最终答案用了它吗？**还不能。** 这一节要补的就是从回答回到真实资料的入口。

现在只记住两件事：**搜到的片段是候选；回答引用的片段还要逐个核对。** 即使模型自己写出「来源：Git 学习笔记」，那也只是模型生成的文字，标题可能写错，文档也可能不存在。

本课继续升级同一个知识工作台。3.1 普通回答、3.2 结构化建议、3.3 流式取消、3.4 入库、3.5 检索停点都保留。开发完成后，回答下方会多出真实来源卡片；点出每张卡片对应哪篇文档、哪个片段，再判断它能否支持这句话。**先完成下面的开发，旧版页面此刻还没有这个来源区。**

:::concept{title="先分清页面上的两个区域"}

| 页面区域 | 它证明了什么 | 还不能证明什么 |
| --- | --- | --- |
| 本次检索命中 | 服务端这次找到了哪些候选片段 | 模型最后一定使用了它们 |
| 回答实际引用 | 模型选择的编号确实属于本次候选，卡片来自真实片段 | 片段足以支持回答里的每一句话 |

本课负责核对来源身份；回答是否被资料支持，仍要亲自读。3.7 会把这一步纳入评估。

:::

### 给每个片段编号，再核对回答选了谁

可以先把处理过程读成：找自己的资料 → 给每个候选片段编号 → 模型选择编号 → 服务端核对编号 → 显示真实来源卡片。这次不改数据库，也不存储回答或引用。已有的真实片段 ID、文档标题、片段位置和内容已经足够。

:::deepdive{title="给 AI 的技术备注：引用链路与代码名称"}
下面是实现约定，可随参考 Prompt 照抄给 AI，不要求先背代码名称。核对时仍要按上面的两个区域、下文的非法 ID 实验和账号隔离要求实际验收。

`/api/knowledge/ask` 改为：

```text
当前用户的 Top-3 Chunk → 服务端 sourceId → 带 ID 的 Context
→ 结构化模型结果 → JSON.parse → Zod strict
→ 检查 ID 属于本次 Top-3 → 服务端映射来源卡片
```

Retrieved Match 是 Retriever 给模型看的候选 Chunk；Verified Citation 是模型选出的 sourceId 经格式和本次候选集合检查后，由服务端映射回真实 Chunk 的来源卡片。后者仍需人工判断是否足以支持答案。
:::

## 先给真正的 Chunk 一个 sourceId

本课先用 Mock 开发：上一课若以 real 收尾，先按[模式切换步骤](/environment#stage3)改回 mock 并重启，复用当前账号的 Mock 文档；原云库和四次迁移不变。

片段在数据库里已有一个真实编号，例如 123。服务端据此生成 `SRC-CHUNK-123`；这个来源编号叫 **sourceId**。同一片段下次即使排名变化，编号仍相同。`资料 1` 只是一次检索的名次，不能作为正式 ID。ID 不含 ownerId、Key 或其他秘密，也不接受浏览器指定。

从本课开始，`/retrieve` 和 `/ask` 返回的候选列表 `matches` 都带这个编号，最终引用 `sources` 也带同一个编号。下一课的检查工具才能逐个核对“引用确实来自这次候选”。只看标题和预览不够：两个不同片段可能恰好有相同文字。编号相符仍只证明来源在候选中，不能证明回答内容正确。

本次候选仍沿用 3.5 的限制：只有当前账号、已入库、同一个 Embedding 模型和维度的片段能进入。模型只能从**这次**的候选里选编号，不能选完再去全库找；否则可能把本次没搜到的内容，甚至别人的私有资料带进来。

先补需求，再让 AI 开发。必要约定：sourceId 只能由本次 Retrieved Set 分配；模型引用必须经过严格 Schema 与集合成员校验。

:::deepdive{title="给 AI 的技术备注：来源编号的范围"}
字段与类型名可照抄；你要用两次请求和两个账号核对编号与归属。

对每个 `RetrievedChunk` 使用真实数据库 `chunkId`，只把本次经过 SQL ownerId、ready、Embedding 模型和维度过滤的结果映射为 `CitableChunk`。使用现有 /api/knowledge/ask，不另开接口；sourceId 为真实 Chunk 的 SRC-CHUNK-<id>。answered 引用必须属于本次 Retrieved Set；无资料返回 insufficient，不补造来源。

## 让模型只能从这些 ID 里选

模型只返回一个 JSON object。资料足够时：

```json
{"status":"answered","answer":"Git 可以保存代码版本。","sourceIds":["SRC-CHUNK-123"]}
```

资料不足时：

```json
{"status":"insufficient","answer":"当前资料中没有足够依据。","sourceIds":[]}
```

复用同一个 Provider `generate()`，给它 `structured: true` 和服务端固定的 system instruction。Mock 可用本次 Top-1 的真实 sourceId 生成固定 JSON，但必须和真实结果走同一套验证。不要再写第二套 Chat fetch。

## JSON 合法，引用仍可能是假的

先用本地测试替身（Stub）做一个反例：让它返回 `SRC-CHUNK-999999`。这串编号写法正确，却不是本次找到的片段。接口必须拒绝，页面不能给它画一张来源卡片；恢复合法编号后，真实卡片又应出现。检查“写法正确”和检查“确实属于本次候选”是两件事。

:::task{title="主动测试假 sourceId"}

不用自己寻找云端坏答案。沿用 3.2 的本机 Stub 约定，让 AI 把这条实验以及下文的重复／非本次／Bob 来源等断言加入实际 Citation 处理链的 `npm test`，数据库隔离项加入 3.4 的 `npm run test:db`。测试应先喂合法 ID 证明成功，再喂假 ID 证明整次拒绝，最后恢复合法 ID 重新成功；只在测试进程改变 Stub，不改产品成员校验或 `.env`。运行两条命令时逐项看案例名、失败数 0 和退出 0；原页面合法来源仍可显示，才算恢复。未完成测试脚本就先补开发，未运行写未验证，不让 AI 回答“已经拒绝”代替实际证据。
:::

按三步检查，不要一次记住一串库名：

1. **回答格式合规。** `answered` 是“按资料回答”的结果类型：答案非空、最多 300 字符，来源 1～3 个；它仍需人工核对是否真的被资料支持。`insufficient` 表示资料不足：答案非空、最多 120 字符，来源必须为空。两种情况都拒绝额外字段、重复来源、代码围栏和无法解析的 JSON。
2. **每个来源都在本次候选里。** 有一个未知编号，就拒绝整次结果，不能悄悄删掉它后继续展示。即使编号确实存在于数据库，只要不在这次 Top-3，也必须拒绝。
3. **卡片信息由服务端取。** 标题、位置和预览从已核对的真实片段里读取，不能直接使用模型编的文字。

:::deepdive{title="给 AI 的技术备注：两道校验怎样实现"}
具体写法可照抄；上面的长度、数量、拒绝条件和三步观察都要保留。先 `JSON.parse`，再用 strict Schema 区分 `answered` 与 `insufficient`；随后建立 `Map<sourceId, CitableChunk>`，逐个检查模型 ID 的集合成员资格。格式校验用 Zod，成员校验用本次 Map，二者不能互相替代，也不能根据模型 ID 再查询任意 Chunk。
:::

## 页面展示真正的来源
