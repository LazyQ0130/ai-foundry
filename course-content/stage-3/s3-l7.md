## 能回答，不代表它已经好用

3.6 的回答带着真正来自本次检索的来源卡片。你问「什么工具保存代码版本？」，看到 Git 和一段顺畅答案。这是一次成功调用，但只问一题，无法知道它是否只是碰巧答对。来源 ID 属于本次 Top-3，也不证明回答的每一句都由那块资料支持；Top-1 similarity 更不是正确概率。

这节课不改用户产品，不加公开的「评估全部资料」按钮。开发者在本机用一组固定题目，重复调用已经存在的 `/api/knowledge/ask`。结果分开看：该找的文档进 Top-K 没有、该回答或拒答是否照做、引用是否指向预期文档、耗时和 Token 如何变化。最后再亲自读回答与来源，判断具体结论有没有依据。

```text
固定非敏感知识包 → 固定 Eval Set → 顺序调用真实产品 API
→ 确定性指标 + 本地详细报告 → 人工 Citation Support 复核
```

## 先固定这一轮要比较的问题

**Evaluation（评估）**在这里就是“用事先准备的一组题，重复检查自己的产品”。这组题叫 Eval Set；负责登录、逐题调用产品 API 并记录结果的程序叫 Runner。它只是替你按同样步骤做检查，不能自己知道一句话是否有事实依据，所以还要人工阅读。

“固定”指比较不同运行结果时，资料、题目与预期先保持一致；真正发现题目写错可以修，但要记录新版本、重新建立比较起点，不能在一轮中途改题来掩盖失败。

参考实现用三篇短资料：Git 学习笔记、PostgreSQL 学习笔记、Cookie / Session 学习笔记。只写清楚可验证的事实，不用私人笔记。12 道题里，8 道有答案：覆盖直接问法、换表达、同一文档的不同事实以及跨文档易混淆的概念；4 道应拒答，其中两道接近 Git、数据库和 Cookie 的话题，却没有被资料说明。每题固定 `id`、`question`、`expectedStatus` 和 `expectedDocumentTitles`。不要看到第一轮结果后悄悄改题目来追求全绿。

```json
{"id":"git-01","question":"什么工具可以帮助我保存代码版本？","expectedStatus":"answered","expectedDocumentTitles":["Git 学习笔记"]}
```

无答案题的 `expectedStatus` 是 `insufficient`，预期标题数组为空。自己的知识库可以换成自己的题集，但先用课程的小型知识包跑通流程。题目必须与**实际入库版本**对应，不能评估时临时换资料。

先补需求，再让 AI 开发。必要约定：固定资料、固定题集和顺序执行使结果可比较；人工复核完整回答与实际引用，uncertain 不算成功。

## 先用 Mock 把工具跑通

**Mock 只能检查流程，不能证明回答质量。** 本课内部参考实现把文字变成一组可重复的模拟数字，没有模拟“意思相近就靠近”；只要有候选，回答就固定引用排第一的片段，显示同一句示例，也不会判断资料够不够回答。因此引用未命中、应拒答却回答，可能来自这份模拟实现的能力限制，仍须如实记为失败。不要为这 12 道题增加关键词特判。你让 AI 写的 Mock 若不同，也先读清它实际模拟了什么。

例如知识包只有三篇且各一个片段，Top-3 会把三个都取出：即使检索命中 8/8，也不能证明排序正确。能逐题记录、保留错误和写出报告，说明工具流程跑通；真实回答、拒答与来源支持要求还要用真实模式和人工复核完成。

在开发或执行下面的 Runner 之前，先在 A 把 `.env` 的 `AI_PROVIDER_MODE` 改回 `mock`，Ctrl+C 停旧服务、在原根目录重新 `npm run dev`，等 Ready、核对模式；3.6 的 real 不会自动切回。保留原云库与模型配置，后面的账号／知识包步骤也先按 Mock 做。

Runner 用本机配置 `EVAL_BASE_URL`、`EVAL_USERNAME`、`EVAL_PASSWORD` 登录隔离测试账号，拿到 Session Cookie 后，逐题 POST 到现有 `/api/knowledge/ask`；`EVAL_MODE` 指定本轮是 mock 还是 real。Key、密码和 Cookie 不进题集、课程或 Git。真实模式另需显式 `EVAL_REAL_CONFIRM=YES`；Mock 不需要。Runner 不重写 Embedding、SQL、Prompt 或 Provider，也不自动重建知识包。

## 哪些结果机器可以确定？

对 8 道可答题，`retrievalHit` 看预期文档是否至少有一篇进入 Top-K。它测的是**检索命中**，不是回答正确率。`statusMatch` 看可答题是否 `answered`、无答案题是否 `insufficient`；分别报告有答案回答数和无答案拒答数。`expectedCitationHit` 看最终验证过的 `sources` 是否包含预期文档。3.6 已保证引用来自本次检索，Runner 可以记录 `verifiedSources`，但不能把它叫作「引用正确率」。

可答题已经回答，却没引用预期文档时，报告应明确显示 `expected_citation_miss`（预期引用未命中）。这是工具能确定的一项问题；回答究竟有没有事实依据，仍要你读原文判断。`automaticChecksPassed:false` 表示存在自动检查问题；命令正常结束只表示这一轮已收集完整。即使为 true，也不能替代后面的人工复核。

以一道 Git 题为例，分开问三次：该找的 Git 笔记进候选了吗？产品应答还是应说资料不足？最后选的来源来自预期笔记吗？然后你还要读回答与片段，判断它是否真的有依据。找到笔记、选对来源、写对答案是不同结果，不能只看其中一个。

数字里的分母也要看清：`7/8` 表示这 8 道可答题中有 7 道满足当前这项检查；`4/4` 可以是 4 道应拒答题全都拒答。它们在检查不同事情，不能直接合成一个“产品可靠率”。

不要把这些合成一个「AI 质量 86 分」。分别看 `7/8`、`4/4` 之类的分子和分母。每题记录 embedding、retrieval、chat、total 耗时，摘要至少给总耗时中位数和最大值；只报平均数会藏起慢请求。汇总 Embedding 和 Chat tokens；某次 Provider 没给 usage 就保留 `null`，不要补零冒充精确值。模型价格会变化，人民币成本应按运行当天 Provider 官方单价计算：输入 Token × 当日输入单价 + 输出 Token × 当日输出单价 + Embedding Token × 当日单价。当前接口若没有精确拆分计费字段，就不要编造金额。

**中位数**是把耗时从小到大排好后位于中间的值。假设五次分别用 1、1、1、1、10 秒：中位数是 1，最大值是 10，平均值是 2.8；只看平均值看不清那次等待 10 秒的情况。这里的 `null` 表示没有取得用量值，数字 0 表示实际用量是零，两者不能混写。

汇总也遵守同一规则：12 题都没给用量，总计写 `null`；只有部分给了，就只相加已知值，同时列出缺测题数。这种部分总计不能拿来当整轮成本。Mock 没有真实模型调用，不意味着它返回了“实测 0 Token”。

## 哪些必须人工看？

打开本机 review 文件，逐条对照**完整回答**与**实际引用 preview**。对每条 `answered` 勾选 `supported`、`unsupported` 或 `uncertain`，记下判断理由。`uncertain` 不能自动算成功。不要让已配置的 Chat 模型再给自己的答案打分；这课由人复核。最后单独统计三类数量，不合入自动指标。

`supported` 是“资料确实支持”，`unsupported` 是“资料支持不了这句话”，`uncertain` 是“目前无法确认”。例如原文只说 Git 记录代码历史，回答却说它会自动恢复被删的数据库，来源即使真存在，也支持不了这个结论。预览看不够时回到自己的对应原文；仍无法确定就记 uncertain，不因为有来源标题而勾支持。

对错误要找原因。预期文档没进 Top-K 是 `retrieval_miss`；有资料却拒答是 `wrong_refusal`；没资料却回答是 `missing_refusal`；来源和检索都看似合理但回答越界是 `unsupported_generation`；引用是真实 Chunk 却无法支持核心结论是 `citation_support_problem`；超时、5xx 或结构失败是 `provider_failure`。后两类常需要人工判断，程序不能假装已经知道事实是否被支持。

## 跑第一轮真实 Evaluation
