## 能回答，不代表它已经好用

3.6 的回答带着真正来自本次检索的来源卡片。你问「什么工具保存代码版本？」，看到 Git 和一段顺畅答案。这是一次成功调用，但只问一题，无法知道它是否只是碰巧答对。来源 ID 属于本次 Top-3，也不证明回答的每一句都由那块资料支持；Top-1 similarity 更不是正确概率。

这节课不改用户产品，不加公开的「评估全部资料」按钮。开发者在本机用一组固定题目，重复调用已经存在的 `/api/knowledge/ask`。结果分开看：该找的文档进 Top-K 没有、该回答或拒答是否照做、引用是否指向预期文档、耗时和 Token 如何变化。最后再亲自读回答与来源，判断具体结论有没有依据。

```text
固定非敏感知识包 → 固定 Eval Set → 顺序调用真实产品 API
→ 确定性指标 + 本地详细报告 → 人工 Citation Support 复核
```

## 先写一组永远不变的问题

参考实现用三篇短资料：Git 学习笔记、PostgreSQL 学习笔记、Cookie / Session 学习笔记。只写清楚可验证的事实，不用私人笔记。12 道题里，8 道有答案：覆盖直接问法、换表达、同一文档的不同事实以及跨文档易混淆的概念；4 道应拒答，其中两道接近 Git、数据库和 Cookie 的话题，却没有被资料说明。每题固定 `id`、`question`、`expectedStatus` 和 `expectedDocumentTitles`。不要看到第一轮结果后悄悄改题目来追求全绿。

```json
{"id":"git-01","question":"什么工具可以帮助我保存代码版本？","expectedStatus":"answered","expectedDocumentTitles":["Git 学习笔记"]}
```

无答案题的 `expectedStatus` 是 `insufficient`，预期标题数组为空。自己的知识库可以换成自己的题集，但先用课程的小型知识包跑通流程。题目必须与**实际入库版本**对应，不能评估时临时换资料。

:::prompt{title="建立固定知识包和 12 道 Eval Set"}

```text
请继续我完成的 Stage 3.6 项目，不改变用户产品、Prisma schema 或四次 migration。新增 eval/knowledge-pack.json，使用 Git、PostgreSQL、Cookie/Session 的三篇短非敏感资料，每个事实明确可核对。新增 eval/rag-cases.json：12 条固定题，8 条可答、4 条无答案；有答案题覆盖不同表达、同文档不同事实和易混淆概念；无答案题至少两条与资料领域接近，但资料确实没有答案。每项只含 id、question、expectedStatus、expectedDocumentTitles，不放密码或 Cookie。加输入校验：10～20 题、ID 唯一、两种状态都有、可答题至少一个预期标题、无答案题标题为空。不要通过数据库表存 Eval Set，不操作 Git。
```

## 先用 Mock 把工具跑通

Runner 用本机环境变量 `EVAL_BASE_URL`、`EVAL_USERNAME`、`EVAL_PASSWORD` 登录隔离测试账号，拿到 Session Cookie 后，逐题 POST 到现有 `/api/knowledge/ask`。Key、密码和 Cookie 不进题集、课程或 Git。真实模式另需显式 `EVAL_REAL_CONFIRM=YES`；Mock 不需要。Runner 不重写 Embedding、SQL、Prompt 或 Provider，也不自动重建知识包。

:::stuck{title="评估连续出现 429 或 502"}
若刚入库就开始评估，三次 Embedding 可能已占用同一用户的限流额度；先等窗口结束，再顺序运行。502 要区分结构错误、引用错误和输出长度上限，查看受控错误类别与本地报告，不要记录完整 Provider 响应，也不要通过取消限流或关闭 Schema 检查追求全绿。
:::

现有 AI 接口约每用户每分钟 5 次，入库时生成 Embedding 也占用这份额度。**知识包入库后先等至少 60 秒**，再开始评估。12 题必须顺序运行，题间留足时间，不能临时把正式限流改成 1000 次。429、502、504 或网络失败记为 `provider_failure`，继续下一题，**不自动重试**。跑完在本机 `.runtime/stage3-eval-report.json` 写详细结果，在 `.runtime/stage3-eval-review.md` 写人工复核表；两者都被 Git 忽略。终端只打印计数和摘要，不打印完整回答、密码或 Session Cookie。

:::prompt{title="通过真实产品 API 顺序运行评估"}

```text
新增 scripts/rag-eval.mjs，只读取固定 Eval Set 和本机环境变量 EVAL_BASE_URL、EVAL_USERNAME、EVAL_PASSWORD；仅允许本地测试 URL。真实模式必须显式 EVAL_REAL_CONFIRM=YES，否则拒绝运行。先登录并在内存中保留 Session Cookie，然后顺序调用已有 POST /api/knowledge/ask，题间至少等待 13 秒以尊重 5 次/分钟限流。每题只调用一次；429、502、504、网络失败都记录 provider_failure，不自动重试。每题记录预期和实际状态、检索标题、经验证来源标题、各段 latency、usage、错误分类；详细 answer、source preview 和检索 preview 只写到被 Git 忽略的 .runtime/stage3-eval-report.json 与人工 review Markdown。终端只打印安全摘要，不打印密码、Cookie、Key、完整回答、Prompt 或向量。先用 Mock 完整运行 12 题，验证报告写入和分类，不把 Mock 的质量数字当真实表现。不要操作 Git。
```

## 哪些结果机器可以确定？

对 8 道可答题，`retrievalHit` 看预期文档是否至少有一篇进入 Top-K。它测的是**检索命中**，不是回答正确率。`statusMatch` 看可答题是否 `answered`、无答案题是否 `insufficient`；分别报告有答案回答数和无答案拒答数。`expectedCitationHit` 看最终验证过的 `sources` 是否包含预期文档。3.6 已保证引用来自本次检索，Runner 可以记录 `verifiedSources`，但不能把它叫作「引用正确率」。

不要把这些合成一个「AI 质量 86 分」。分别看 `7/8`、`4/4` 之类的分子和分母。每题记录 embedding、retrieval、chat、total 耗时，摘要至少给总耗时中位数和最大值；只报平均数会藏起慢请求。汇总 Embedding 和 Chat tokens；某次 Provider 没给 usage 就保留 `null`，不要补零冒充精确值。模型价格会变化，人民币成本应按运行当天 Provider 官方单价计算：输入 Token × 当日输入单价 + 输出 Token × 当日输出单价 + Embedding Token × 当日单价。当前接口若没有精确拆分计费字段，就不要编造金额。

## 哪些必须人工看？

打开本机 review 文件，逐条对照**完整回答**与**实际引用 preview**。对每条 `answered` 勾选 `supported`、`unsupported` 或 `uncertain`，记下判断理由。`uncertain` 不能自动算成功。不要让 `qwen3.7-flash` 再给自己的答案打分；这课由人复核。最后单独统计三类数量，不合入自动指标。

对错误要找原因。预期文档没进 Top-K 是 `retrieval_miss`；有资料却拒答是 `wrong_refusal`；没资料却回答是 `missing_refusal`；来源和检索都看似合理但回答越界是 `unsupported_generation`；引用是真实 Chunk 却无法支持核心结论是 `citation_support_problem`；超时、5xx 或结构失败是 `provider_failure`。后两类常需要人工判断，程序不能假装已经知道事实是否被支持。

## 跑第一轮真实 Evaluation

先确认三篇固定资料已用北京地域 `text-embedding-v4`、1024 维入库；Chat 使用 `qwen3.7-flash`。明确打开真实调用开关，顺序运行 12 题，期间不要改知识包或 Prompt。即使结果不是 12/12，例如 11/12、9/12，甚至更低，也先保留真实报告。只修明显程序 Bug、题集写错或资料版本不一致；不要反复针对这 12 题调参直到全绿，那会让评估集失去发现问题的能力。

选一个失败案例从头追：预期文档有没有进入 Top-K？状态该回答还是拒答？最终引用是否是预期文档？回答是否真的被引用片段支持？这比单一分数更能告诉你下一步该改检索、资料、模型输出，还是约束条件。如果计划部署自己的项目，还要在独立云数据库上验证 pgvector extension 和四次 migration；本地通过不等于云端已通过。

最后检查 3.1～3.6 回归、平台测试、Prompt Copy 和 390px 排版，查看 `git diff`、`git status`，确认 `.runtime`、Key、Cookie、完整真实回答和向量没有进入提交，再保存 Stage 3 的可恢复完成版本。到这里，你已经完成 Stage 3 的完整 AI 知识工作台。先保存一个可恢复的阶段版本，再回到阶段自检，确认自己能解释模型调用、Embedding、RAG、引用和 Evaluation 的完整关系。
