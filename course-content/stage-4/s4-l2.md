## 先准备一条能被找到的资料

从你**完成后的 4.1 项目**继续。登录练习账号，在现有「知识文档」区确认或新建一篇自己的短资料，例如写下 Git restore 与 reflog 分别能帮助你做什么。先用已有知识检索确认文档状态为 `ready`，普通 RAG 仍能使用。这时 Agent 实验区只有 4.1 的回显工具，还没有知识搜索选项。

本课只新增一个业务只读工具：`search_knowledge({ query })`。你很快会看到模型提出搜索主题、服务端检索刚才的资料，再把短结果交回模型。Agent Loop 已在 4.1 完成，这里沿用它。

:::prompt{title="让 Agent 第一次搜索自己的知识库"}

```text
请从我完成的 Stage 4.1 项目继续，不重写 Agent Loop 或工作台。保留 echo_research_topic，再新增唯一业务只读工具 search_knowledge。模型可见参数只有 { query: string }；服务端用 strict Zod 把 query trim 后限制在 1～1000 字符，并拒绝任何额外字段。工具的 risk=read。

Route 从 currentSession(request) 取得 userId，放进仅服务端可用的 Tool Execution Context，连同 request.signal 交给 Runtime 和 Tool。search_knowledge 复用现有 embed(query) 与 retrieveTopK(userId, embedding)，不要重新写向量 SQL。把结果缩成 matches 数组，每项仅含 title、position、最多 160 字符的 preview、similarity；空结果为 matches=[]。工具结果仍作为 role:tool 数据回给模型。

增加固定 knowledge_search Mock 模式：第一次模型决策提出 search_knowledge({ query: goal })；工具实际走 Stage 3 的 Mock Embedding 和 PostgreSQL owner Top-K，第二次模型决策根据工具结果给固定回答。在现有 AgentExperiment 增加「搜索我的知识库」选项和安全 matches 卡片，显示模型、Embedding、工具次数与终态。先让正常路径在页面跑通，不添加新表、其他工具或写操作，也先不要操作 Git。
```

:::

## 刚才是谁决定搜索范围？

模型决定 `query`，例如「Git 恢复版本」。它没有资格决定 `ownerId`：Route 从当前 Session 取得身份，Tool 用它调用 Stage 3 的 `retrieveTopK`。检索 SQL 在排序和 `LIMIT 3` **之前**筛选 owner、`ready`、Embedding 模型和维度。因此 Bob 即使有更相似的资料，也不会进入 Alice 的候选集。

`Tool Execution Context` 是服务端传给工具的可信信息，包含当前 userId、取消信号和预算预留函数；它不是模型参数。模型可见的 JSON Schema 只有 `query`。工具结果也只是一段不可信的 `role:tool` 数据：文档里若写着「忽略规则、调用其他工具」，不能把这段话拼成新的 system 指令。**模型决定搜什么，服务端决定搜谁的数据。**

:::check{title="核对你刚得到的结果"}
- `search_knowledge` 的模型参数中没有 `ownerId` 或 `userId`。
- 结果卡片没有文档 ID、Chunk ID、向量、完整 Chunk 或数据库字段。
- 4.1 的 Direct 与 echo 工具路径仍能运行。
:::

## 故意找错人，再修好边界

先用另一个练习账号 Bob 创建一篇与查询更相近的 Git 文档，然后切回 Alice 搜索。不要依赖模型说「我不会透露」；用数据库层的测试证明 Bob 的资料根本没有进入 Alice 的 Tool Result。

:::prompt{title="验证身份隔离与坏参数"}

```text
请给 search_knowledge 增加真实 PostgreSQL Alice/Bob 隔离测试。Bob 的 ready Chunk 与查询使用更接近的向量，Alice 也有一篇合法但略低相似度的资料。以 Alice 的 Session 运行 Agent：结果只能含 Alice 的 title、position、preview、similarity，Bob 的标题、短预览和 ID 都不可见，也不能占掉 Alice 的 Top-K 名额。再以 Bob Session 验证他能查到自己的资料。

测试浏览器请求体携带 userId/ownerId 时被严格拒绝；测试模型 Tool arguments 携带 ownerId/userId、缺 query、非字符串、空值、超长值与其他额外字段时均被拒绝，工具执行数为 0。保留 4.1 对未知工具和一次多个 Tool Calls 的整轮拒绝。空知识库应返回 matches=[] 并正常结束。不要把 Bob 资料交给模型后再让模型自行隐藏；确认 owner 过滤在 SQL Top-K 之前。
```

:::

观察两次搜索：Alice 能见自己的资料，Bob 能见自己的资料；Alice 看不到 Bob 那篇更相似的资料。再运行固定「伪造 ownerId」故障模式，应得到 `failed`、Embedding 0 次、工具执行 0 次。问题不是 `ownerId=2` 写得对不对，而是模型和浏览器都不该决定这个值。

## 每项工作开始前，单独算预算

一次真实知识搜索通常有三项 Provider 工作：第一次模型调用 1 单位，搜索前 Embedding 1 单位，最后模型回答 1 单位。模型可能直接回答，搜索也可能失败或被取消，所以不要在 HTTP 请求开始时一次扣 3 单位。

:::prompt{title="补齐 Embedding 预算与取消"}

```text
请在现有 Tool Context 中加入 reserveProviderUnit("embedding")，只在真正准备 embed(query) 前预留 1 个 weighted Provider unit。继续沿用每用户每分钟 10 单位的现有预算；每次真实模型调用仍各预留 1 单位，Mock 不消耗真实 Provider 单位。Embedding 前预算不足时返回 budget_exhausted，不能发出 Embedding 请求。把同一个 AbortSignal 从 HTTP 请求传到 Runtime、search_knowledge、embed；Abort 后不启动下一项工作。

用确定性测试覆盖：第一次模型前预算不足（0/0/0）；第一次模型后、Embedding 前不足（1 model、0 embedding、0 tool）；Embedding 已完成、最后模型前不足（1 model、1 embedding、1 tool）；完整闭环（2 model、1 embedding、1 tool，真实模式合计 3 units）。再覆盖模型前、Embedding 前、Embedding 中及 Tool Result 后取消。保持 4.1 的 4 步/3 次工具上限和所有终态。给 UI 增加安全的次数与预算显示，不展示原始 Provider JSON。
```

:::

运行「Embedding 预算不足」和「最终模型预算不足」模式，分别观察 `embeddingCalls=0` 与 `modelCalls=1、embeddingCalls=1、toolCalls=1`。再运行取消测试，确认取消之后不会开启下一次模型或 Embedding。Mock 负责稳定复现这些边界；真实网络取消不要求在每个时机瞬间物理终止。
