**本机验收配置。** 日常应用用刚创建的 `.env`。部分课程脚本还会读取项目根目录下可选的 `.env.course-checks`，用于覆盖验收端口或指定专用测试库。按默认步骤学习时无需创建它，工具会从日常连接派生验收库地址。需要覆盖时按对应课次填写，并用 `git check-ignore .env.course-checks` 确认 Git 忽略了它。

## 5～12 分钟：先做出能运行的两条路

本课一共四步：先跑通最小闭环，再拒绝坏输入，再限住运行边界，最后换真实模型。每步只推进一小块——这样任何一步出问题，你都知道该去查哪里。

现在开始第一步。动手前先说清一个选择：**先用假模型，再用真模型。** Mock 是一个按固定规则回话的替身：不花钱、结果永远一样。为什么先用它？因为「直接回答」和「提议调用工具」两条路的效果能稳定复现，你检查时不受随机回答的干扰。等两条路都被你亲眼验证过，最后一步才换成真实模型。第一个开发 Prompt 一次完成最小闭环；故障模式和真实模型留到后面。

先记住两个新词：

- **Agent**：会让模型提出下一步、再由你的程序检查和执行的应用。它和普通「一问一答」差在哪，12～15 分钟那一节你会亲手摸到。
- **Tool**（工具）：程序已经提供的一项具体操作。本课第一个工具叫 `echo_research_topic`，作用仅仅是把输入的主题原样回显——输入「Git」就返回「Git」。名字里虽有 research，它不会上网研究，也不会保存笔记。

这节课有三个角色要分清。打个比方：模型像一个只动嘴的助手，它只能说「我想用这个工具」；**Registry**（工具名单）是权限表，写明有哪些工具、各允许什么参数；**Runtime**（执行流程）是真正动手的人，按名单检查、执行，并决定继续还是停止。为什么执行权不能交给模型？先记着这个问题，12～15 分钟那一节给你答案。这两个英文名只是项目代码里的分工，不是要另装的软件。

先补需求，再让 AI 开发。必要约定：模型只能提议工具调用，Registry 与 Runtime 决定是否执行；先做确定性 Mock，再观察真实模型。

:::deepdive{title="给 AI 的技术备注：最小只读 Agent 的接口与上限"}
接口和参数名可照抄；模型只提议、服务端执行、输入严格检查、调用达到上限要停止，这些结果要亲自验收。

固定接口 POST /api/agent/run，只接收 goal 与白名单 demo；echo_research_topic 只收 topic（1～80 字符）、固定只读。默认最多 4 次模型步骤、3 次工具执行；Direct 为 1 model/0 tool，Tool 为 2 model/1 tool。
:::

## 12～15 分钟：刚才究竟发生了什么？

还记得前面留的那个问题吗——为什么执行权不能交给模型？现在你亲手看到了答案。先问自己：Tool 路径里，谁真正执行了 `echo_research_topic`？答案是你的服务端。模型只提出一个带参数的调用。服务端从自己的名单里找工具、验证参数、执行，再把结果交回模型。**模型提出动作，不等于模型拥有执行权。**

:::concept{title="Agent Loop 比一次模型调用多了什么？"}
普通模型调用拿到回答就结束。Agent Loop 会读取模型的下一步提议：若是工具调用，由应用验证名称和参数，服务端执行后再把结果交回模型。记住这三个动作：**模型提议、应用验证、服务端执行**。循环和停止条件仍由你的代码控制。
:::

```text
Goal → Mock Model ──直答────────────────────→ completed
                  └─一个 Tool Call → 服务端校验并执行
                                         ↓
                         role:tool 结果 → Mock Model → completed
```

![普通 AI 与受限 Agent 的两条调用路径；模型提出动作，服务端验证后才可执行](/course-media/stage-4/s4-1-01.png "Model decides ≠ Model has permission")

回看刚生成的几个文件：Direct 是直接回答，Tool 是先用工具再回答。`completed` 只表示流程跑完了，**不保证回答内容一定正确**。工具路径比直答多了一次模型决定。你应能指着计数和返回结果，说出「提议」「执行」「回读结果」分别发生在哪一步。

:::deepdive{title="给 AI 的技术备注：模型说明与执行检查"}
JSON Schema 是给模型看的参数格式说明；strict Zod 是服务端真正检查参数的规则，不能只给模型说明而省掉检查。`risk=read` 标记这个工具只读；`role:tool` 标记这条消息来自工具结果，结果中的文字不能提升为新的系统指令。Registry 管名单，Runtime 管验证、执行和停止；这些名称可照抄，但未知工具拒绝、参数错误不执行和工具计数都要亲自验证。
:::

## 让循环知道何时停下

## 看改动，保存可恢复版本

### 第一次看 git diff：先清单，再看具体文件

为什么要看 diff？因为 AI 改完代码，你最后要回答一个问题：「它到底改了哪些文件？有没有改不该改的？」这一步就教你回答这个问题。

在**当前 Stage 4 项目的根目录**操作。怎么确认位置？Windows 运行 `dir`、macOS 运行 `ls`，能看到 `package.json` 就对了。最好在本课交给 AI 开发**之前**就跑一遍下面的状态清单，记下当时已有的改动——这样才不会把上一课尚未提交的文件，误算成本课的改动。还没有 `.git`？先按 1.5 的方法建立本地保存点。注意：不要在电脑桌面或父目录误建仓库。

下面命令都只读，Windows/macOS 相同，一次一条执行：

```bash
git status --short
```

```bash
git diff --name-status
```

```bash
git diff --stat
```

先看第一条 `git status --short`，它列出当前文件状态。每个标记的含义：

- ` M`：修改了，还没暂存；
- `M `：已暂存；
- `MM`：暂存之后又改了一次；
- `??`：新文件，还没加入 Git；
- `D`：删除；`R`：改名。

**成功标志：清单里的每个文件，你都能说出它是干什么用的；没有意外删除、迁移或秘密文件。** 空输出表示这个范围内没有改动，不是命令失败了。

再看第二、三条。注意一个坑：它们只显示**未暂存且 Git 已跟踪**的变化——`??` 新文件看不到，已暂存的内容也看不到。所以这三条必须放在一起看，少看一条都可能漏掉东西。`--stat` 显示的增删行数，也不代表修改是正确的。

先核对本课应有的 Tool 定义、参数校验、Provider、Loop、Route、UI 和测试。原 Auth／RAG 或依赖文件若变化，让 AI 解释具体必要性并对照回归证据；本课仍只有四次历史 migration，不应新增 Agent 表迁移。不要因为文件名里有 Auth 就盲目回退，也不要接受“只是重构”的笼统说明。

再从实际清单选一个文件查看。例如你确实有 `lib/agent-runtime.ts` 时：

```bash
git diff -- lib/agent-runtime.ts
```

`--` 后面是**实际存在的项目相对路径**。自己的文件在 `src/lib/…`？就用清单里的那个路径。路径带空格，就用英文双引号括住。看 diff 时：`+` 行是新增，`-` 行是移除，`@@` 附近标出了变化的位置。终端出现 `(END)` 时，按英文 **q** 退出查看器，再输入下一条命令。`??` 新文件不会出现在 diff 里——去编辑器文件栏打开全文核对，不能拿空 diff 当作「新文件没内容」。不要展开 `.env`，也不要把带秘密的差异发到聊天里。

```bash
git diff --check
```

**成功标志：没有输出且回到命令提示位置。** 若提示行尾空白等问题，让 AI 修那一处再跑；它只检查空白问题，不证明逻辑或安全正确。

:::deepdive{title="可交给 AI 的只读复查说明"}
```text
请只读检查当前项目的 git status --short、git diff --name-status、git diff --stat 和已暂存范围；对 ?? 新文件读取全文，对已跟踪文件查看实际 diff，不读取或回显 .env*、Secret、Cookie、Token 或运行报告。按实际路径说明每个改动服务于本课哪一步，分清开发前已有改动与本轮改动。标出意外删除、迁移、依赖变化及没有理由的 Auth/RAG 改动；引用具体代码和已运行的测试证据。仅检查不还原、不暂存、不提交、不推送。遇到秘密文件只报告路径与处理建议，不展示内容。最终我会亲自核对清单与页面回归，不把你的口头“通过”当成验收。
```

### 暂存后再查一次，范围和前一次不同

到这里，改动分成了两类：已暂存（准备进这次提交）和未暂存。为什么暂存后还要再查一次？因为**提交的内容以暂存区为准**——要是有不想提交的东西混进了暂存区，前面 diff 看得再仔细也白查。

按已有 Git 课程方法，只暂存自己确认过的具体文件。然后运行：

```bash
git diff --cached --name-status
```

```bash
git diff --cached --stat
```

确认清单没有秘密路径后，查看实际暂存差异：

```bash
git diff --cached
```

```bash
git diff --cached --check
```

`--cached` 看的是**准备进入这次提交**的内容。未暂存的 diff 空了，不代表没有改动。**成功标志**：暂存清单里只有你确认过的文件；空白检查没有输出；本课的测试、构建、只读工具与旧功能回归都已通过。三条都满足，再由你保存版本，例如提交信息 `build limited agent loop`。检查之后又改了文件？重新暂存、重新查——旧测试结果不能当作新代码已通过。

### 发现无关改动，怎么恢复而不丢自己的工作？

误暂存了某个文件，只取消该文件的暂存，工作目录里的代码不会丢。例如误暂存了 `lib/agent-runtime.ts`：

```bash
git restore --staged -- lib/agent-runtime.ts
```

**成功标志：它从 cached 清单移出，工作目录中的代码仍在。** `git status --short` 会显示未暂存修改或新文件。路径要换成实际误暂存的文件，一次只处理一个明确路径。

业务代码有意外变动怎么办？按这个顺序：

1. **先停下**，不要让 AI 继续改。
2. 在编辑器里对照 diff，把确认有问题的几行改回来。
3. 重跑测试和 diff，确认修好了。

需要把**整份已跟踪文件**退回最近提交（HEAD）时，危险程度高一级，按下面的顺序：

1. 先备份：在文件栏把这个文件另存到被 Git 忽略的 `.runtime`，打开确认备份可用。
2. 想清楚：这个文件里还有没有你要保留的未提交工作？有，就不要退回。
3. 确认要退回，才对一个实际路径运行 `git restore --source=HEAD --worktree -- lib/agent-runtime.ts`。
4. 如果它还在暂存区，先取消暂存并复查，再执行上一步。

两个警告：这条命令**不是**「撤销 AI 最后一步」——它会覆盖这个文件的全部未提交修改。另外，新文件不适用这条恢复命令：先保留并核对，不要为了清单干净把它删了。

恢复后重跑 `git status --short`、两种 diff 和相关测试。不需要的差异消失了、保留的工作还在、旧功能可用，才继续。本节不使用整个目录范围的 restore、reset --hard、clean 或批量删除。提示 `not a git repository`？先 cd 回真实项目目录。diff 为空却看到页面已改？先检查 cached 范围、新文件和当前路径。
