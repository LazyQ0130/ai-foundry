## 5～12 分钟：先做出能运行的两条路

现在才开始添加 Agent。先让固定的 Mock 扮演模型：它不调用真实服务，所以我们可以稳定地看到「直接回答」和「提议调用工具」两种结果。第一个开发 Prompt 一次完成最小闭环；故障模式和真实模型留到后面。

:::prompt{title="先做出可见的 Mock Agent 闭环"}

```text
请从当前 Stage 4 Starter 开始，在现有 Next.js 工作台做一个最小、可运行的 Mock Agent 实验。先只完成 Direct 和 Tool 两条正常路径，不接真实模型，也不加故障演示。

1. 在服务端建 Tool Registry，只注册 echo_research_topic。输入 { topic: string } 去掉首尾空格后为 1～80 字符；工具只回显主题，不读写数据库或访问网络。模型只看到工具的 name、description、JSON Schema；strict Zod 校验、risk=read 和 execute 留在服务端。
2. 新增 deterministic Mock model：Direct 返回一条回答；Tool 先返回一个 echo_research_topic 调用，收到工具结果后再返回回答。不要让浏览器提供工具代码。
3. 新增有界 agent-runtime，用 for 循环，默认最多 4 次模型步骤和 3 次工具执行。直答返回 completed；工具路径先校验并由服务端执行，再把结果作为 role:tool 数据交回 Mock model，继续到 completed。记录模型与工具次数。
4. 新增受保护的 POST /api/agent/run：复用现有 Session 和同源写保护；请求体只接收 goal 与固定 demo（direct/tool），身份从 Session 获取。首页新增小型 AgentExperiment，输入目标、选择 Direct/Tool、运行并显示终态、回答和两个计数。

请先运行本机 Mock，确认两条路径都能在页面完成。保留原 AI、知识库和 RAG 功能；不要新增 migration、其他工具、审批、MCP 或持久化，也先不要操作 Git。
```

:::

保持 `npm run dev` 运行并刷新首页。现在实验区才应该出现。输入一个短主题，先选「直答演示」，再选「Tool 演示」：

| 页面操作 | 第一次应看到的结果 |
|---|---|
| Direct | `completed`，模型 1 次，工具 0 次 |
| Tool | `completed`，模型 2 次，工具 1 次 |

如果实验区没出现，先检查开发服务器和第一个 Prompt 的改动是否保存；如果计数不对，检查工具结果有没有交回 Mock，让它做第二次决定。到这里你已经亲手看到了最小 Agent 闭环。

## 12～15 分钟：刚才究竟发生了什么？

先问自己：Tool 路径里，谁真正执行了 `echo_research_topic`？答案是你的服务端。模型只提出一个带参数的调用。服务端从自己的名单里找工具、验证参数、执行，再把结果交回模型。**模型提出动作，不等于模型拥有执行权。**

```text
Goal → Mock Model ──直答────────────────────→ completed
                  └─一个 Tool Call → 服务端校验并执行
                                         ↓
                         role:tool 结果 → Mock Model → completed
```

![普通 AI 与受限 Agent 的两条调用路径；模型提出动作，服务端验证后才可执行](/course-media/stage-4/s4-1-01.png "Model decides ≠ Model has permission")

回看刚生成的几个文件：Tool Registry 是服务端允许执行的名单；JSON Schema 是告诉模型该怎样提议参数的说明；strict Zod 是服务端真正用来验收参数的关口；`risk=read` 标记这个工具只读；`role:tool` 表示工具结果是数据，不是新的系统指令。Direct 没有工具调用，Tool 则多了一次模型决定。先看到两种结果，再理解这些名字，就不会把「模型说要调用」误当成「已经安全执行」。

## 让正常闭环拒绝坏动作

现在已有可运行的 Mock，可以让它故意提出坏调用。先补强刚才的校验，再让页面提供固定故障模式。这里不用增加第二个工具。

:::prompt{title="补齐严格校验与固定故障演示"}

```text
请继续改进现有 Agent 文件，不重写已经跑通的 Direct/Tool 路径。Tool Call 由服务端校验：id 为非空字符串且不超过 128 字符，type 为 function，工具名必须在唯一 Registry 中，arguments 为不超过 2048 字符的有效 JSON；strict Zod 拒绝缺字段、错类型、空 topic 和任何额外字段。一次返回多个 Tool Calls 时整轮拒绝，不能先执行第一个。执行前确认 risk=read；失败只返回受控错误类别，不带原始 Provider 内容。

扩展 deterministic Mock 和 AgentExperiment 的固定模式：unknown_tool、bad_json、extra_field（在 topic 外加 ownerId）、multiple_tools。Route 只接受这些固定 demo 值，不接受浏览器传入任意工具名、userId、ownerId、风险级别或工具实现。为正常闭环和四种拒绝路径补测试，并接好 npm test 脚本。先不要接真实 Provider，也不要操作 Git。
```

:::

再看页面：正常的 Direct/Tool 仍应成功；未知工具、坏 JSON、多余 `ownerId`、一次两个调用都应 `failed`，工具执行数为 0。特别看「多个调用」：服务端没有偷偷选第一个执行。这个结果比模型口头承诺遵守规则更可信。

## 让循环知道何时停下

正常和非法调用都看过了，再测试运行边界。模型可能不断要工具，用户也可能中途取消。每次准备调用模型前，由服务端检查是否还能继续。

:::prompt{title="补齐步骤、预算与取消边界"}

```text
请在现有有界 for Runtime、Route 和实验区上增量加入停止状态，不改变已通过的 Direct/Tool 和严格校验。默认 maxAgentSteps=4、maxToolCalls=3；每次模型调用前检查 AbortSignal、步骤/工具上限和预算预留。返回 completed、failed、cancelled、max_steps、max_tools、budget_exhausted 等明确终态与受控步骤摘要。工具收到同一 signal；取消后不再开始新的模型或工具调用。

Route 复用每用户每分钟 5 次 HTTP guard。真实 Provider 将复用每用户每分钟 10 个 weighted Provider units 的预算函数：每次真实模型请求前预留 1 单位；Mock 不扣真实单位。扩展固定 Mock 模式 max_steps、max_tools、budget_exhausted、cancel，并给 UI 加取消按钮。补齐这些固定路径的测试；不要泄漏 Key、Cookie、system prompt 或原始响应。保持原 AI、知识库与 RAG 路由不变；先不要操作 Git。
```

:::

现在用页面和测试逐项观察，而不是只读代码：

| 故障 | 你应该看到 |
|---|---|
| 未知工具名 | `failed`；工具执行 0 次 |
| 坏 JSON 参数 | `failed`；没有猜测或修补参数 |
| 多余 `ownerId` 字段 | strict Zod 拒绝；工具执行 0 次 |
| 一次两个 Tool Calls | 整轮拒绝；工具执行 0 次 |
| 模型反复请求工具 | 到 `max_steps` 或 `max_tools` 后停止 |
| 预算不足 | `budget_exhausted`；下一次 Provider 请求没有发出 |
| 运行中取消 | `cancelled`；之后不再开启模型或工具 |

:::task{title="亲手复核三条安全边界"}
运行「未知工具」「多余字段」「多个工具」三种模式，记下每次工具执行数。再试预算不足与取消。回答自己：这些停止是谁决定的——模型，还是你的服务端？
:::

:::check{title="完成故障实验后"}
- `npm test` 覆盖直答、工具闭环、非法参数、多工具、上限、预算和取消；`npm run build` 通过。
- 多工具时没有执行第一个工具；取消后没有新调用。
- 失败信息只给受控类别，不泄漏 Provider 原文或服务端配置。
:::

:::warning{title="Mock 与真实预算的含义不同"}
Mock 是稳定的教学替身，不花百炼费用；真实模式在发出每一次模型请求前预留一个 Provider 单位。一次工具闭环通常是两次模型调用，不是一条 HTTP 请求就算一个单位。
:::

## 最后接入并试一次真实模型

前面两条正常路径和所有故障都由 Mock 验证过了。现在让真实模型接到同一 Runtime 和同一只读工具，观察它能否自行选择直答或 Tool。

:::prompt{title="接入真实 Provider，保留 Mock 验收"}

```text
请给现有 agent-provider 增加 real 模式，复用项目 ai-provider 已有的服务端配置、Key、超时、错误映射与取消信号，不改变原 generate、stream、embed 行为。使用现有 Tool Registry 生成的模型可见 JSON Schema，发送 tool_choice=auto、enable_thinking=false、parallel_tool_calls=false；严格解析 finish_reason、tool_calls 与 usage，再交给同一个 agent-runtime 校验和执行。每次真实模型调用前复用 Route 的预算预留；Mock 的固定结果和故障测试继续可用。接好本地 Provider Stub 测试，覆盖成功、非法响应与上游失败；不要把 Provider 原始响应或 Key 返回给页面。完成后运行 npm test 和 npm run build，先不要操作 Git。
```

:::

只有 Mock、Stub 测试和本机构建通过后，才把 `.env` 的 `AI_PROVIDER_MODE` 设为 `real`，填写你自己的北京地域百炼配置。用非敏感短主题先试普通解释，再试「请用 echo_research_topic 回显主题 RAG，然后报告结果」。记录模型调用次数、工具执行次数、`finish_reason`、usage 与耗时，不保存完整请求、回答或 Key。

真实模型可能选择直答。`tool_choice=auto` 把选择留给模型；本课不靠强制调用来伪造 Tool 成功。最多换两次更明确的自然语言任务；若仍直答，就如实记录。确定性的 Mock/Stub 测试用于验证程序分支，真实调用用于检查集成链路。

## 看改动，保存可恢复版本

运行 `git status`、`git diff`、`git diff --check`。指出新增的 Tool 定义、参数校验、模型调用、循环停止、Route 与 UI 分别在哪个文件；确认原 Auth、RAG 和四次 migration 没被无关改动。检查暂存区没有 `.env`、Key、数据库连接串或运行日志，再保存一次版本，例如提交信息 `build limited agent loop`。

本课只得到一个**请求内**的只读小 Agent。下一课才把已有知识库检索接成真实业务工具；写入确认、MCP、多步工作流与持久化都在后续课程。现在你应该能清楚地说：**模型只是提出动作，执行权在服务端。**
