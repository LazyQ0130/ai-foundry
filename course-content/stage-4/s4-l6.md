## 第一单元：保存与回读

从完成的 4.5 项目继续。先用旧的「完整研究 Workflow」跑到等待确认，记住刷新后提议会消失。现在让 AI 增量开发一个新的「4.6：可恢复研究 Run」入口。这个入口此刻还不存在；完成下面的 Prompt 后才操作它。

本课开始真正使用前面预告的词：**Run** 是一次研究任务，**Step** 是任务里的步骤，**Action** 是等待确认的精确写提议；保存它们，就是持久化。**幂等**在这里指同一个确认动作重复请求，业务笔记仍只新增一条；**事务**让保存笔记和标记执行状态一起成功或一起撤回。先用“刷新后找回同一提议”和“重复确认仍一条”理解结果，再按下面的实现约定开发与验收。

:::concept{title="重复确认、同时确认、中途失败：三件不同的事"}
**重复确认**：你没收到成功响应，再提交同一个 Action，应该拿回原笔记，不再新增。这是本课的幂等；重新开启任务产生另一个 Action，即使标题相同，也不自动算重复。

**并发确认**：两个请求几乎同时确认同一个 Action。不能只靠按钮变灰，因为另一窗口或请求仍可能发来；数据库要让它们协调顺序，并约束同一个动作只能对应一条笔记。

**事务回滚**：笔记刚写入，但“Action 已执行”还没记好时发生错误，这一组数据库修改应一起撤回。否则重试时系统不知道已经写过，会留下不一致的记录。事务不等于撤销所有外部服务调用，本课这一组处理的是数据库中的笔记和执行状态。
:::

**checkpoint（安全恢复点）**是已存入数据库、程序明确允许从那里继续的任务状态。刷新后找回提议，靠的是保存过的 Run 和 Action，不是浏览器记住程序运行到了哪一行。后面的 Resume（恢复）只处理明确标为可恢复的暂停；尚未保存安全恢复点的 `running` 任务崩溃，不会自动接着跑。

## 回看刚才写入的三张表

`AgentRun` 保存任务归属与当前状态。`AgentStep` 按 `(runId, position)` 排列，为页面提供审计时间线；它不负责消费写操作。`AgentAction` 保存精确的写入参数与消费状态。Resource 上的 `agentActionKey` 是业务结果的第二道唯一约束。运行 `npx prisma migrate status`，应看到原四次 migration 加本课第五次。

:::concept{title="为什么分成 Run、Step 和 Action？"}
Run 回答“这是谁的任务，现在到哪一步”；Step 回答“每一步发生了什么”；Action 回答“这份精确写提议是否已被确认和执行”。`idempotencyKey` 是同一个写动作的稳定身份证，数据库用它阻止重复产生业务笔记。它只保证这一 Action 的业务幂等，不表示网络请求只发生一次，也不等于全系统 exactly-once delivery。
:::

![Agent Run 持久化、跨重启恢复与幂等业务写入](/course-media/stage-4/s4-6-01.png "Persist → Pause → Resume → Idempotent Write")

浏览器只保存 Run ID。它不是通行证：每次 GET、Resume 和 Confirm 都要重新读取 Session，并核对 `run.ownerId`。Step 只存短摘要、工具名、状态和安全用量；不要把密钥、Token、完整模型响应、Embedding 或完整知识 Chunk 放进时间线。

## 真正重启服务器，再检查权限

Server A／B／C 是**同一个项目先后启动三次**，不是同时开三份服务。先在页面停到 waiting_approval，记下非秘密 Run ID；在日常 dev 终端 Ctrl+C，等命令提示位置，再原目录 `npm run dev`，等 Ready 后回同一地址刷新并恢复最近 Run。不要改数据库、Secret 或注册新账号冒充恢复。确认后再按同样顺序重启一次；GET 仍 completed、saved ID 不变才通过。重启后端口变了先查原占用者，不用另一个地址的 Cookie 凑证据。

在 `waiting_approval` 时停 Server A，启动 Server B（同一 PostgreSQL 与签名 Secret），用同一 Session GET Run。提议和时间线仍在，取得新 Token 后确认。再启动 Server C，GET 应是 `completed` 且 saved Resource ID 不变。让 Bob 用 Alice 的 Run ID 尝试 GET、Resume 和 Confirm，均不得读到 Alice 的 goal、摘要、提议或业务结果。向创建/恢复/确认请求分别塞 `ownerId`、`status`、`actionId`、`idempotencyKey` 等额外字段，strict schema 应拒绝。取消等待中的 Run 后，也不能 Resume 或确认。

## 最后试真实 Provider

8 次并发 Confirm、两个并发 Resume、事务中途失败、响应丢失重试和跨用户请求，不手工复制 Token。在 4.2 的 `npm run test:db` 增量加入本课实际 Route／事务测试，由脚本内存保留 fixture Token、同时发送请求，并查询对应新 Action／Resource／Run。**成功标志：同 Action 一条业务结果、回滚 +0、正常重试后 +1，竞争 Resume 只有一套实际工作；拒绝与恢复断言逐项通过、失败数 0、退出 0。** 测试只动 stage4_checks 中的新 fixture，不能给日常 HTTP 加回滚开关。测试结束关闭自建服务，原日常 Run 和资料仍在。

测试通过后，真实模式配置保存，停止旧 dev 并重新 `npm run dev`；当前账号先有真实向量的 ready 文档，新入库至少等 60 秒，之后才运行和重启验收。切回 Mock 也按同样顺序重启。运行中断且尚未保存 checkpoint 的 running 不会自动复活，这与等待确认的可恢复状态不同。

确定性、PostgreSQL、并发与重启测试通过后，切到已配置的 Chat 模型与 Embedding 模型。观察真实搜索、综合到 `waiting_approval`：正常两次模型、一次 Embedding、一次只读 Tool，确认前 Resource +0。重新 GET 或重启后确认，Confirm 不再请求 Provider，Resource +1；重发仍 +1。真实模型会自主选择工具，若一次没有提出预期 Tool，记录实际输出并检查 Prompt/Tool 边界，不伪造计数。

这一课解决刷新与重启后的等待恢复、可恢复暂停和同一写动作只产生一条业务笔记。它仍有以下运行限制，交付时必须说明：

- 任务没有独立的后台执行进程或排队服务，不能保证关掉请求后任务仍自动完成。
- 多台服务同时运行时，没有额外的执行权协调机制，不能声称支持多实例或跨区域调度。
- 请求、模型调用与 MCP 限流只存在当前服务进程内，不能把它当成多实例共享限流。
