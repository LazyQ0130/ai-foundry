## 回看刚才写入的三张表

`AgentRun` 保存任务归属与当前状态。`AgentStep` 按 `(runId, position)` 排列，为页面提供审计时间线；它不负责消费写操作。`AgentAction` 保存精确的写入参数与消费状态。Resource 上的 `agentActionKey` 是业务结果的第二道唯一约束。运行 `prisma migrate status`，应看到 Starter 四次 migration 加本课第五次。

:::concept{title="为什么分成 Run、Step 和 Action？"}
Run 回答“这是谁的任务，现在到哪一步”；Step 回答“每一步发生了什么”；Action 回答“这份精确写提议是否已被确认和执行”。`idempotencyKey` 是同一个写动作的稳定身份证，数据库用它阻止重复产生业务笔记。它只保证这一 Action 的业务幂等，不表示网络请求只发生一次，也不等于全系统 exactly-once delivery。
:::

![Agent Run 持久化、跨重启恢复与幂等业务写入](/course-media/stage-4/s4-6-01.png "Persist → Pause → Resume → Idempotent Write")

浏览器只保存 Run ID。它不是通行证：每次 GET、Resume 和 Confirm 都要重新读取 Session，并核对 `run.ownerId`。Step 只存短摘要、工具名、状态和安全用量；不要把密钥、Token、完整模型响应、Embedding 或完整知识 Chunk 放进时间线。

## 让故障暂停，再从安全位置继续

:::prompt{title="实现 paused 和 Resume"}

```text
增加 deterministic persistent_provider_failure：在任何业务写入之前让一次模型工作发生可恢复的 UPSTREAM 故障。把失败 Step 的 errorCategory 和 Run.status=paused 持久化；不能创建 Action 或 Resource。POST /api/agent/runs/:runId/resume 只接受 {}、只允许当前 Session owner 的 paused Run。用原子 paused→running 状态迁移抢执行权；并发两个 Resume 时只启动一套模型工作，另一请求返回 409。V1 从搜索与综合这个安全 checkpoint 重新执行只读阶段，每次实际 Provider 工作重新逐项扣预算。预算在第二次模型前耗尽时也先记录 failed/blocked Step 与 paused Run，不能留下半个 Action。cancelled 与 failed 视为终态。UI 显示暂停原因和 Resume 按钮。
```

:::

选择「可恢复故障」，看到 `paused` 和失败 Step，再点 Resume。它会重新搜索、综合并到达 `waiting_approval`。Resume 指从安全 checkpoint 重做可重复的只读工作，并不表示从程序的下一行 CPU 指令继续。故意同时发两次 Resume，只有一位请求获得执行权。

:::check{title="暂停不是丢失"}
- 故障后已有 Run 和失败 Step，但没有 Action 或 Resource。
- Resume 只能从 `paused` 开始；`completed`、`failed`、`cancelled` 不重跑。
- 重新发生的真实模型或 Embedding 工作重新计入预算。
:::

## 一个确认动作只能有一个业务结果

4.3 的无状态签名可验证参数未被改动，但同一有效 Token 再次提交仍可能产生第二条 Resource。现在 Action 是数据库中的权威记录。让 AI 增量加入确认，再故意重发。

:::prompt{title="把确认绑到 Action"}

```text
从这一课开始，当前项目中所有真正执行 save_research_note 的确认操作，都统一走 persisted AgentAction 路径。前面课程留下的只读工具和安全验证逻辑继续保留；旧的无状态可确认写入口不得继续产生真实 Resource，可以返回受控的已迁移提示。不要通过删除前面功能来实现。Confirm body 严格只接收 approvalToken。验 V2 HMAC、当前 Session userId、runId、actionId、toolName 与 canonicalArgs 后，在 PostgreSQL Prisma transaction 中 SELECT AgentAction FOR UPDATE，检查 owner、Run 和 Action 状态。稳定计算 SHA-256(JSON.stringify([runId,stepId,toolName,canonicalArgs])) 作为 idempotencyKey。首次确认用签名的精确 title/content 创建 Resource(agentActionKey=idempotencyKey)，同一事务标 Action executed、记录 approvedAt/executedAt、完成 Step 与 Run。已 executed 时按 agentActionKey 返回原 Resource，不再写。Confirm 不调用模型。确认后 UI 重新 GET Run，以数据库时间线为准。增加重复提交按钮，显示复用已有结果。
```

:::

点确认后，Run 与 Action 都完成，Resource 增加一条。用同一个 Token 再确认，得到已有 Resource，数据库仍是一条。再并发发送至少 8 个同 Action 的 Confirm，断言 `AgentAction=1`、`Resource(agentActionKey)=1`、`Run=completed`，没有随机 500。这里保证的是**同一个 Action 的幂等业务写入**；网络请求仍可能重发，不能称整个系统拥有 exactly-once delivery。

:::prompt{title="故意让事务在写入中途失败"}

```text
写 PostgreSQL 集成测试：在 Resource.create 后、Action executed 更新前，通过仅在直接测试 helper 可注入的 hook 抛错。断言整个事务回滚：Resource=0、Action 仍 proposed、Run 仍 waiting_approval。随后正常 Confirm，只产生一条 Resource。再模拟数据库已 commit 但客户端丢失响应，重新建 Prisma Client 或重启进程后用原 Token 重试，返回同一 Resource。测试 hook 不得由 HTTP Route 接收。
```

:::

事务把业务写入与状态变化绑在一起；行锁让并发确认排队；Resource 的数据库 UNIQUE 防止第二条相同业务结果。Step 负责解释“发生了什么”，Action 负责判定“这次写动作是否已消费”。

## 真正重启服务器，再检查权限

在 `waiting_approval` 时停 Server A，启动 Server B（同一 PostgreSQL 与签名 Secret），用同一 Session GET Run。提议和时间线仍在，取得新 Token 后确认。再启动 Server C，GET 应是 `completed` 且 saved Resource ID 不变。让 Bob 用 Alice 的 Run ID 尝试 GET、Resume 和 Confirm，均不得读到 Alice 的 goal、摘要、提议或业务结果。向创建/恢复/确认请求分别塞 `ownerId`、`status`、`actionId`、`idempotencyKey` 等额外字段，strict schema 应拒绝。取消等待中的 Run 后，也不能 Resume 或确认。

## 最后试真实 Provider

确定性、PostgreSQL、并发与重启测试通过后，切到已配置的 `qwen3.7-flash` 与 `text-embedding-v4`。观察真实搜索、综合到 `waiting_approval`：正常两次模型、一次 Embedding、一次只读 Tool，确认前 Resource +0。重新 GET 或重启后确认，Confirm 不再请求 Provider，Resource +1；重发仍 +1。真实模型会自主选择工具，若一次没有提出预期 Tool，记录实际输出并检查 Prompt/Tool 边界，不伪造计数。

没有后台 Worker/Queue、多实例执行 Lease 或跨区域编排；请求、Provider 与 MCP 限流仍是单实例内存。这一课解决刷新与重启后的等待恢复、可恢复暂停和 Action→Resource 的业务幂等。
