## 两个人都登录了，为什么资料还是共享的？

上一节，Alice 和 Bob 已经可以分别注册和登录。服务端也能从 Session 认出当前是谁。但 Bob 登录以后，为什么还能看到 Alice 创建的资料？先不要改页面：直接看现有的 `GET /api/resources`。如果它查询整个 Resource 表，登录只挡住了陌生人，并没有把资料分给各自的账号。

本课继续使用你完成 2.5 的**同一个项目和专用练习数据库**。先查看 Git 状态、Prisma schema、两次迁移、四种 Resource 方法、页面管理组件，以及库里现有 Resource 的 ID、数量、标题和内容。保留你在 Stage 1 做的搜索、标签、重要筛选、统计与自选功能；保留 A/B 式的个人改动，不用 Starter 覆盖。预计操作 80～110 分钟，迁移及网络等待另计。实验只用非敏感练习账号。

## 登录解决身份，所有权解决归属

一条资料除了标题、简介和分类，还需要知道**是谁创建的**。本节用 `ownerId` 记录所属 User 的 ID。Session 回答“请求者是谁”；资料所有权回答“他能否读写这一条”。服务端的数据库查询必须使用这两个信息，前端隐藏卡片或按钮不能代替服务端判断。

**认证**是认出请求者，**授权**是判断他能做什么。例如 Alice 的用户 ID 是 7，她的一条资料记录 `ownerId=7`；Bob 登录后，服务端认出的是 Bob，不能因为他填了 Alice 的资料 ID，就准许修改。这个 ownerId 必须由服务端按登录身份设置，不能信任页面自行报来的名字或编号。

:::concept{title="三个不同的问题"}

没有有效 Session，资料 API 返回 **401**。有 Session 但目标 ID 不存在，返回 **404**；目标确实存在却属于别人，也返回同样的 **404**，不向请求者透露他人资料是否存在。数据库暂时不可用时返回 **503**，响应不要泄露连接串。客户端给出的 ownerId 不能成为权限依据。

:::

## 给 Resource 加上所属用户

在现有 `Resource` 上增加可空的 `ownerId Int?` 和到 `User` 的关系，在 `User` 上增加 `resources Resource[]`，为 `ownerId` 建索引。参考实现的外键在删除用户时将其资料 ownerId 设为 null；本课没有删除用户的公开接口。迁移 SQL 应当只加列、索引和外键，不应出现删除或重建 Resource 表。运行迁移前后都直接查询原记录，逐条比对 ID、标题、简介、分类和重要状态。

### 以前保存的资料怎么办？

2.3～2.5 的历史资料没有归属信息。可空字段让迁移安全通过，旧记录保持原样，`ownerId=null`。它们仍在数据库里，但不进入任何普通用户的“我的数据库资料”列表；猜测其 ID 也不能修改或删除。页面变空不等于数据被删，先去数据库核对原 ID 和数量。

### 为什么不能自动分配给 Alice？

过去没有记录创建者，程序无法知道旧资料是谁的。把所有旧资料分给第一个注册者会凭空制造归属，尤其可能把别人的资料交给 Alice。本课允许它们继续无归属，不提供公开认领接口。只有在**确定是单人隔离练习库**、明确备份并确认每个指定 ID 的来源后，才可另做一次性的本地处理；不要批量认领，不覆盖已有非空 ownerId。Git 保存代码，不会恢复数据库误删的资料。

## 创建资料时，由服务端决定它属于谁

`POST /api/resources` 已经验证 Session。本节把 `session.user.id` 写入新 Resource 的 `ownerId`。请求体仍只接受原有标题、简介和分类；若额外提供 `ownerId`、`userId` 或关系字段，直接返回 400。即使 Alice 把 Bob 的 ID 填进请求体，也不能借此创建 Bob 的资料。原有长度、空值、分类校验和 HTTP 201 响应继续保留。

## 读取资料时，只查询当前用户的记录

关键查询形状是 `prisma.resource.findMany({ where: { ownerId: session.user.id }, ... })`。这里不是把完整集合发到浏览器后再过滤。Alice GET 只返回 Alice 的新资料，Bob GET 只返回 Bob 的；旧 `ownerId=null` 不匹配任一用户。页面“本地示例资料（只读）”来自 Stage 1 静态文件，不属于任一账号的数据库资料，数量与个人列表要分开。

## 不能靠隐藏按钮实现数据隔离

Bob 的界面不显示 Alice 卡片，只能证明 GET 的结果看起来正确。Bob 仍能猜到或从别处知道 Alice 的真实数字 ID，然后直接发送 `PATCH /api/resources/[id]` 或 `DELETE /api/resources/[id]`。因此修改和删除的**数据库操作本身**必须同时限制目标 ID 与当前 `ownerId`。前端体验和服务端权限是两项分别验证的事情。

## 修改和删除，也必须检查归属

服务端应当让数据库在**同一次修改或删除中**核对“资料 ID 对不对、是否属于当前账号”。不符合任一条件就拒绝，不能先检查归属、再发一条不带归属限制的写入。不存在和他人的资料统一返回 404，避免向请求者透露别人是否有这条资料。非法 ID 是 400，未登录先是 401，其他数据库故障是 503。PATCH 不允许请求体更改归属，其他编辑校验不变。DELETE 仍要由页面先请用户确认。

:::deepdive{title="给 AI 的技术备注：归属条件与 P2025"}
Prisma 6 允许在带唯一 ID 的 `update`、`delete` 的 `where` 中增加非唯一 ownerId 条件，例如 `where: { id, ownerId: session.user.id }`。这让检查与写入成为同一次受约束的操作。P2025 是 Prisma 在这里表示“没有找到符合写入条件的记录”的错误编号；统一映射成 404，不区分不存在与他人资料。不要吞掉其他数据库故障，也不能改成先查后无条件写入。
:::

:::prompt{title="第三段：把归属写进修改和删除条件"}

```text

```

3. 普通窗口先开 Network，点 Alice 的“重新读取”；趁它 Pending 立刻退出并登录已有 Bob。记录是否在旧请求结束前已切到 Bob；动作超过 10 秒就没有测到竞态，回 normal 读稳后再试。不要通过刷新整页代替组件中的退出／登录。
4. **成功标志：切到 Bob 的当下清掉 Alice 卡片、草稿和提示；等旧请求结束或被取消，Bob 仍只见自己的列表。** 取消旧请求可在 Network 显示 cancelled／Failed，属于允许的保护结果；不能让迟到的 Alice 200 覆盖 Bob。若旧请求结束时登录还没切完，写“未测到晚响应”，不能勾选此项。

恢复：终端 B Ctrl+C，启动 `node scripts/fault-proxy.mjs normal`，确认 GET 200；停止 B 和 A，关闭实验窗口，副本终端 `cd ../..` 回日常项目运行 `npm run dev`，重新登录核对原资料。副本配置不复制回日常项目。准备拒绝目录／迁移或端口冲突时按 2.7 排障，不删除旧目录、取消 ownership 或改接口追求通过。

## 再检查一次数据库与页面

核对迁移前的每条旧记录仍在且 ownerId=null，Alice/Bob 新记录各有非空 ownerId。未登录四种资料 API 均为 401；已登录者只能操作自己；不存在与他人 ID 都为 404；故障不暴露连接凭证。

浏览器会自动带上 Cookie，这很方便，也需要防止其他网站诱导你的浏览器借登录状态执行写操作。这类攻击叫 **CSRF（跨站请求伪造）**。`Origin` 说明请求来自哪个网站；`Fetch Metadata` 是浏览器附带的来源关系信息，其中 `Sec-Fetch-Site` 表示请求网站与目标网站的关系。它们帮助服务端拒绝异常来源，不能代替 Session 身份和 ownerId 权限检查。**SameSite=Lax 本身不等于完整 CSRF 防护**：仍要检查写接口的 Origin / Fetch Metadata 同源限制，让跨来源请求被拒绝。完整生产安全复核留给 2.8 的部署门槛。

重新检查静态九条示例、搜索、筛选、统计与自选功能；它们不应因为个人数据库列表为空而消失。再确认浏览器刷新后仍能识别会话，但不会短暂显示前一账号状态。

:::check{title="把页面和数据库两端的证据对齐"}

- 两个独立账号各自 GET 只见自己的资料；旧无归属记录在数据库而不在普通列表。
- 同浏览器 Alice→退出→Bob 后，不出现 Alice 的卡片、编辑草稿或成功提示；延迟的旧 GET 不能覆盖 Bob。
- 静态示例仍只读，Stage 1 原有交互正常；同源写入可用，异常来源被拒绝。

:::

## 保存自己的安全版本

先看 Git diff 与迁移 SQL。修改应集中在 Resource 关系、增量 migration、四个资料接口和现有管理组件；必要的同源写入检查可以放在小 helper 中。确认没有覆盖自己的旧页面或引入与本课无关的功能。按自己的项目流程保存可恢复的代码版本；**Git 不会自动备份数据库**，迁移前后的数据库核对与备份仍是独立工作。

## 卡住了怎么办

:::stuck{title="Migration 提示无法新增必填字段"}

检查 schema 是否误写为 `ownerId Int`。已有旧记录无法凭空填必填值，改为 `Int?`，先审 SQL，再做增量迁移；不要 reset 或删除旧表。

:::

:::stuck{title="原来的资料突然在页面消失"}

先在数据库按原 ID 查询；若 ownerId=null 且内容仍在，这是个人 GET 排除了无归属旧资料。不要为了让页面变满而自动认领，先确认使用的是正确的隔离 schema。

:::

:::stuck{title="AI 把所有旧资料分配给 Alice"}

暂停应用这段迁移或数据脚本。检查是否有无条件 UPDATE Resource；保留可空字段并移除自动赋值，已运行时先根据备份逐条核对，不能猜测恢复。

:::

:::stuck{title="GET 仍然返回全部记录"}

在服务端检查 `findMany` 的 `where.ownerId` 是否来自有效 Session。浏览器 `filter` 不算修复；用 Alice/Bob 两套 Cookie 直接请求 API。

:::

:::stuck{title="Bob 看到了 Alice 的资料"}

先比对两套 Cookie 是否真的独立，`/api/auth/me` 是否显示不同用户 ID。再查 Alice 记录的 ownerId 和 GET 查询条件；不要删除 Alice 的记录来掩盖问题。

:::

:::stuck{title="Bob 猜到 Alice 的 ID 后能修改"}

检查 PATCH 的 Prisma `update.where` 是否同时有 `id` 和当前 Session 的 `ownerId`，以及是否存在只按 ID 更新的另一条路径。复测前后数据库标题与内容。

:::

:::stuck{title="Bob 能删除 Alice 的记录"}

检查 DELETE 的 `delete.where` 是否同样带 ownerId；前端不显示按钮并不能保护接口。若记录已经误删，不要误以为 Git 能恢复数据库，用实际数据库备份处理。

:::

:::stuck{title="POST 接受前端传入的 ownerId"}

在 JSON 校验阶段拒绝 ownerId/userId/owner，并只把 Session 的 user.id 写入 create.data。用 Bob 的 ID 伪造请求，确认没有创建新记录。

:::

:::stuck{title="已登录但 GET 一直返回空数组"}

先查 `/api/auth/me` 的用户 ID，再查新记录的 ownerId。若只有迁移前 ownerId=null 的旧数据，空列表是预期结果；亲手创建一条新资料再复测。

:::

:::stuck{title="退出后旧资料还在页面"}

检查 logout 成功后是否立刻清空 resources、editDraft、preview 和状态提示，并隐藏个人管理区。直接用旧 Cookie 调 GET 还应是 401。

:::

:::stuck{title="Bob 登录后短暂显示 Alice 的资料"}

这是旧 GET 的竞态。切换账号时中止未结束请求，并递增账号代次；处理每个响应前核对代次，延迟 Alice 响应后再观察 Bob 页面。

:::

:::stuck{title="数据库连接失败"}

核对专用练习库的连接、服务状态、schema 和迁移状态；503 不应含 DATABASE_URL。先恢复连接再复测，不使用 reset 消除报错。

:::

:::stuck{title="Stage 1 静态资料被改坏"}

对照 Git diff 找到被覆盖的静态文件或筛选组件，只撤回误改路径，保留本课 Resource 迁移与 API。静态九条与个人数据库列表应分开计数。

:::

:::stuck{title="以为 Git 能恢复数据库中的删除操作"}

Git 管理的是代码和迁移文件，不保存当前数据库每一行。先停止写入、检查数据库备份或快照；不要再运行删除或 reset。下次迁移前先记录数据并备份。

:::
