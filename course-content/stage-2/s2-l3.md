2.1，你只在浏览器里预览资料。2.2，浏览器真的向 `/api/resources` 发出 POST，Next.js 服务端检查并回答 `saved: false`。现在刷新页面，刚才的资料依然不在正式列表，因为服务端还没有把它写到长期存储。这节才让它留下来。

继续使用**你完成 2.2 的同一个项目**。不要重下 Starter，也不要用示例 `app/page.tsx` 覆盖自己的页面。你的输入组件、排序或清除筛选、原始资料和个人标题都要保留。只用非敏感测试内容；没有账号与所有权检查的匿名写入接口，仅在受控本地环境运行，不作为公开应用部署。

## 服务端收到了，为什么刷新后还是没有？

2.2 的服务端把输入检查一遍就回了 JSON；它没有记录下一次请求还能查到的资料。页面里的 React 状态也会随刷新消失。我们需要让服务端写入数据库，再通过**另一次 GET 请求**读回来。是否保存成功，以数据库写入结果和重新读取为准，不能只看按钮变绿。

## 第一次认识 PostgreSQL 和 Prisma

### 数据库负责留下什么

**PostgreSQL** 是这次真正保存资料的数据库。资料写入后，关闭浏览器、刷新页面或重启 Next.js，数据库里的记录仍可被下一次请求查询。**持久化**说的就是这种跨请求、跨页面运行时间的保存。

### Prisma 在中间做什么

**Prisma** 让服务端用代码创建和查询资料。`schema.prisma` 描述资料字段，Migration（迁移）把这个定义应用到实际数据库，Prisma Client 是服务端调用数据库的代码入口。这三个动作分开：写好模型不等于建好表，迁移成功也不等于页面已经能读到资料。

:::concept{title="这节真正的数据路径"}

```text
当前表单 → POST /api/resources → 服务端校验 → Prisma 写入 PostgreSQL
                                                   ↓
数据库资料展示区 ← GET /api/resources ← Prisma 从 PostgreSQL 读取
```

原始 9 条示例资料暂时仍来自原文件。它们不自动进入数据库；你的项目若已改过示例数量，以自己的原始数量为准。

:::

## 第一次定义资料的数据结构

打开实际的 `prisma/schema.prisma`。一条 `Resource` 至少有：`id`（数据库生成的唯一标识）、`title`（标题）、`desc`（简介）、`tag`（现有分类）、`important`（默认 `false`）、`createdAt` 和 `updatedAt`。这里先保存“是否重要”字段，为以后整合列表留好结构；本节不增加编辑重要状态的按钮。

不必逐行背 Prisma 语法。你要能指出：哪些字段来自表单，哪些由数据库或 Prisma 自动生成。不要把浏览器自己编的随机 ID 当成数据库记录 ID，也不要现在引入用户归属字段和复杂关联。

## 让数据库真正创建资料表

确认目标是专用练习库后，运行迁移（例如 `npx prisma migrate dev --name init_resource`），再确认 `npx prisma generate` 能生成 Client。迁移文件应留在 `prisma/migrations/` 并纳入 Git，`.env` 则必须留在 Git 之外。迁移成功后，用数据库工具或只读 Prisma 查询核对 `Resource` 表存在、目前为空；不要为了“有数据”先把原始九条资料导进去。

如果服务商限制创建 shadow database，先读**具体错误**、核对当前账号权限和 [Prisma 对 shadow database 的说明](https://www.prisma.io/docs/orm/prisma-migrate/understanding-prisma-migrate/shadow-database)。不要尝试删除现有数据库。可以让 AI 评估在隔离练习库中配置单独的 shadow 目标，或改用你已有的本地 PostgreSQL；不同服务商权限不同。Neon 的 [Prisma 迁移说明](https://neon.com/blog/better-postgres-with-prisma-experience)介绍了其连接与迁移支持，但仍以你的实际迁移结果为准。

## 把上一节的 POST 接到数据库

### 这次才是真正的保存

继续改**已有的** `app/api/resources/route.ts`。保留 2.2 的 JSON 格式、字段类型、空白、长度和真实分类检查；“全部”仍不能作为资料分类。检查通过后，服务端调用 Prisma 创建一条记录。只有数据库实际创建成功，才返回 HTTP `201`、`status: "saved"`、`saved: true`、数据库返回的 `id`、标题、简介、分类、`important` 和实际创建时间。`updatedAt` 若实现也返回，应与模型一致。

### 保存失败不能假装成功

数据库无法连接或写入失败，应返回 503 或合适的 500 JSON，页面不显示 `saved:true`，浏览器也不收到数据库密码。服务端可以记录错误类别用于本地排查，不把完整连接地址发给页面。不要在 `catch` 里造一个假 ID，也不要把资料先塞进模块级数组再称为数据库保存。

:::prompt{title="第二段：升级真实 POST 并增加 GET"}

```text

把 POST 改为：校验通过才用 Prisma 写入 Resource；数据库成功后返回 HTTP 201、ok:true、status:"saved"、saved:true、实际数据库记录及“资料已保存到数据库。”。数据库失败返回明确的 500/503 JSON，不输出密码，也不伪造保存成功。错误输入仍为 400，不写库。
在同一 Route Handler 增加 GET /api/resources，按创建时间倒序从 PostgreSQL 真正读取，返回 {ok:true,resources:[...]}，避免缓存旧列表。不要读取 resources.ts 冒充数据库。
先用真实 HTTP 请求分别验证：初始 GET、合法 POST、随后 GET、空标题和坏标签；用只读数据库查询核对 ID 与数量。此阶段先不要修改页面，也不要把原始资料导入数据库。报告真实状态码和字段，不输出 DATABASE_URL。
```

## 再建一条 GET：把资料读回来

`GET /api/resources` 每次从 PostgreSQL 读取，例如按 `createdAt` 倒序，成功返回 `{ "ok": true, "resources": [...] }`；空库就返回空数组。它不能读取 `resources.ts`、localStorage 或页面状态冒充数据库。请求和响应都不要缓存成旧结果。

先不改页面：让 AI 用适合你系统的命令向本地 API 发一次完整 JSON，再调用 GET，给你看**实际响应**。Windows PowerShell 可以先用 `@{title="测试";desc="第一次写库";tag="文章"} | ConvertTo-Json` 生成请求体，再用 `Invoke-RestMethod` 发到本机地址；端口以开发服务器显示的为准。确认 POST 的 `id` 与 GET 中同一条记录一致，再继续前端。重复调用 GET 不应额外创建记录。

## 亲自验证：刷新以后还在不在？

:::task{title="保存一条，再用新请求读回来"}

在自己的受控练习库里填入一条非敏感资料，按下面步骤保留 POST、GET、数据库查询和重启后的实际结果。每一步都看同一记录的 ID；若失败，先查清当前结果，不连续点击保存。

:::

1. 在新区域查看初始 GET；空库应显示没有数据库资料。填一条非敏感测试资料并点保存，核对 HTTP 201、`saved:true` 和真实 ID。
2. 另发 GET，确认同一 ID、标题、简介与分类存在；直接查询数据库中的记录数，再与 GET 对照。重复 GET 两次，数量不应增加。
3. 刷新页面：输入框可清空，但数据库展示区应再次 GET 并显示已保存资料。关闭页面重开，再看一次。
4. 停止 **Next.js 开发服务器**，再启动同一个项目；重新打开页面和 GET，确认记录还在。重启页面服务不是删除数据库。
5. 直接向 API 发空标题、空简介、坏分类和错误类型，确认 400 且数据库记录数不增加。
6. 在受控测试环境模拟数据库连接失败，GET/POST 都应报错；页面不能显示新保存成功。恢复连接后重新读取，确认失败请求没有偷偷写入。

### 在 Network 里核对真实链路

打开浏览器开发工具的 Network（网络）面板。保存时找 `/api/resources` 的 `POST`，核对 Request Payload 与当前输入一致、Response 为 `201` 和 `saved:true`、记录 ID 来自服务端；随后找 `GET`，核对 Response 中有同一 ID。刷新后应该再出现 GET，而不是仅从旧 React 状态恢复。若工具无法打开 Network，可用服务端请求日志、真实 HTTP 调用和页面结果交叉检查，并诚实记录未直接检查的部分。

### 数据库出问题时会怎样

不要为了实验故障停掉他人正在用的数据库。可以在**专用练习项目**暂时配置一个不可用的本地测试端口并重启开发服务器，观察 GET/POST 失败，随后恢复本地 `.env`；不要泄漏原连接地址，不对正式库做破坏性操作。保存失败后先恢复连接、单独 GET 核对，再决定是否重新 POST，避免网络边界不明时重复创建。

:::check{title="证明保存的四层证据"}

- POST Response 是 201、`saved:true`，ID 是服务端实际返回的数据库记录 ID
- GET、只读数据库查询、刷新后的页面指向同一条记录
- 重启 Next.js 后 GET 仍能读到；重复 GET 不新增记录
- 输入错误和数据库连接失败都没有假成功，也没有新增记录

:::

## 卡住了怎么办

:::stuck{title="按失败发生的位置排查"}

### 数据库服务无法连接

先看练习库控制台是否可用、主机与端口是否正确、当前网络是否允许连接；再用只读连接测试。区分“Next.js 没启动”和“Next.js 启动了但 Prisma 连不到库”。不要把完整地址贴进求助消息。

### DATABASE_URL 格式错误

确认根目录 `.env` 的键名正好是 `DATABASE_URL`，一行完整、没有多余空格或断行，连接类型为 PostgreSQL。只报告解析错误和非秘密主机信息，不让 AI 回显值。改完重启开发服务器和 Prisma 命令。

### 数据库账号或密码错误

在服务商控制台核对该练习库的账号和连接方式，必要时重新复制到本地 `.env`。不要通过浏览器表单、截图或聊天发送密码；已公开的凭证要在服务商处轮换。

### Prisma 安装后命令不可用

回到项目根目录，检查 `package.json` 中两个 Prisma 包版本及依赖安装结果，用 `npx prisma --version` 核对本项目 CLI。不要全局装一个不同主版本来绕过错误。

### Prisma Client 尚未生成

确认 schema 已保存、迁移目标正确，在项目根运行 `npx prisma generate`，然后重启 Next.js。若仍报导入错误，检查实际生成位置与服务端导入路径，不要在浏览器组件直接导入 Prisma Client。

### Migration 执行失败

先看错误代码与数据库目标，确认当前是专用练习库、schema 和迁移文件一致。不要用 reset、drop、清表或删迁移记录解决；请 AI 只读解释冲突后再决定最小修复。

### 服务商不允许创建 shadow database

确认报错是否指向 shadow 权限，而不是密码或网络。查服务商与 Prisma 官方说明，考虑专门的隔离 shadow 目标或已有本地 PostgreSQL；不要拿日常业务库当 shadow，也不要给不可信的数据库账号扩大权限。

### POST 返回成功但 GET 查不到

核对 POST 的 `id`、GET Response、两个请求实际使用的 `DATABASE_URL` 目标与 schema，以及 GET 是否仍读静态资料或缓存。不要先再点一次保存；用只读数据库查询确认记录到底在不在。

### 数据库实际保存了，但页面没有更新

先单独调用 GET 确认记录，再看页面是否在 POST 成功后调用 GET、是否读取这次 JSON、是否把列表错误单独显示。点“重新读取”即可重查，不要重发 POST 制造重复资料。

### 刷新后新资料消失

区分输入框清空与数据库列表消失。检查刷新后的 GET 是否发出、是否 200、数据库查询是否仍有该 ID、是否意外换到了另一个库；不要用 localStorage 遮掩。

### AI 把地址放进 NEXT_PUBLIC_

停止运行与公开同步，检查代码和构建产物是否包含真实值。让 AI 只移除本轮误加的公开配置，改为服务端读取 `DATABASE_URL`；若值已公开，先在服务商处轮换。

### .env 出现在 Git 待提交文件中

先不要 commit。确认真实文件名与 `.gitignore` 的 `.env*` 规则，再检查它是否早已被 Git 跟踪或选入暂存区。只处理这个明确文件的跟踪状态；若曾推送，按泄漏处理并轮换凭证。

### AI 把原来的九条资料覆盖了

停下继续修改，比较 `lib/resources.ts`（或你项目的实际源文件）的本轮差异与旧版本，让 AI 仅修复本轮误改。重新核对原列表数量和自定义资料，不要整项目恢复覆盖其他工作。

### 数据库断开时仍显示保存成功

查看 POST 的实际状态码和 Response；若是 503/500，检查页面是否忽略 `response.ok` 或沿用上次成功状态。若仍是 201，检查 Route Handler 是否在 Prisma 写入完成前就返回，或在 `catch` 中伪造了成功。

### Stage 1 筛选或自选功能损坏

先比对原始资料列表与页面本轮差异，确认数据库展示区是否错误地混入旧列表计算。修复仅限本轮改动，再按原项目实际功能逐项测试搜索、标签、重要、统计和排序/清除筛选。

:::
