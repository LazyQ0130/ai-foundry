## 功能都做完了，为什么产品还是不好用？

打开你完成 2.6 的知识工作台。先自己想四个问题：数据库读取要三秒时，用户看到什么？刚注册、没有资料的 Bob 看到什么？标题只输入空格会怎样？保存时数据库突然不可用又会怎样？先观察现有页面和 Network，再动手修改。继续使用原项目、独立练习数据库和原有 A/B 自选功能，不要用参考文件覆盖自己的页面。

一条资料能正常保存，只证明顺利时的路径。真实用户还会等待、输错、断网、过期。页面需要说清当前知道什么，以及下一步能做什么。

## 用户操作以后，页面可能处于哪些状态？

本节只认识四个词：**Loading** 是请求还在等；**Empty** 是读取成功而数组为空；**Error** 是没有得到可用结果；**Validation** 是输入不符合要求。它们由真实请求和验证产生，不能用本地假资料或定时器伪造接口结果。

:::concept{title="最小状态表"}

读取：`idle → loading → ready / empty / error`。新增：`idle → saving → saved / error`。编辑与删除：`idle → busy → success / error`。表单可以另有输入提示。这些是思考真实流转的工具，不要求你的组件采用完全相同的 TypeScript 类型。

:::

## 第一次把等待做清楚

初次进入个人列表和手动重新读取，都应该在 GET 未结束时显示“正在读取”。若保留先前列表，必须说“以下是上一次结果，尚未验证为最新”。请求真正成功以后才更新记录数。不要在按钮刚点下去时先显示成功。

### 正在读取和正在保存不是一回事

GET 正在刷新，不代表 POST 还在保存；POST 正在保存，也不能被列表提示替代。保存、修改、删除各自要有等待文案，并阻止同一次操作的快速重复提交。操作结束后恢复按钮；账号切换时清理旧状态。检查有没有一个全局 busy 把无关操作也锁住。

:::prompt{title="第二段：完善真实 GET 状态"}

```text
只处理当前账号的 GET /api/resources。在 2.6 已验收的账号切换保护上补充状态反馈，不从头重写取消旧请求或响应归属机制。根据真实响应区分 idle、loading、ready、empty、error；初次读取、手动重新读取都要有提示。若保留旧列表，在等待或失败时明确标为上一次结果，不能当成新结果。GET 成功返回 [] 才显示个人资料为空；失败不能显示 Empty。保留重新读取按钮。401 清除私人列表、草稿及旧成功提示，显示重新登录入口；403 不解释成未登录，503 给稍后重试建议，网络中断给检查连接建议。保留服务端 ownerId 过滤，不改写入操作；先验收 GET 与账号切换，再报告实际结果。不操作 Git。
```

## 没有资料，不等于发生错误

给 Bob 注册一个专用练习账号。`GET /api/resources` 成功返回 `{ ok: true, resources: [] }`，页面应说“你还没有保存资料，可以从上面的表单新增第一条”。这不是数据库故障。Stage 1 的九条静态示例在另一块区域，不能拿它们判断 Bob 的个人数据库是否为空。若 GET 返回 503 或网络断开，浏览器根本不知道列表是否为空。

:::check{title="读取的三种证据"}

- 延迟约两秒的真实 GET 期间看见 Loading，结束后看到数据库结果。
- 新账号 GET 成功且数组为空，出现 Empty，不出现 Error。
- 数据库读取故障时 GET 返回 503，出现 Error 和重新读取入口；恢复后再读能消除错误。

:::

## 输入不正确时，告诉用户怎么改

HTML 的 `required` 能挡空字符串，却会放过只含空格的标题。前端可在预览或保存前检查 `trim()` 后是否为空，显示“请填写资料标题”，并保留简介和分类。标题最长 100 字、简介最长 500 字、分类必须在已有标签中；PATCH 的 `important` 必须是布尔值。服务端 400 仍要验证并返回具体问题，因为直接 HTTP 请求可绕过前端。前端不要把服务端 400 统一改写成“网络故障”。

## 网络和数据库失败时怎么办？

GET 的网络失败建议检查连接后重新读取；503 建议检查数据库后再读；401 清理私人视图并重新登录；403 表示请求被拒绝，不能直接说成未登录；404 表示这条资料不存在或当前账号无权访问。页面只呈现可读消息，不展示数据库连接串、密码、Session Token 或服务端异常堆栈。API 本身也不能返回这些秘密。

### 错误以后能不能重新尝试？

读取 GET 通常可以由用户重新发起。对 POST、PATCH、DELETE，要先判断上次是否可能已经生效。自动重试写入可能创建两条、重复修改或重复删除。重新读取列表是**核对结果**，不是重发写入。

## 保存成功，但列表读取失败了

一次保存包含两个请求：POST 创建记录，随后 GET 更新页面列表。POST 返回 201 和真实记录，就能确认保存；GET 失败只能说明列表没刷新。页面可以同时显示“资料已保存”和“读取列表失败，请重新读取”。不要把已确认的保存改写成失败，也不要再次 POST。用隔离测试项目让 POST 正常写入而 GET 返回 503，再直接查数据库。

## 最需要小心的一种情况：结果尚未确认

另一种情况是 POST 已写入数据库，但响应在回到浏览器前丢失。浏览器 `fetch` 报网络异常，无法判定数据库有没有新增。提示“尚未确认本次操作结果，请先重新读取资料列表，确认是否已经保存”，让用户核对；核对成功前暂时禁用同类写入，不自动重发 POST。PATCH、DELETE 的响应丢失也按同样原则处理。

:::concept{title="术语预告：幂等（4.6 的写入确认中再学习）"}
幂等可以先理解成“同一个业务动作重复请求，结果仍只发生一次”。现在不用记“幂等键”的实现；本课先做到结果未知时重新读取核对、不自动重发。4.6 才会给 Agent 的同一确认动作建立数据库约束；那不是给本课所有 HTTP 写入自动加上保证。
:::

:::task{title="理解核对：写入结果尚未确认"}
先用自己的话回答，拿不准再展开答案。

1. 点击保存后断网，没收到响应。为什么先核对结果，而不是立刻再保存一次？
2. 保存已明确成功，之后列表刷新失败。页面应分别说明哪两件事？
:::

:::deepdive{title="核对答案：写入结果尚未确认"}

1. 因为服务端可能已写入，只是响应没回来。此时结果尚未确认，恢复后先只读核对，避免重复创建。
2. 说明“已保存”和“列表刷新失败”。提供重新读取，不能说成保存失败、让用户再提交。
:::

:::task{title="迁移练习：三份报告，哪份能下结论？"}
先判断各自能证明什么，再让 AI 解释拿不准的地方：

1. AI 报告“保存成功”，没有请求或数据库证据。
2. POST 返回 201 和记录 ID，随后 GET 返回 503。
3. POST 发生网络异常；恢复后 GET 和只读数据库查询都发现同一条新资料。

哪份可以声称“页面列表已刷新”？哪份足以说明资料已保存？如果此时提供“一键重发 POST”，会有什么风险？
:::

:::deepdive{title="核对答案：把保存、显示和请求次数分开"}
三份都不能声称页面列表已成功刷新。1 没有足够证据；2 能证明保存，不能证明随后的读取；3 核对同一条新资料后，可以说明已经保存，但还要实际刷新页面确认显示。一键重发可能再建一条；4.6 将进一步用同 Action 的数据库约束保证重复确认只产生一条业务结果。
:::

## 登录过期以后，私人数据不能继续显示

用专用测试 Session 触发 GET 401：清空旧个人列表、编辑草稿和旧成功提示，显示登录入口，不把它解释为 Empty。Alice 退出后 Bob 登录，继续用 2.6 的延迟请求实验复验：Alice 的慢 GET 不能覆盖 Bob 的结果。本节只补充过期、错误与恢复反馈，沿用已通过的账号切换保护；客户端隐藏卡片只是体验，服务端按 `ownerId` 查询和写入的限制仍必须存在。下面的 Session 实验也可以在本节的隔离副本进行，配置和命令都要放在同一个副本中。

### 3. 每次只开一种故障，按真实证据验收

在[Network](/environment#network)中先开始记录，再点按钮。每次切换下表模式都在**终端 B 按 Ctrl+C**，等命令结束，再输入新命令；终端 A 不停，页面账号也不重新登录。代理故障只影响副本入口，启动 normal 即恢复。所有命令在副本目录执行。

| 实验 | 终端 B 命令与浏览器操作 | 成功标志／恢复 |
| --- | --- | --- |
| Loading | `node scripts/fault-proxy.mjs slow-get`；Alice 点重新读取 | 真实 GET 响应在代理中延迟两秒，Network 为 Pending，页面显示 Loading／旧列表未刷新；随后 HTTP 200 和真实列表。Ctrl+C 后启动 normal 恢复 |
| 快速重复保存 | `node scripts/fault-proxy.mjs slow-write`；输入唯一标题 `fault-double-01`，快速点两次保存 | 真实写入响应延迟两秒，按钮等待；Network 只有一个 POST 201；下方数据库 count 为 1。恢复 normal 后重新读取仍只有一条 |
| POST 成功、GET 失败 | `node scripts/fault-proxy.mjs read-fail-after-write`；Alice 保存唯一标题 `fault-read-01` | POST 真实 201 后，后续 GET 被代理注入 503；页面分别保留保存成功与读取失败，不再次 POST。count 为 1。恢复 normal 后点重新读取，GET 200、资料出现、读取错误消除 |
| 写入响应丢失 | `node scripts/fault-proxy.mjs lose-write-response`；Alice 保存唯一标题 `fault-lost-01` | 应用实际写入成功后，代理仅将第一次成功写响应的正文截断；Network 可能已有 201 响应头，但正文传输失败、JSON 不完整。页面说结果尚未确认，不能说一定没保存，也不能自动重发。count 为 1；先点重新读取核对该条，再恢复 normal，不再保存同一条 |

代理日志中的 `FACT POST … HTTP 201` 是它收到的应用响应，不代表浏览器收到了完整、可验证的成功结果；丢失实验先返回响应头再中断正文，避免直接断连接引发浏览器自动重发 POST。“注入 503”也不等于真的断开数据库。下面另做真实数据库故障。每次用**新的唯一标题**，否则 count 会混入上次留下的资料。

另开终端 C，也 `cd` 到副本目录，分别核对实际数据库记录，不能只看页面文案：

```bash
node scripts/fault-project.mjs count fault-double-01
```

把最后的标题换成对应实验标题。**成功标志：`FACT matching-title: 1` 和一条真实 ID。** 显示 0 或 2 都是本项未通过，保留证据修页面，不删记录凑成 1。工具不打印内容、Cookie 或密码。

### 4. 真实数据库故障与恢复：只动副本的一张表

先让终端 B 恢复 `node scripts/fault-proxy.mjs normal`，Alice 登录状态正常且基线列表已读到。终端 C 运行：

```bash
node scripts/fault-project.mjs db-break
```

**成功标志：`PASS db-break`。** 工具核对副本标记和随机 schema，将它的 `Resource` 表临时改名为 `Resource_fault_hold`；这是让真实数据库查询找不到表，不是删除资料，也不是关掉整个数据库。User／Session 表保持可用。Alice 点击重新读取：**GET 真实返回 503，页面显示 Error 与重新读取入口；旧列表若保留，须标记未刷新，不能显示 Empty 或刷新成功。** Response 不应带连接串、密码或数据库异常堆栈。

无论页面检查是否通过，都立即在终端 C 恢复：

```bash
node scripts/fault-project.mjs db-restore
```

**成功标志：`PASS db-restore`；再点重新读取得到 GET 200，原资料仍在，错误消除。** 命令重复运行也能保持已恢复状态。如果中途关了窗口，重新打开终端、cd 到副本，先运行 db-restore 再继续；不要建一张空表代替原表，不改日常连接。会话过期的 401 按前面专用账号步骤单独验收，不能把 503 当作未登录。

### 5. 退出实验，回到日常项目

先确认 db-restore 成功。在终端 B、A 分别 Ctrl+C 停代理和副本 dev，关闭 localhost:3007 的实验页面。终端 C 从副本运行：

```bash
cd ../..
```

```bash
npm run dev
```

确认已回到日常项目的 `package.json`，按新打印的 Local 地址重新登录日常账号。**成功标志：原个人资料仍在、CRUD 正常、没有故障注入。** 副本和测试 schema 留作证据，不删除目录、表或原资料。若在副本修了页面，只将确认过的业务代码差异请 AI 合回原项目，再在原项目复验；不复制副本 `.env`、`.fault-demo.json` 或依赖。本工具无需改正式 Route，所以停代理并恢复表即可撤掉故障。

:::stuck{title="副本不能启动、一直 503 或恢复后仍出错"}
`THREE_MIGRATIONS_REQUIRED` 先确认已完成 2.6 且在 Stage 2 项目，别增删迁移凑数。`PRISMA_CLIENT_REQUIRED` 先在原项目 `npx prisma generate`，完成后再准备副本。`SINGLE_SCHEMA_REQUIRED`／`SCHEMA_QUALIFIED_MIGRATION_REFUSED` 表示项目不是本课单 schema 结构或迁移写死了其他 schema；停止演示，让 AI 只读解释差异，不能去掉保护或随意重写已应用的迁移。`ISOLATED_DEMO_REQUIRED` 核对当前目录、标记文件和副本 schema；不要移除保护。`DEMO_PORT_BUSY`／3008 被占用时先停自己上次的代理／副本，不能随意停其他项目；两个端口必须都空闲再开始。代理 502 表示连不到副本，检查终端 A Ready；数据库 503 则先 db-restore、核对副本配置和三次迁移。POST 403 检查是否全程使用 localhost:3007、是否跑错副本或 Origin 不一致，不关同源检查。恢复后 401 要重新登录副本账号；如果日常项目也掉登录，重新登录日常账号即可，Cookie 按主机共享而不按端口隔离。`DEMO_TABLE_STATE_INVALID` 让 AI 只读查看指定 schema 的两张表名，停止改表，不删除或 reset。副本代码是创建时的快照，原项目后续修改不会自动同步。
:::

在 A/B 两个独立 schema 上用各自账号测试，先记下原有记录，不删除旧资料。你只选了一条课程路线，就先验收自己的路线；若维护 A/B 两份项目，各自在自己的根目录准备副本，顺序运行，不能共用同一副本。

## 卡住了怎么办

:::stuck{title="Loading 一直不结束"}

在 Network 看 GET 是否仍 Pending、被中止或卡在服务端；检查 `finally`、请求代次和实际数据库连接。不要靠固定定时器强行切成成功。

:::

:::stuck{title="GET 返回空数组却显示错误"}

核对 HTTP 是否为 200、JSON 是否有 `resources: []`；只有有效响应才进 Empty，检查是否错误地把长度 0 当失败。

:::

:::stuck{title="GET 失败却显示还没有资料"}

检查是否把 `resources.length === 0` 直接用作 Empty；先判断本次 GET 是否成功，再显示空状态。

:::

:::stuck{title="连续点击后多了两条相同资料"}

在 Network 数 POST 次数，并在数据库按本次标题查新记录；在发请求前同步锁住同一次保存，不要只依赖按钮渲染后的 disabled。

:::

:::stuck{title="空格标题也保存成功"}

检查前端是否只用了 `required`；检查服务端是否在验证前 `trim()`，用直接 HTTP 再测 400。

:::

:::stuck{title="数据库故障时页面仍显示成功"}

对照 Network 的 POST/PATCH/DELETE 状态码；只有确认成功响应才显示成功，旧成功提示应在下一次操作开始时清掉。

:::

:::stuck{title="保存成功后列表刷新失败"}

核对 POST 是否已返回 201，再看 GET 的失败码；保留保存事实，只让列表显示错误和重新读取入口，不重新 POST。

:::

:::stuck{title="不知道上一次 POST 是否已经写入"}

先停止继续点击，用 GET 或数据库查询核对本次标题、ID 和时间；响应丢失不能当成明确失败，更不能自动重发。

:::

:::stuck{title="编辑失败后输入内容丢失"}

查看 PATCH 是否真的返回成功；仅成功才关闭编辑框，400/503 时保留编辑草稿和具体错误。

:::

:::stuck{title="删除失败但卡片先消失"}

确认删除卡片的条件来自成功响应和重新读取；503/网络异常时保留卡片并提示先核对，不做乐观删除。

:::

:::stuck{title="登录过期后仍看到以前的资料"}

检查 GET 的 401 分支是否清空资源、草稿、预览和旧成功提示，再切换到登录入口；不要把旧列表保留为匿名视图。

:::

:::stuck{title="重新读取后出现上一账号资料"}

检查 Alice 退出时是否中止 GET、递增请求代次；每个响应更新页面前核对代次，Bob 的请求不能被 Alice 的晚响应覆盖。

:::

:::stuck{title="恢复网络后旧错误不消失"}

重新读取开始时切 Loading，GET 成功后按非空/空列表切 Ready/Empty；检查是否只追加错误文案而未替换状态。

:::

:::stuck{title="改状态以后静态筛选坏了"}

比较 Stage 1 静态资源和过滤逻辑的 diff；撤回与本节无关的变更，单独验证搜索、标签、重要筛选、统计及自选功能。

:::
