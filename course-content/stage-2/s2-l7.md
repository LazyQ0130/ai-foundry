## 功能都做完了，为什么产品还是不好用？

打开你完成 2.6 的知识工作台。先自己想四个问题：数据库读取要三秒时，用户看到什么？刚注册、没有资料的 Bob 看到什么？标题只输入空格会怎样？保存时数据库突然不可用又会怎样？先观察现有页面和 Network，再动手修改。继续使用原项目、独立练习数据库和原有 A/B 自选功能，不要用参考文件覆盖自己的页面。

一条资料能正常保存，只证明顺利时的路径。真实用户还会等待、输错、断网、过期。页面需要说清当前知道什么，以及下一步能做什么。

## 用户操作以后，页面可能处于哪些状态？

本节只认识四个词：**Loading** 是请求还在等；**Empty** 是读取成功而数组为空；**Error** 是没有得到可用结果；**Validation** 是输入不符合要求。它们由真实请求和验证产生，不能用本地假资料或定时器伪造接口结果。

:::concept{title="最小状态表"}

读取：`idle → loading → ready / empty / error`。新增：`idle → saving → saved / error`。编辑与删除：`idle → busy → success / error`。表单可以另有输入提示。这些是思考真实流转的工具，不要求你的组件采用完全相同的 TypeScript 类型。

:::

## 第一次把等待做清楚

初次进入个人列表和手动重新读取，都应该在 GET 未结束时显示“正在读取”。若保留先前列表，必须说“以下是上一次结果，尚未验证为最新”。请求真正成功以后才更新记录数。不要在按钮刚点下去时先显示成功。

### 正在读取和正在保存不是一回事

GET 正在刷新，不代表 POST 还在保存；POST 正在保存，也不能被列表提示替代。保存、修改、删除各自要有等待文案，并阻止同一次操作的快速重复提交。操作结束后恢复按钮；账号切换时清理旧状态。检查有没有一个全局 busy 把无关操作也锁住。

:::prompt{title="第二段：完善真实 GET 状态"}

```text
只处理当前账号的 GET /api/resources。根据真实响应区分 idle、loading、ready、empty、error；初次读取、手动重新读取都要有提示。若保留旧列表，在等待或失败时明确标为上一次结果，不能当成新结果。GET 成功返回 [] 才显示个人资料为空；失败不能显示 Empty。保留重新读取按钮。401 清除私人列表、草稿及旧成功提示，显示重新登录入口；403 不解释成未登录，503 给稍后重试建议，网络中断给检查连接建议。保留 AbortController、请求代次和 ownerId 服务端过滤，不改写入操作；先验收 GET 与账号切换，再报告实际结果。不操作 Git。
```

:::

## 没有资料，不等于发生错误

给 Bob 注册一个专用练习账号。`GET /api/resources` 成功返回 `{ ok: true, resources: [] }`，页面应说“你还没有保存资料，可以从上面的表单新增第一条”。这不是数据库故障。Stage 1 的九条静态示例在另一块区域，不能拿它们判断 Bob 的个人数据库是否为空。若 GET 返回 503 或网络断开，浏览器根本不知道列表是否为空。

:::check{title="读取的三种证据"}

- 延迟约两秒的真实 GET 期间看见 Loading，结束后看到数据库结果。
- 新账号 GET 成功且数组为空，出现 Empty，不出现 Error。
- 数据库连接故障时 GET 返回 503，出现 Error 和重新读取入口；恢复后再读能消除错误。

:::

## 输入不正确时，告诉用户怎么改

HTML 的 `required` 能挡空字符串，却会放过只含空格的标题。前端可在预览或保存前检查 `trim()` 后是否为空，显示“请填写资料标题”，并保留简介和分类。标题最长 100 字、简介最长 500 字、分类必须在已有标签中；PATCH 的 `important` 必须是布尔值。服务端 400 仍要验证并返回具体问题，因为直接 HTTP 请求可绕过前端。前端不要把服务端 400 统一改写成“网络故障”。

## 网络和数据库失败时怎么办？

GET 的网络失败建议检查连接后重新读取；503 建议检查数据库后再读；401 清理私人视图并重新登录；403 表示请求被拒绝，不能直接说成未登录；404 表示这条资料不存在或当前账号无权访问。页面只呈现可读消息，不展示数据库连接串、密码、Session Token 或服务端异常堆栈。API 本身也不能返回这些秘密。

### 错误以后能不能重新尝试？

读取 GET 通常可以由用户重新发起。对 POST、PATCH、DELETE，要先判断上次是否可能已经生效。自动重试写入可能创建两条、重复修改或重复删除。重新读取列表是**核对结果**，不是重发写入。

:::prompt{title="第三段：验证输入并完善写入反馈"}

```text
在我当前组件中完善 POST、PATCH、DELETE：点击后立即显示各自等待状态，同次操作快速重复点击只能发一个请求；成功必须等待服务端可验证的响应。标题只含空格时明确提示，保留用户填写的其他字段；服务端 400 的具体错误要显示，服务端仍为最终验证方。显式 HTTP 401 要清除私人状态并请用户登录；403、404、503 保留各自含义。若写入响应丢失或无法判断结果，提示先重新读取核对，不自动重发 POST/PATCH/DELETE。POST 明确成功后若 GET 失败，同时保留“保存成功”和“列表读取失败”；编辑失败保留草稿，删除失败保留卡片。保留 ownerId 限制和原有静态功能。先验收再报告，不操作 Git。
```

:::

## 保存成功，但列表读取失败了

一次保存包含两个请求：POST 创建记录，随后 GET 更新页面列表。POST 返回 201 和真实记录，就能确认保存；GET 失败只能说明列表没刷新。页面可以同时显示“资料已保存”和“读取列表失败，请重新读取”。不要把已确认的保存改写成失败，也不要再次 POST。用隔离测试项目让 POST 正常写入而 GET 返回 503，再直接查数据库。

## 最需要小心的一种情况：结果尚未确认

另一种情况是 POST 已写入数据库，但响应在回到浏览器前丢失。浏览器 `fetch` 报网络异常，无法判定数据库有没有新增。提示“尚未确认本次操作结果，请先重新读取资料列表，确认是否已经保存”，让用户核对；核对成功前暂时禁用同类写入，不自动重发 POST。PATCH、DELETE 的响应丢失也按同样原则处理。本节不用设计幂等键。

## 登录过期以后，私人数据不能继续显示

用专用测试 Session 触发 GET 401：清空旧个人列表、编辑草稿和旧成功提示，显示登录入口，不把它解释为 Empty。Alice 退出后 Bob 登录，还要防止 Alice 的慢 GET 回来覆盖 Bob 的结果。保留上一节的请求代次与 `AbortController`。客户端隐藏卡片只是体验，服务端按 `ownerId` 查询和写入的限制仍必须存在。

## 亲自测试四种状态

在 A/B 两个独立 schema 上用各自账号测试，先记下原有记录，不删除旧资料。临时故障代码只放在隔离测试副本，验收后移除。不要用前端定时器冒充两秒网络延迟。

1. 延迟 GET 两秒，观察 Loading，结束后确认真实列表；新 Bob 的空数组显示 Empty。
2. 让隔离环境的数据库连接失效，确认 GET 503、错误提示和恢复后的重新读取；检查响应没有秘密。
3. 标题只填空格，确认前端提示且其他输入未丢；用直接 HTTP 发非法 tag、错误类型 `important`，确认服务端 400。
4. 延迟 POST 响应，快速点两次，直接查询仅新增一条；再让 POST 成功、随后 GET 失败，分别看到两条独立反馈。
5. 使专用 Session 过期，GET 401 后不见旧个人资料；模拟 Alice 慢请求再切 Bob，Bob 不出现 Alice 的资料或提示。
6. 再做一次真实 CRUD；Bob 无法 GET/PATCH/DELETE Alice 的资料。检查静态九条资料、搜索、筛选、统计及你的自选功能。

:::check{title="只凭页面文案还不够"}

- 对照浏览器 Network 的状态码、响应体，以及专用数据库中的真实记录。
- 测试故障注入已移出交付代码；`ownerId=null` 的旧资料仍在库中。
- A/B 的原自选功能和静态示例仍可用，没有新增与本节无关的依赖。

:::

## 下一节：把全栈产品真正交付出去

2.8 才会处理部署与交付。本节结束时，你应该能解释“还在等待”“确实为空”“请求出错”“输入需修改”各自有什么证据，以及写入结果未知时为什么先核对再行动。

## 卡住了怎么办

:::stuck{title="Loading 一直不结束"}

在 Network 看 GET 是否仍 Pending、被中止或卡在服务端；检查 `finally`、请求代次和实际数据库连接。不要靠固定定时器强行切成成功。

:::

:::stuck{title="GET 返回空数组却显示错误"}

核对 HTTP 是否为 200、JSON 是否有 `resources: []`；只有有效响应才进 Empty，检查是否错误地把长度 0 当失败。

:::

:::stuck{title="GET 失败却显示还没有资料"}

检查是否把 `resources.length === 0` 直接用作 Empty；先判断本次 GET 是否成功，再显示空状态。

:::

:::stuck{title="连续点击后多了两条相同资料"}

在 Network 数 POST 次数，并在数据库按本次标题查新记录；在发请求前同步锁住同一次保存，不要只依赖按钮渲染后的 disabled。

:::

:::stuck{title="空格标题也保存成功"}

检查前端是否只用了 `required`；检查服务端是否在验证前 `trim()`，用直接 HTTP 再测 400。

:::

:::stuck{title="数据库故障时页面仍显示成功"}

对照 Network 的 POST/PATCH/DELETE 状态码；只有确认成功响应才显示成功，旧成功提示应在下一次操作开始时清掉。

:::

:::stuck{title="保存成功后列表刷新失败"}

核对 POST 是否已返回 201，再看 GET 的失败码；保留保存事实，只让列表显示错误和重新读取入口，不重新 POST。

:::

:::stuck{title="不知道上一次 POST 是否已经写入"}

先停止继续点击，用 GET 或数据库查询核对本次标题、ID 和时间；响应丢失不能当成明确失败，更不能自动重发。

:::

:::stuck{title="编辑失败后输入内容丢失"}

查看 PATCH 是否真的返回成功；仅成功才关闭编辑框，400/503 时保留编辑草稿和具体错误。

:::

:::stuck{title="删除失败但卡片先消失"}

确认删除卡片的条件来自成功响应和重新读取；503/网络异常时保留卡片并提示先核对，不做乐观删除。

:::

:::stuck{title="登录过期后仍看到以前的资料"}

检查 GET 的 401 分支是否清空资源、草稿、预览和旧成功提示，再切换到登录入口；不要把旧列表保留为匿名视图。

:::

:::stuck{title="重新读取后出现上一账号资料"}

检查 Alice 退出时是否中止 GET、递增请求代次；每个响应更新页面前核对代次，Bob 的请求不能被 Alice 的晚响应覆盖。

:::

:::stuck{title="恢复网络后旧错误不消失"}

重新读取开始时切 Loading，GET 成功后按非空/空列表切 Ready/Empty；检查是否只追加错误文案而未替换状态。

:::

:::stuck{title="改状态以后静态筛选坏了"}

比较 Stage 1 静态资源和过滤逻辑的 diff；撤回与本节无关的变更，单独验证搜索、标签、重要筛选、统计及自选功能。

:::
