## 上线以后多了哪些东西？

GitHub 保存源码和迁移文件；Vercel 安装依赖、构建并运行 Next.js；独立的云 PostgreSQL 保存生产数据；浏览器通过 HTTPS 访问 Vercel。Deployment 显示 Ready 只说明某次构建和发布完成。页面能打开、数据库能连接、迁移成功、认证成功、资料 CRUD 成功和用户隔离成功，需要分别取证。

:::concept{title="交付链路"}

`GitHub → Vercel Build → Next.js Production → Prisma → Neon PostgreSQL`。浏览器从公开 HTTPS 地址发请求；Git 不保存生产数据库内容，也不能还原误删的云数据。

:::

## 准备真正的云 PostgreSQL

在 Neon 官方控制台为这份知识工作台建立一个**独立、空白**的 PostgreSQL 项目。不要连接 AIFoundry 平台业务库、个人其他生产库或先前本地练习 schema。只把 Neon 给出的连接信息填入 Vercel 项目的 **Production** 服务端环境变量 `DATABASE_URL`；不要贴到聊天、源码、README 或截图。保留本地 `.env` 给本地开发，确保它被 `.gitignore` 排除。首次生产迁移只建表，不搬运 Alice/Bob 本地账号、Session、旧 ID 或故障测试资料。

### 环境变量不是代码

应用在服务端通过 `process.env.DATABASE_URL` 和 Prisma 读取它。名字可以写进文档，真实值只放在受控环境里。不要创建 `NEXT_PUBLIC_DATABASE_URL`：`NEXT_PUBLIC_` 会把值带到浏览器构建。保存或修改 Vercel 环境变量后，检查它是否属于目标 Production deployment，并重新部署使新配置进入构建和运行环境。

### 本地数据库和生产数据库要分开

先记录本地和 Neon 项目的**名称**及用途，不记录连接串。Preview 若需要完整功能，应使用独立的 Neon 数据库或 branch；本课只给 Production 配置数据库。不要让 PR Preview 共享 Production 的写入库。检查 Vercel 中变量适用的环境，不能只看变量名相同。

## 让 migration 安全进入生产环境

项目已有三次迁移：Resource、User/Session、Resource.ownerId。保留 `prisma/migrations` 全部历史和当前 schema。Vercel 的构建命令应先 `prisma generate`，再 `prisma migrate deploy` 和 `prisma migrate status`，最后 `next build`。依赖安装后运行 `postinstall: prisma generate`，可避免构建缓存留下旧 Prisma Client。参考项目把普通本地 `build` 设为 `prisma generate && next build`，把 Vercel 的 Build Command 设为 `npm run vercel-build`，对应脚本执行 `prisma generate && prisma migrate deploy && prisma migrate status && next build`。运行前确认 Production 的 `DATABASE_URL` 指向新建的独立库。

不要在生产部署运行 `prisma migrate dev`、`prisma migrate reset`、`prisma db push` 或 `drop database`。部署后用受控环境运行 `prisma migrate status`，并通过 Neon 的只读查询核对 Resource、User、Session 表以及 `_prisma_migrations`。不要因为页面能打开就推断表已经存在。


## 把 GitHub 项目交给 Vercel

推送**知识工作台自己的仓库**，在 Vercel 导入这个 GitHub 项目，确认框架识别为 Next.js，设置 Production 的 `DATABASE_URL` 和 Build Command，再启动部署。界面按钮的位置可能变化，关键是核对项目仓库、环境范围与构建命令。不要在 GitHub 或 Vercel 日志里打印连接串。若官方界面要求账号登录、授权 GitHub 或创建云项目，由项目所有者亲自完成；不要把密码交给 AI。

## 第一次看部署日志

打开该次 Production deployment 的 Build Logs，按安装依赖、Prisma Client 生成、migration、Next build 的顺序找出实际停止处。Deployment Ready 后仍需查运行时日志与浏览器 Network。每次记录部署的 Git commit、时间和公开域名，避免把旧部署的结果算到新代码上。

### 部署失败时先判断是哪一层

安装失败先查锁文件与 Node 版本；`prisma: command not found` 查依赖是否安装；Client 未生成查 postinstall 与 generate 输出；`DATABASE_URL` 缺失查 Production 变量的作用环境；migration 失败查数据库目标、权限和实际错误；`next build` 失败查 TypeScript 与构建日志；首页正常而 API 500 则看运行时日志和数据库连接。不要遇到红色部署就重建项目。

## 打开第一个真正的 HTTPS 地址

复制 Vercel 的 Production URL，在全新浏览器会话打开首页。确认地址为 HTTPS，静态资料和 Stage 1 功能仍可用。用 Network 看真实 `/api/auth/me`、`/api/resources` 响应；不要把本地 `localhost` 的成功算成 Production。新库在注册前没有本地测试数据，首次个人列表的 Empty 应来自成功的空数组，不是失败请求。

## 在公网重新注册和登录

用专门的生产验收账号注册 Alice；确认 `POST /api/auth/register` 成功、`GET /api/auth/me` 返回 Alice，刷新页面后仍登录，然后退出并确认 `/me` 与资料 API 为 401。再登录一次。检查浏览器 Cookie 属性为 `HttpOnly`、`Secure`、`SameSite=Lax`、`Path=/`；不要复制 Cookie 值。若刷新就退出，检查 HTTPS、Cookie 的域名与 Path、Session 表以及服务端日志。生产会话证据必须来自公网。

## 把 CRUD 和用户隔离重新走一遍

Alice 的 GET 应先返回空数组；新增一条资料，记录返回的 ID；GET 重读、PATCH 修改、刷新确认、DELETE 测试记录，并按需要保留一条演示资料。用另一个独立浏览器会话注册 Bob：Bob 的 GET 不应出现 Alice 的资料；Bob 新增自己的资料后，Alice 也不应看到 Bob 的资料。Bob 猜 Alice 的 ID 发 PATCH 和 DELETE，均应得到 404，Alice 原资料仍在；反向也检查一次。不要只看客户端卡片隐藏，核对真实响应和数据库 ownerId。

## 检查失败状态和安全边界

在生产地址验证正常 Loading、成功空数组的 Empty、空格标题等 Validation 400、未登录 401、不存在或他人资料的 404。数据库故障的 503 已在 2.7 隔离环境测过，不要为了演示破坏生产连接或迁移。写入从正常 Vercel 页面发起应成功；伪造异常 Origin 的请求应被 403 拒绝。特别比较浏览器 Origin 与服务端识别的正式域名，不能通过删除同源保护来“修复”全部写入 403。响应与日志不应泄露连接串、密码哈希、Session Token 或堆栈。

通过 Neon 安全只读查询核对 Alice、Bob 的 Resource.ownerId 各等于本人 User.id，Session 属于正确用户、passwordHash 不是明文，且没有 `ownerId=null` 的本地历史资料被上传。查询时只记录结论与无秘密的计数，不复制哈希值或 Token。

## 卡住了怎么办

:::stuck{title="Vercel Build 失败"}

按 Build Logs 的最早失败步骤检查安装、generate、migration、Next build；记录本次 commit 与错误，不凭页面旧版本判断。

:::

:::stuck{title="prisma command not found"}

核对 package.json 中 Prisma CLI 所在依赖、实际安装日志和 Build Command；确认构建环境安装了该依赖后再重建，不先改数据库。

:::

:::stuck{title="Prisma Client 没有生成"}

看 postinstall 与显式 `prisma generate` 输出，核对 schema 路径和缓存；Client 类型或运行时代码仍旧时重新构建对应 commit。

:::

:::stuck{title="DATABASE_URL 未配置"}

检查 Vercel 变量名拼写、Production 作用环境与当前 deployment 创建时间；在官方界面补齐后重新部署，别把值贴进日志。

:::

:::stuck{title="生产 migration 失败"}

先确认目标是专用 Neon 库，再读 `migrate deploy` 的具体错误、权限和历史状态；不要 reset、db push 或手工补表。

:::

:::stuck{title="页面能打开但 API 500"}

比较首页与失败 API 的 Network，查该请求的 Vercel Runtime Logs；区分连接、迁移与应用异常，检查响应不含内部秘密。

:::

:::stuck{title="Neon 能连接但表不存在"}

对照实际数据库、schema 与 `_prisma_migrations`，在正确目标上运行已有 `migrate deploy`；不要手工创建 Resource、User 或 Session。

:::

:::stuck{title="注册成功但刷新掉登录"}

先看刷新后的 `/me` 状态，再查 HTTPS 下 Cookie 的 Secure、HttpOnly、域名、Path、有效期与 Session 记录；不复制 Token。

:::

:::stuck{title="生产页面写操作全部 403"}

在 Network 比较同页请求的 Origin、正式域名和响应；检查代理识别的 `request.nextUrl.origin` 与 Fetch Metadata，按实际域名修配置，不删除同源保护。

:::

:::stuck{title="本地正常，Vercel 数据库连接失败"}

核对 Vercel Production 变量作用范围、Neon 项目状态、连接方式和运行时日志；本地 `.env` 成功不代表云端有同一变量。

:::

:::stuck{title="Production 和 Preview 连到了同一个数据库"}

在 Vercel 核对各环境的变量目标，停止 Preview 的写入验证；为 Preview 使用独立库或 Neon branch，Production 保留原库。

:::

:::stuck{title="部署后还是看到本地测试数据"}

先确认浏览器是否仍在 localhost 或旧域名，再检查 Production 变量指向的数据库；停止写入，核对是否误用了本地或旧库，不删生产数据。

:::

:::stuck{title="Alice / Bob 在线隔离失败"}

分别核对两个会话的 `/me`、GET 响应、Resource.ownerId 与服务端 PATCH/DELETE 条件；先停止公开演示并修复越权路径，不能靠隐藏卡片。

:::

:::stuck{title="保存成功但刷新查不到"}

确认 POST 的真实响应与 ID，再看 GET 是否同一账号、同一 Production deployment、同一数据库；GET 失败与真正空列表要分开。

:::

:::stuck{title="环境变量保存后仍使用旧配置"}

检查变量的环境范围及当前 deployment 创建时间；新建 Production deployment 后核对日志和受控连接结果，不能用旧 deployment 取证。

:::

:::stuck{title="不小心把 .env 加到了 Git"}

停止推送，检查暂存和历史范围；从索引移除这个明确文件并轮换已经暴露的凭据，检查公开仓库是否曾收到它，不在报告中复制旧值。

:::

:::stuck{title="README 里放进真实连接串"}

停止发布，替换成变量名，检查已推送版本与部署日志并轮换凭据；只删除文档中的秘密不足以让泄露过的密码重新安全。

:::

:::stuck{title="GitHub push 后没有新的 Production deployment"}

检查 push 到的仓库和分支、Vercel 导入的 GitHub 项目、Production branch 与 Git 集成状态，再查看是否有失败或排队部署。

:::
