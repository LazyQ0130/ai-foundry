你现在的知识工作台能搜索、按标签和重要程度筛选，能显示当前结果数与总数，也有你自己加上的功能。今天如果发现一篇新文章，想把它放进工作台，你会怎么做？

目前通常要找到存放资料的源文件，修改数据，保存代码，页面才会出现新资料。真正给普通用户使用的产品，应让用户直接在网页里新增资料。本阶段要把**同一个**工作台逐步升级成有 API、数据库和账号的全栈产品。这一节先看清路径，并做一个能填写和预览的入口。

继续使用你完成 1.6 的项目，**不要重新下载第 0 课 Starter 覆盖它**。排序、清除筛选、个人资料与其他自选功能都应保留。Stage 2 可以单独购买；如果手里没有项目，可先到[免费的第 0 课](/lesson/stage-1/s1-l0)下载 Stage 1 Starter 并在本机跑起来。**Starter 只是起点，不等于完成 1.6 的最终项目，也不能下载后直接跳进 2.1。** 当前没有另一个 Stage 2 Starter 下载资源。

进入本课前，先用自己的项目做一次自检：资料列表、搜索、标签和重要筛选、当前数与总数都能实际操作；至少一个自己决定的功能可用；能找到真实资料文件与页面文件；能在本机启动、检查 Git 状态并找到可恢复的 commit。还要能解释浏览器页面与本机开发服务器的关系，并按 Stage 1 阶段自检实际验证这些功能。缺哪项就先补哪项；已有同等规模 Next.js 项目的学员也按同一标准检查，不必为了形式重做 Stage 1。

### 为什么新增资料还需要修改代码？

静态资料写在项目文件里。页面可以读取它、搜索它、筛选它，但用户在浏览器里没有一个把新资料长期写回去的通道。改源文件相当于开发者更新产品，并不是普通用户在使用产品时新增资料。

:::concept{title="现在的数据流"}

```text
resources.ts（或你项目里的实际资料文件）
    ↓
当前页面
    ↓
搜索 / 标签 / 重要筛选
    ↓
资料卡片
```

## 一个真正的新增操作，要经过哪些地方？

### 页面负责什么

**前端**就是用户看得见、能输入和操作的页面。标题、简介、标签的输入框以及预览结果属于前端。页面接住输入，只说明浏览器知道这段内容。

### 服务端和 API 负责什么

**API** 是前端向服务端提出请求的入口。**服务端**接收请求、检查数据，并执行不应该由浏览器直接处理的操作。下一节会创建 `POST /api/resources`，让页面第一次把资料交给 Next.js 服务端。**如果你当前项目没有这个接口，它现在还不存在；本节也不会创建。**

### 数据库负责什么

**数据库**长期保存资料，让之后的请求还查得到。Stage 2 会用 Prisma 和 PostgreSQL 完成这一步，安排在 2.3。此刻能在页面看到输入，既不能证明服务端收到，也不能证明数据库保存。

## 先把整个过程连起来

未来一次真实新增资料将经过：

```text
用户填写资料
      ↓
浏览器页面
      ↓
POST /api/resources（2.2 才创建）
      ↓
Next.js 服务端 → 数据检查
      ↓
PostgreSQL 数据库（2.3 才接入）
      ↓
返回结果 → 页面展示新资料
```

这是一张**目标图**，不是当前已实现清单。2.1 只做最上方的浏览器输入与预览。后续课程继续接上请求、保存、登录和权限。

像 1.4 一样，查看本轮实际修改范围。让 AI 只解释，再亲自打开主要文件。

:::prompt{title="只读复查本轮数据去向"}

```text
先不要修改代码。请根据这次实际修改记录和当前文件回答：
1. 输入区域主要改了哪些文件？给出真实路径。
2. 用户填写的数据暂时在哪里？
3. 有没有实际发送到服务端？有没有数据库写入？
4. 下一节接 POST API 时，当前哪些输入与预览部分可以继续使用？
请指出依据，不要把未来计划说成已完成。
```

:::

你不用完整读懂 React 表单。只需能指认：页面接收输入，目前只有前端预览，服务端尚未收到这条资料，下一节要补上这个连接。

## 给这个版本留一个保存点

检查修改文件范围，确认没有误改资料和依赖。沿用 1.5～1.6 的方法，亲手检查 Git 状态与记录，验证通过后保存可恢复版本。不要让 AI 自动执行恢复命令；若还有自己想保留的修改，先逐项分清。

## 下一节，让浏览器真正把资料交给服务端

2.2 会复用刚做好的输入入口，创建真实 POST API，让页面发送请求并接收 JSON。那时还没有数据库；长期保存要等 2.3。未完成认证和权限前，只在受控开发环境使用非敏感测试资料，不公开可匿名写入真实数据库的应用。

:::deepdive{title="为什么刷新能帮我判断预览是否保存？"}

本页的输入和预览暂时放在浏览器运行时的页面状态。刷新会重新加载页面，这段临时状态通常随之消失。将来真正保存后，页面可以再从服务端和数据库读取资料。刷新是一个有用的观察方法，但要确认真实保存，还应检查实际请求和重新读取的结果。

:::

## 卡住了怎么办

:::stuck{title="从真实文件和页面现象排查"}

### AI 找不到我的资料数据文件

让它列出当前页面实际导入的数据、组件与路径，并给出文件内容依据。你也打开文件核对；不要为了符合 `resources.ts` 示例而新造一份资料。

### 我的页面已经拆过组件

这正常。让 AI 沿现有组件关系找到列表与筛选，选择合适位置加输入区；不要求搬回单一 `page.tsx`。

### AI 把原来的资料覆盖了

先停止追加修改，查看本轮差异与旧资料。要求它只修复本轮造成的数据改动，保留你原有个性化资料；再核对旧列表与统计。不要用整项目恢复覆盖其他未保存工作。

### 输入后没有预览变化

确认点了“预览资料”、文件已保存、浏览器地址是当前项目。说清输入值、点击动作和实际显示，让 AI 检查按钮是否读取当前输入。

### AI 把预览加入了正式卡片列表

指出旧列表数量被改变，让它把预览放在独立区域，并保持原数据与列表计算不变；重新查总数与筛选。

### AI 擅自创建 API 或安装数据库依赖

本课不需要这些。先检查新增文件和依赖的范围，让它只移除本轮无关修改，保留原有项目内容；再运行项目验证。

### 刷新后预览消失，我是不是做错了？

没有。这正是本节要观察的现象：浏览器里的预览未送到服务端，也未保存到数据库。

### 我自己的 Stage 1 功能被影响

用具体操作说明原来怎样、现在怎样，让 AI 在保留预览的同时修复这次造成的问题。再次验证新旧功能，确认后才保存版本。

### 我已经有类似的输入表单

先检查它是否只做预览、是否会写入正式数据或调用 API。符合本节结果就复用，补上明确的“尚未保存”提示并完成验证，不要重复做第二套表单。

:::
