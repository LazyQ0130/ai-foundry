2.3 让你从 PostgreSQL 重新读到保存过的资料。现在打开自己的数据库资料区，选中上一节保存的一条练习记录：如果标题写错了，你会怎么办？不应要求使用者打开数据库控制台手动改。产品需要让页面把修改发给服务端，由服务端按 ID 更新数据库，再重新读取。

继续使用你完成 2.3 的项目和专用练习库，只操作自己新建的非敏感资料。此时仍没有登录和所有权检查；新增的匿名修改、删除接口只能在受控本地环境练习，**不能作为正式生产版本公开部署**。不要重新下载 Starter，也不要覆盖你自己的排序、清除筛选或其他个性化代码。

**隔天回来或重新安装依赖后，先恢复环境：**确认终端仍在同一个项目根目录，检查本地 `.env` 的 `DATABASE_URL` 指向 2.3 的**同一练习库**（只核对非秘密目标，不打印连接串），再检查 `npx prisma migrate status`。若 Prisma Client 缺失或旧类型报错，在项目根目录运行 `npx prisma generate`，再启动 `npm run dev`。这只重新生成客户端代码，不会重新建库或清除资料；不要为了恢复环境运行 `migrate reset`。后面的课程遇到同类环境问题，回看本段即可。

## 一条资料保存以后，还能改吗？

先看看数据库中已保存的资料。页面上的卡片只是显示结果：即使你在 React 数组里改了标题，刷新后数据库里的旧标题仍会回来。真正的修改路径是“编辑 → 提交 PATCH → Prisma 修改数据库 → GET 重新读取”。删除同理，隐藏卡片不等于删库。

## CRUD 到底是什么？

:::concept{title="四个动作，四次真实数据操作"}

| 名称 | 含义 | 本项目对应的操作 |
| --- | --- | --- |
| Create | 创建 | `POST /api/resources` 写入新记录 |
| Read | 读取 | `GET /api/resources` 从数据库查询 |
| Update | 修改 | `PATCH /api/resources/[id]` 更新指定记录 |
| Delete | 删除 | `DELETE /api/resources/[id]` 删除指定记录 |

本节只需理解动作、ID 和结果，不必学习整套 RESTful 架构、事务隔离或 ORM 底层原理。

:::

## 先找到你要修改的那条资料

在数据库资料区找一条**自己创建的练习记录**，记下标题、数据库 ID、创建时间。先用已有 GET 确认它确实存在。原始九条资料来自静态文件，不作为本节编辑对象；如果你自己改过示例数量，以当前项目为准。

### 为什么数据库需要 ID？

两条资料可能同名。**ID** 是数据库用来区分记录的编号。`PATCH /api/resources/12` 只应修改 ID 为 12 的记录；`DELETE /api/resources/12` 也只应删除它。标题不能可靠地代替 ID。数据库 ID 由数据库生成，删除后不重新编号；它与原始静态资料文件中的 ID 也不是一套编号。

先核对实际 `Resource` 模型：`id`、`title`、`desc`、`tag`、`important`、`createdAt`、`updatedAt`。2.3 已有迁移，本节通常**不需要改 Schema 或新增迁移**。Next.js 15 的动态 Route Handler 中，`params` 是 Promise，读取 `id` 前要 `await params`；按你项目安装的版本核对实际写法。

## 新增第一条编辑接口

在现有 `app/api/resources/` 下增加 `[id]/route.ts`，先只写 PATCH，不改页面。它接收标题、简介、分类和 important：仍拒绝空白、过长文字和非法分类，`important` 必须是布尔值。ID 要是合法正整数，数据库不存在该 ID 时回 HTTP 404。成功时返回 HTTP 200、`{ok:true,resource:{...}}`，其中 `resource` 是 Prisma 更新后的真实记录。数据库不可用不能伪造成功。

:::prompt{title="第一段：按真实数据库 ID 新增 PATCH"}

```text
请先读取我当前项目的 Prisma Resource 模型、2.3 的 POST/GET Route Handler 及真实分类来源，再增量新增 PATCH /api/resources/[id]。按当前 Next.js 版本核对动态参数的读取方式；Next.js 15 的 params 需要 await。
PATCH 接收 title、desc、tag、important，复用已有服务端验证规则：文字类型、trim 后非空、标题最多 100 字、简介最多 500 字、分类必须是现有分类且不是“全部”，important 必须是真正的 boolean。ID 仅接受合法正整数。成功用 Prisma 按该 ID 更新，返回 HTTP 200 和数据库实际更新后的 {ok:true,resource}；不存在返回 404，输入错误返回 400，数据库失败不伪造成功，也不把连接密码返回浏览器。
不要改变原 POST/GET 的契约，不修改页面，不新增 User、Session、owner 或依赖，不操作 Git。完成后列出真实修改文件，并先用独立练习记录验证 PATCH 前后数据库内容。
```

:::

先用真实 HTTP 请求对自己新建的练习 ID 测试合法 PATCH，再 GET 核对。额外试不存在的 ID、`0`、非数字 ID、空标题、坏分类、`important:"true"`；应分别得到 404 或 400，数据库原记录不变。**404** 表示指定 ID 的记录不存在，不能把它当作“更新成功但页面没刷新”。

:::check{title="先证实接口再接按钮"}

- PATCH 成功响应中的 `resource.id` 与目标 ID 一致，字段为更新后的数据库值。
- GET 再读仍是新值；数据库只读查询也能看到变化。
- 无效 ID、空标题、坏分类、错误 important 类型不会更新任何记录。

:::

## 让页面可以编辑已有资料

在当前数据库资料展示组件中，为每条真实数据库记录加“编辑”。点开时把该条记录当前标题、简介、分类和 important 预填到表单。点“取消”只关闭表单，**不发送 PATCH**；点“保存修改”才请求 `/api/resources/实际ID`。成功响应后另发 GET，让页面显示新数据库结果。保存期间禁用重复提交。若 PATCH 成功但 GET 失败，应保留修改已成功的事实，提示单独“重新读取”，不要自动再 PATCH。

不要在原始静态卡片上放这个编辑入口，也不要仅把本地数组改掉就提示成功。浏览器里可以看到旧值预填、字段被修改、刷新后仍是新值，才是可观察的完整链路。

## 删除不是让卡片暂时消失

删除会真实改变数据库。实验只用**自己新建、明确可以删除**的练习记录。不要对旧课程资料、平台业务数据或别人保存的资料做删除实验。

### 第一次创建 DELETE 接口

同一个 `[id]/route.ts` 增加 DELETE。服务端校验 ID，Prisma 按单个 ID 删除，成功回 HTTP 200、`{ok:true,deletedId:实际删除的ID}`；不存在回 404，非法 ID 回 400，数据库失败回错误 JSON。不要做无 ID 的批量删除、清空表、`migrate reset` 或重排 ID。

:::prompt{title="第二段：只按指定 ID 删除练习记录"}

```text
请在刚创建的 [id]/route.ts 增加 DELETE /api/resources/[id]，先检查真实文件与 Resource 模型。ID 必须是合法正整数；用 Prisma 删除这一条记录。成功返回 HTTP 200、{ok:true,deletedId:数据库实际删除的ID}；不存在返回 404，数据库故障返回明确失败，不伪造删除成功。
只允许单个明确 ID；不要新增无 ID 的批量删除、清空 Resource 表、运行 migrate reset、修改迁移或安装依赖。暂不修改页面，不操作 Git。用专门创建的可删除练习记录验证 DELETE 前后数据库记录数及其他 ID 不变。
```

:::

### 删除之前先确认

每条数据库记录的“删除”按钮应明确显示目标标题与 ID，并要求二次确认。取消时**不得发送 DELETE**。确认后才发送请求，成功后 GET 列表；删除期间禁用重复点击。如果 DELETE 成功但 GET 失败，不自动再删一次，提示重新读取。不能只在浏览器隐藏卡片。

:::warning{title="删除真的会改变数据"}

只删除本节自己新建的练习记录。普通 Git commit 保存代码，**不会自动备份或恢复数据库中的记录**。若真实记录已删除，又没有数据库备份或其他来源，不能保证找回。

:::

## 刷新以后结果还一样吗？

刷新会清掉当前表单状态，并触发新的 GET。修改后的 A 应继续显示新标题；删除后的 A 不应再出现。服务端响应、刷新后的 GET 和数据库只读查询要指向同一 ID。若页面先变了、刷新后恢复，检查是不是只改了 React 状态、PATCH 返回错误或 GET 仍读静态文件。

## 修改 A，为什么 B 不应该变化？

两条记录的 ID 不同。PATCH 与 DELETE 都带明确的 ID，服务端 `where: { id }` 只能作用于该条。测试时除了看 A，也要查 B 的原始 ID、标题和字段；B 不变才证明没有误用标题查找、错误遍历或批量操作。删除 A 后，B 的 ID 不会重新编号。

现在你能按 ID 管理数据库记录，但接口仍没有登录或资源所有权检查，只能用于受控本地练习。2.5 才引入注册、登录与 Session，2.6 才处理服务端所有权。不要把当前匿名修改、删除接口公开部署。

:::deepdive{title="为什么更新后还要再次 GET？"}

PATCH 的成功响应说明服务端报告已更新；新 GET 证明另一请求能从数据库读到结果。刷新再 GET 排除只改当前页面状态的误判。若写操作成功后读取失败，先恢复读取确认状态，避免重复写入或删除。

:::

## 卡住了怎么办

:::stuck{title="按 ID、请求、数据库、页面逐层排查"}

### PATCH 返回 404

先 GET 核对目标 ID 是否仍存在。确认路径里传的是真实数据库 ID，不是静态示例 ID 或标题；不要为消除 404 另建同名记录冒充原记录。

### DELETE 返回 404

先重新 GET。若记录已不在，可能已删除过；不要反复 DELETE。若还在，检查 URL 的 ID 与当前卡片 ID。

### ID 传递不正确

检查按钮绑定的记录、URL 中的数字及服务端解析。`0`、负数、字母和超出可接受范围的 ID 应被 400 拒绝，不能落到“删除第一条”的默认行为。

### 编辑框没有显示旧内容

检查点击编辑时是否使用该条 GET 返回的 `resource` 预填，而不是新建表单的空白状态。不同卡片连续打开也应切换到对应 ID 的值。

### 点击保存后页面变化，但刷新后恢复

看 PATCH 实际状态码、响应 ID、接下来的 GET 和数据库只读查询。只改本地数组或缓存旧 GET 都无法证明持久化。

### 删除后卡片消失，但数据库记录仍存在

确认 DELETE 得到成功响应且返回的 `deletedId` 正确，再 GET 和只读查库。若只是前端过滤了卡片，恢复显示并修好真实删除路径。

### 取消删除仍然发出了请求

检查确认框的分支，必须在用户确认后才调用 fetch。取消后看服务端请求日志或 Network；不应出现 DELETE。

### 修改 A，却影响了 B

立即停止更多写操作，核对两个 ID 和服务端 `where` 条件。只对新建的练习记录修复与重测；不要批量“修正”全表。

### 数据库连接失败

GET/PATCH/DELETE 都不能显示假成功。检查专用练习库连接状态，恢复后先重新读取，再决定是否重试写操作；不要输出数据库密码。

### 错误输入仍然更新成功

直接向服务端发送空标题、坏分类、字符串形式的 important。服务端应回 400；前端输入控件的限制不能代替服务端校验。

### AI 修改了原始静态资料

查看差异，区分本轮和以前的个性化内容。要求只修复本轮误改，保留原有资料和功能；不要整项目覆盖。

### 原来的搜索或筛选坏了

用修改前的关键词、标签、重要筛选和自选排序/清除筛选重现；确认旧列表仍按自己的原始来源计算，然后针对破坏处修复。

### 旧数据被误删怎么办

先停止写请求，核对目标 ID、数据库备份和可恢复来源。没有备份或其他来源时，已经真正删除的数据库记录可能无法恢复；Git commit 不能自动恢复数据库数据。

:::
