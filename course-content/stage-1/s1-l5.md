上一节，你已经会问 AI 改了哪个文件、哪块代码对应页面变化。接下来还有一个很实际的问题：如果下一次不满意，怎么回到现在这个能用的状态？

这次先亲手保存，再让 AI 做一次很小的实验，最后把实验恢复掉。不需要背一套命令，先经历一次“我知道自己可以回去”。

继续使用完成 1.4 的项目，不要用重新下载的 Starter 覆盖它。如果还没有重要筛选或当前数与总数，先完成前面的课程。标题、颜色、控件写法可以和课文不同。

## 先别急着让 AI 继续改

先花一分钟确认项目现在是好的。保持开发服务器运行，在浏览器做下面几步：

1. 刷新，确认默认卡片与当前数量一致，总数量正确。
2. 开启重要筛选，看卡片和当前数一起变化。
3. 关闭重要，再点工具，看工具资料正常出现。
4. 切回全部，搜索 `Next.js`，确认结果和数量正常；清空搜索。

原始资料下，以上当前数分别是 9、3、2、1，总数一直是 9。改过数据就按自己的资料检查，不必凑数字。如果页面本来就坏了，先处理问题，不要把它当作好版本保存。

现在这个项目是能用的，先给它留一个你以后能回来的位置。记下当前大标题和介绍，稍后恢复时要对照它们；不用改成老师的文字。

:::concept{title="Git 帮你记录项目版本"}

Git 是记录项目不同版本的工具。交给 Git 记录版本的项目，叫仓库，也可能看到英文 repository。commit 先理解成一个版本保存点。

GitHub 是可以把 Git 项目放到网上的平台之一。本节只用本机 Git，不需要 GitHub 账号或网上仓库。

:::

## 电脑上有没有 Git？

另开一个项目终端，让原来的 `npm run dev` 继续运行。像第 0 课一样，确认这里能看到 `app`、`components`、`lib` 和 `package.json`，并且与 AI 打开的项目是同一个目录。

下面的命令由你自己输入终端，一次一条，按 Enter 执行。不要把它们全部发给 AI 代做。

```bash
git --version
```

看到类似 `git version 2.x.x` 就说明已经安装，版本号不必相同。

Windows 找不到命令时，从 [Git 官方 Windows 安装页](https://git-scm.com/install/windows) 安装 Git for Windows。不知道选什么时，保持默认选项通常即可。完成后关闭旧终端、重新打开，回到项目目录再试。

macOS 如果命令能返回版本号就继续；若系统提示安装 Command Line Tools，按提示完成后再试。需要安装说明时查看 [Git 官方 macOS 安装页](https://git-scm.com/install/mac)。安装等待不计入本课预计时间。

### 项目是不是已经在用 Git

```bash
git status
```

正常显示状态，说明 Git 已经在记录这个目录所属的项目，不要再初始化。若列出的文件明显属于上一级目录或另一个项目，先停下确认位置；不要把别人的项目一起保存。

如果提示 `not a git repository`，先确认终端确实在自己的项目根目录。位置正确、项目还没有 Git 时，才依次运行：

```bash
git init
git status
```

`git init` 就是在说：“从现在开始，我想让 Git 记录这个项目的版本。”它会创建隐藏的 `.git` 目录，保存版本信息；不要手动编辑或删除它。

课程的 Starter ZIP 不带 `.git`，所以一路从 ZIP 开始的学生通常要初始化。但你或 AI 以前可能已经做过，也可能已有提交记录；以自己的实际状态为准。

## 给现在这个好版本留一个保存点

### 先看看哪些文件准备被保存

`status` 就是在问 Git：“项目里还有哪些变化没保存？”第一次可能看到很多 `Untracked files`，意思是 Git 还没开始记录这些文件；以后改过的文件常显示为 `modified`。

先看文件名，再考虑保存。不要看到一长串输出就直接往下执行。

**先打开项目根目录的 `.gitignore`。** 它告诉 Git 哪些文件不用纳入版本历史。正常下载的 Starter 已经带上这个文件，第一次保存前确认它仍然存在，并检查下面这些规则，不需要重新创建。如果你用的是旧下载、自己删过它，或项目不是来自官方 Starter，按文末“没有 .gitignore，或规则不完整”处理。

```text
/node_modules
/.next/
/out/
.DS_Store
*.pem
npm-debug.log*
.env*
```

检查后重新运行 `git status`，确认 `node_modules`、`.next` 和 `.env` 一类文件没有出现在待保存列表中，再继续下面的 add。

`node_modules` 没进版本点是正常的，依赖可以重新安装。`.env*` 这类环境文件也通常不应该提交，本课不需要你创建它们。`.gitignore` 自己应该保存进版本点。

如果这些目录或环境文件仍然出现，先看文末排查。已经被 Git 记录的文件不会因为补上忽略规则就自动消失，不能以为补了文件就一定安全了。

确认列出的都是准备保留的项目内容后，亲手运行：

```bash
git add .
git status
```

`git add .` 大致是把当前目录里这次准备保存的修改选进来。再看 `status` 的 `Changes to be committed`，就是接下来准备保存的文件。它可能是新增，也可能是修改或删除；每个都应当是你这次愿意留下的变化。

### 第一次 commit

文件列表确认无误，再运行：

```bash
git commit -m "save working version"
```

这条命令真正创建保存点。引号里的说明让你以后知道这是什么状态。这里统一使用简单英文，意思是“保存可用版本”，不用为了练习记一种固定格式。

如果出现 `Author identity unknown` 或 `Please tell me who you are`，Git 还不知道这次记录署谁的名字。把下面引号里的内容换成你自己的名字和邮箱，只为当前项目配置：

```bash
git config --local user.name "你的名字"
git config --local user.email "你的邮箱"
```

`--local` 只影响这个项目，不改整台电脑的 Git 设置。已有可用身份就不用重复配置。这是版本记录的署名信息，不是注册账号，也不用输入邮箱密码。

然后重新执行刚才的 `git commit -m "save working version"`。不要把失败提示当成已保存。

### 确认保存点真的存在

```bash
git log --oneline -n 3
git status
```

`log` 列出最近几个保存点。找到刚才的 `save working version`：左边一串短字符是版本编号，右边是版本说明。不用背编号，但要亲眼确认这条记录存在。

再看 `status`，应该出现 `working tree clean`。它表示当前文件和刚保存的版本一致，没有新的待保存修改；被忽略的依赖和缓存不算在这里。

如果你已经有提交，当前也没有变化，commit 可能提示 `nothing to commit`。这正常：用 `log` 确认已有保存点，再确认 `status` 为 clean 即可，不需要创建两份内容相同的记录。

如果还列着变化，先弄清它们是什么，再继续。**实验必须从已确认的保存点和 clean 状态开始。** 暂停 AI 的其他修改任务，避免把自己的新工作混进这次实验。

## commit 不是把项目上传到网上

保存文件与保存版本是两件事：`Ctrl+S` 或 AI 写入文件，把当前内容放到磁盘；commit 则记录这次选入的项目文件状态，建立一个以后能认出的版本点。

commit 没有上传到互联网。现在的 Git 历史保存在项目里的 `.git` 中；如果整个项目文件夹连同 `.git` 都丢了，这份本地历史也会丢。本课先完成本地保存与恢复，不处理云端备份。

## 现在故意改一点东西

这次不需要再制造复杂 Bug。只换两处显眼的文字，就能看见保存前后有什么不同。先记住刚才的大标题和介绍，再把下面这段发给 AI。

:::prompt{title="只做页面实验，不操作 Git"}

```text
现在做一个版本恢复实验。请读取当前项目，把页面中央的大标题临时改成“版本恢复实验”，把紧接着的介绍改成“这段修改稍后会恢复”。
只修改实现这两处文字所需的现有文件，保留顶栏、页脚、样式、搜索、筛选、统计和资料数据，不新增文件或依赖。
不要运行任何 Git 命令，不要创建 commit，也不要恢复文件。
直接保存文字修改，完成后告诉我实际修改了哪些文件，以及原来的标题和介绍。
```

:::

AI 可以找文件、改实验文字、解释现象，但本节的 add、commit、restore 都由你亲手完成。**从现在到恢复结束，不要再运行 add 或 commit，也不要点工具里的“全部保存为版本”一类操作。** 我们要丢弃这两处临时变化，不把它们选入下一次保存。

回到浏览器，确认标题真的成了「版本恢复实验」，介绍成了「这段修改稍后会恢复」。如果没有变化，先检查文件是否保存、浏览器地址是否正确，不要只凭 AI 回复继续。

## Git 知道项目已经变了

```bash
git status
```

刚才还是 clean，现在应当出现 `Changes not staged for commit`，下面列出实验改过的文件。先理解成“保存点之后，文件又变了，这些变化还没有被选进下一次保存”。

把文件名和 AI 报告的路径核对。在常见实现里是 `app/page.tsx`；如果标题拆进组件，也可能是组件文件。不能因为课文写了一个路径，就照着恢复那个文件。

你还可以用 1.4 认识的工具改动对比，确认变化确实只是那两处文字。没有 Diff 面板，打开文件看实验文字也行，本节不增加必须掌握的对比命令。

## 回到刚才那个能用的版本

### 先确认要恢复哪个文件

再看一次 `git status`。确认实验变化都在 `Changes not staged for commit` 下，并且这些文件里没有自己还想保留的新修改。如果出现 `Changes to be committed`、新的未跟踪文件，或者 AI 已经创建了新 commit，先停下来按文末排查，不要套用下面的恢复步骤。

:::warning{title="restore 真的会丢弃修改"}

恢复会丢弃指定文件中当前未提交的实验修改，而且是整个文件，不只标题那两行。先确认这个文件里保存点之后的变化全都不要了；如果还混着想保留的修改，就不要执行。

Git 通常不能保证找回被丢弃、又从未 commit 的普通修改。先看清，再恢复。

:::

### 亲手 restore

这次从 clean 保存点开始，实验后又没有 add 或 commit，所以 `git restore` 可以让指定文件回到刚才保存时的内容。它不是选择任意历史版本的通用按钮。

例如，**只有当你的真实路径确实是 `app/page.tsx`** 时，才执行：

```bash
git restore "app/page.tsx"
```

如果改的是别的文件，用 `git status` 中的真实路径替换引号里的内容。路径有空格也要保留英文双引号。涉及两个文件，就先逐个确认，再分别执行；不要把整个项目一次性恢复。

### 页面和 Git 都再检查一次

回浏览器刷新，核对标题与介绍回到了你记录的实验前内容。它可能是你在 1.1 自己写的文字，不一定是「个人知识工作台」。

再按开头顺序点一次：默认 → 重要 → 关闭重要后选工具 → 切全部搜索 Next.js。卡片、当前数与总数都应正常。清空搜索。

然后运行：

```bash
git status
git log --oneline -n 3
```

应回到 `working tree clean`，刚才的保存点仍在。页面恢复了、Git 也与保存点一致，这次实验才完成。如果还有变化，先看文件名，不要为了得到 clean 就继续随意丢弃文件。

## 什么时候值得保存一个版本

一个功能刚验证通过、一个 Bug 刚修好，或者准备让 AI 试一个自己不确定的方案，都适合先保存。

不必每改一个字就 commit 一次。在你觉得“现在这个状态我愿意回来”的时候保存，然后再继续尝试。这样不满意时，你有一个确认过的起点，不必一直叫 AI 接着改。

版本说明写清现在是什么状态即可，例如“完成重要资料筛选”“修复筛选组合问题”“完成统计展示”，或本次的 `save working version`。不用学习一套命名格式。

## 自己再做一次

:::task{title="不用逐条照抄，再确认一次保存点"}

先检查当前项目正常，再用自己的版本说明建立第二个保存点，并用 log 找到它。这次自己回想顺序：先看变化、选入准备保存的内容、创建保存点、检查记录与状态。

如果刚恢复完没有任何新变化，可以做一个自己真正想保留的小文字调整，验证后再保存。如果没有想改的，就只确认已有保存点。看到 `nothing to commit` 是正常的，不要为了练习造一个无意义功能或空版本。

:::

:::check{title="离开前，确认自己做过这些动作"}

- 亲手检查了 Git，并按实际情况选择初始化或沿用已有仓库
- 检查忽略规则和待保存文件后，创建或确认了可用状态的 commit
- 用 status 看过实验前后的变化，用 log 找到了保存点
- 看清真实路径，只恢复了确认不要的实验文件
- 页面标题、介绍、搜索、筛选、统计恢复正常，知道未提交的修改不一定能找回

## 卡住了怎么办

:::stuck{title="先看状态，别急着恢复"}

### git 命令找不到

按前面的官方安装指引装好 Git，重新打开终端，回到项目目录，再运行 `git --version`。不要只在旧终端反复输入。

### not a git repository

先核对目录是不是自己的项目根目录。确认未初始化才用 `git init`；如果以前明明有记录，先查是否打开了另一份项目，别急着建新仓库掩盖问题。

### Author identity unknown

按“第一次 commit”中的两条 `git config --local` 配置自己的名字、邮箱，再重试同一条 commit。已有身份无须重配，不要把个人信息发到公开求助帖。

### 没有 .gitignore，或规则不完整

先确认打开的是项目根目录。如果确实缺少，在自己的项目中新建 `.gitignore`，不要命名成 `.gitignore.txt`，补上前面列出的规则；已有文件只补缺少的部分，保留原内容。可以让 AI 只处理这个文件，不执行 Git 命令。保存后重新看 status，不要为补一个文件重新下载并覆盖整个项目。

### add 后出现一大堆 node_modules，或出现 .env

先不要 commit。核对目录，检查 `.gitignore` 是否真实保存、名字是否正确，并确认这些文件有没有已经被选入或以前就被记录。

Stage 1 没有要求创建秘密环境变量。自己创建过的 `.env` 先在本地确认内容，不要把里面的值贴给 AI。可以只提供文件路径和 Git 状态，让 AI 只读说明原因、指出需要排除的文件，不自动执行命令；确认待保存列表不含这些文件后再继续。新增忽略规则不会自动移除已经选入或记录的文件。

### commit 后仍然有变化

先看具体文件，可能是 AI 又改了、工具生成了未忽略文件，或 commit 前没全部选入。弄清内容再决定是否保存，不要直接 restore。没有回到已确认的 clean 起点，就先不开始实验。

### AI 实验修改改了很多文件

用 status 和本次修改记录逐个核对，问 AI 为什么需要改。尤其检查有没有自己还想保留的未提交内容；同一个文件里混着两种修改时，也不要整文件恢复。先让它只读解释，不要让它自动操作 Git。

### 实验后误做了 add，或者 AI 创建了 commit

先停下。若变化出现在 `Changes to be committed`，普通 restore 可能恢复到已选入的实验内容，并不会自动回到前面的好版本；若实验已 commit，也已超出本次“丢弃未保存实验”的流程。

把 status、最近三条 log 和实际操作告诉 AI，要求只解释当前情况，不执行恢复命令。确认保留与丢弃的内容后再处理，不要在不清楚状态时试一串撤销命令。

### restore 提示 pathspec 不存在

回到项目根目录，用 status 复制真实路径，注意大小写和空格引号。不要凭课文示例猜。如果它是新建、尚未记录的文件，普通 restore 不能按保存点还原它；这次实验本来只应改现有文件，先查为什么出现新文件，不要批量删除。

### restore 后页面没变化

先打开文件看实验文字是否已恢复，再核对开发服务器仍运行、浏览器 Local 地址正确，并刷新。也检查实验修改是否曾被 add 或 commit；别反复对同一路径执行而不看状态。

### 不小心恢复了还想保留的内容

不要承诺一定能找回。Git 通常不能恢复从未 commit、已被丢弃的普通修改。可以看看编辑器是否保留本地历史或 AI 对话是否有原片段，但它们不一定存在。这正是重要状态要先 commit 的原因。

### working tree clean 或 nothing to commit

这是好事：Git 没看到需要再保存的新变化。用 log 确认已有保存点，不是“Git 没工作”。

### LF will be replaced by CRLF

这是 Windows 上常见的换行格式提示，通常不代表本次保存失败。看命令是否完成，再用 log 和 status 确认；如果同时有真正的错误，把完整错误和刚才命令交给 AI 分析，不要为这一条提示修改整台电脑的设置。

:::

:::deepdive{title="commit 到底保存了什么？"}

Git 记录这一刻项目中被纳入版本管理、并被你选入本次保存的文件状态。`git add .` 后又改了文件，不会自动把更晚的变化补进这次 commit，所以保存前后都要看 status。

依赖、缓存等被忽略的内容不在保存点里。commit 也不是浏览器截图，不会记住你当时搜了哪个词。

:::

:::deepdive{title=".git 文件夹是什么？"}

它保存 Git 的本地版本信息。一般不需要打开，更不要手动编辑或删除；丢掉它，也就丢掉这个项目放在这里的历史记录。保存过文件不等于保存过版本，有本地版本也不等于有云端备份。

:::
